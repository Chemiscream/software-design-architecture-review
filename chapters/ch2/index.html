第 2 章 · 软件架构

架构：需求与程序之间的蓝图

架构决定系统由哪些组件组成、组件怎么合作、部署到几台机器上， 也因此决定了性能、可用性、可修改性这些非功能性质量。 本章只有 13 页课件，但每一个标题背后都是简答题和选择题的常见考点—— 我们把它展开成「定义 → 质量 → 视图 → 决策 → 文档」五段可答题的结构。

考试重点 约 30 分钟 高频简答 + 选择 架构视图必考
开始阅读 直接自测 查看课件原图

学习目标

读完后应能做到以下几点，而不是「看过一遍」。

  1. 能用一句话给出软件架构的定义，说清它处在「需求」与「程序」之间的什么位置，以及为什么它主要负责非功能性质量。
  2. 能列举至少 8 个质量属性，并对性能、可用性、可修改性、安全性、可测试性各说出一种典型架构手段及其代价。
  3. 能从逻辑、开发、进程、物理四个视图描述同一个系统，并说明「场景（+1）」为什么不是第五个并列视图。
  4. 能区分参考架构、架构模式、设计模式三者的粒度与复用方式，并说出直接套用参考架构的风险。
  5. 能针对一个具体场景写出含「背景—决策—备选—后果」的架构决策，并说明架构文档应该记录哪些内容。

02

核心概念

#

先把 10 个术语的边界钉死。简答题写不准，多半是术语混了。

软件架构 Software Architecture

对系统的结构的作用和系统的行为进行建模，是系统设计阶段的初步结果， 负责连接系统的需求与技术上的解决方案，主要承担系统的非功能性质量。

定义 高频简答

组件 Component

系统分解后得到的物理组成部分。设计要求组件高内聚、组件之间低耦合， 并且只通过接口合作，从而可以独立开发、替换与复用。

结构 高内聚低耦合

架构关注点 Architectural Concern

架构需要回答的问题集合：系统怎么分解、组件怎么交互、部署到哪、遵循什么策略。 关注点是横切的——同一个关注点会同时牵动多个组件，所以必须在架构层统一决策。

横切

质量属性 Quality Attribute

衡量系统「好不好用」而非「能不能用」的属性。课件分为两类： 非功能性质量（性能、可用性、可修改性……）与功能性质量（保障性、安全性、并行性/并发性）。

考试重点 分类易错

架构视图 Architectural View

从某一类利益相关者关心的问题出发，对架构做的一个侧面的描述。 经典做法是 4+1：逻辑视图、开发视图、进程视图、物理视图，再加一个把四者串起来的场景。

4+1 必考

参考架构 Reference Architecture

为完成一定业务目标而应用的软件架构的部分内容，包含可以复用的部分： 既可以包含各种结构（架构）模式，也可以包含业务组件。

复用 含业务

架构模式 Architectural Pattern

软件结构的模板：把所关注的系统按一定策略分解为可扩展的子系统， 并规定这些子系统之间的合作方式；但不涉及解决具体业务领域问题的部分。

模板 子系统级

设计模式 Design Pattern

体现系统中可扩展的类所承担的特殊作用，通过它们的合作解决相关问题。 粒度在类/对象级，比架构模式更细。

类/对象级 第 3–4 章

架构决策 Architectural Decision

影响系统整体结构、难以事后更改的那类决定。判据是代价： 改起来越贵、波及面越广，就越属于架构决策，必须留下理由与备选方案。

重点 记录理由

架构原型 Prototype

用最小成本验证架构设想的产物，课件列出三种： 水平原型（广而浅）、垂直原型（窄而深）、可行性原型（专攻技术风险）。

验证 易混

答题技巧 凡是问「架构的作用」「为什么需要架构」，都按「定义 + 作用 + 代价」三段写： 定义（蓝图 / 需求与程序的桥）→ 作用（降低复杂度、规定结构与实施流程、承载非功能性质量、支持复用与分工） → 代价（前期投入、可能过度设计、架构错了返工成本极高）。这样写比堆要点更容易拿分。

03

架构详解

#

按课件的 2.1 → 2.5 顺序展开，每一段都补上「为什么」和「代价」。

3.1 架构的位置：需求与程序之间的蓝图

课件用一张图概括了架构的位置：需求在上、程序在下、架构在中间。 上层是「要什么」（功能需求与质量要求），下层是「怎么写」（具体代码与实现细节）， 架构负责把前者翻译成后者的约束条件——它不写代码，但规定了代码必须长成什么样。

01

需求

功能需求 + 质量要求（性能指标、可用性目标、安全合规、交付节奏）。 这一层用的是业务语言，还没有任何技术选择。

02

架构

把需求翻译成结构：组件怎么划分、接口怎么定义、交互怎么组织、部署到哪。 这一层用的是结构与约束语言，是设计阶段的初步结果。

03

程序

在架构规定的框架内编写代码。这一层用的是实现语言（类、方法、SQL）。 架构错了，这一层写得再好也救不回来。

课件给架构的定性是「抽象化实现系统的蓝图」，作用有两条： 降低复杂度（把一个大问题切成若干可分别处理的小问题）、 规定系统的结构和实施流程（让多人可以并行工作而不互相踩踏）。 同时它强调架构是高层次对编程的规定，并且「发现合适架构的过程是循环往复的」—— 这句话很重要：架构不是一次成型，而是随着对需求和技术理解加深而迭代。

理解要点 「架构是蓝图」这个比喻要落到两个可考的点上： ① 蓝图不含每一块砖怎么砌（不含实现细节）； ② 蓝图一旦画错，改的是整栋楼（架构决策的返工成本最高）。 这两点分别对应「抽象层次高」和「决策重量大」。

3.2 系统架构到底包含什么

课件把「系统架构包括」的内容列成四条，考试常以多选或简答出现，需要能背出并解释：

  1. 把系统分解成物理上的组成部分（组件）——这是静态的，涉及结构。
  2. 分布式系统中每个组件分配到计算机（部署）——决定进程边界、网络调用与故障域。
  3. 描述所有组件动态的相互作用——这是动态的，涉及行为与协作流程。
  4. 描述架构的策略，即架构的静态和动态的功能——规定系统按什么原则运转。

课件特意点明两句话，都是判断/辨析题的题眼： 「分解是静态的，涉及结构；相互作用是动态的」； 「系统的功能以结构为基础，不能与之分离」。 后者直接否定了「先随便定结构、功能以后再补」的幻想—— 结构不支持的功能，后期很难靠编码硬补出来（例如没有预留扩展点的单体系统要支持多租户）。

到了设计阶段，架构的要求落成一句硬指标： 必须划分组件，组件通过接口合作，组件具有高内聚性、相互间低耦合性。 内聚回答「一个组件内部的东西是否相关」，耦合回答「两个组件之间的依赖是否可替换」。 架构层面的耦合往往是部署耦合（必须一起上线）和数据耦合（共享同一张表）， 比类之间的耦合更难拆。

3.3 为什么说架构主要负责非功能性质量

课件有一句非常关键的判断：「架构和功能是完全不同的概念，功能在架构下运行」。 功能回答「系统能做什么」，架构回答「系统以什么结构、在什么约束下做这些事」。 两个团队可以实现出功能完全相同、但质量天差地别的系统，差别就在架构。

更准确地说，功能由需求决定，而功能能否达到预期的质量水平由架构决定。 同一句「用户下单」的需求，在单体事务里是几行代码， 在分布式架构里就要处理幂等、补偿、最终一致——功能没变，架构变了，质量属性也跟着变。 所以架构评审的重点通常不是「功能对不对」（那是需求评审和测试的事）， 而是「这个结构能不能支撑目标质量，代价是什么」。

注意课件的分类口径 课件把 安全性、保障性、并行性/并发性 归在「功能性质量」下面， 这与很多教材把安全性视为非功能属性的习惯不同。答题时按课件口径写， 若题目要求展开，可以补一句「通行教材亦常将安全性视为非功能属性，分类口径因教材而异」， 既不失分又显专业。

3.4 质量属性逐条：手段与代价

质量属性不是形容词，而是可以用场景描述、可以被度量的目标。 下面五个是简答题最常要求展开的，每个都按「定义 → 典型架构手段 → 代价」记。

性能 Performance

定义：单位时间内完成的工作量，或单次请求的响应时间（吞吐量 / 延迟）。

手段：缓存、异步与消息队列、并发与线程池、读写分离、CDN、批量合并请求。

代价：缓存带来一致性问题和失效策略复杂度；异步带来最终一致与排障困难； 并发带来竞态与死锁风险。

可用性 Availability

定义：系统在需要时可正常提供服务的时间比例（如 99.9%）。

手段：冗余与集群、健康检查与心跳、故障转移与自动重启、限流降级、多机房部署。

代价：冗余直接抬高成本；多副本带来数据同步与一致性难题； 故障转移引入「脑裂」与切换窗口。

可修改性 Modifiability

定义：以可接受的成本与风险对系统做变更的能力，覆盖可扩展性、可维护性、可移植性。

手段：清晰的分层与模块边界、面向接口编程、依赖倒置、配置外置、插件化扩展点。

代价：抽象层增加间接调用与理解成本；预留扩展点可能永远用不上（过度设计）。

安全性 Security

定义：系统抵抗未授权访问、数据泄露与恶意输入的能力（机密性、完整性、可用性）。

手段：认证与授权分离、统一网关与入口校验、最小权限、传输与存储加密、审计日志。

代价：加密与校验带来性能开销；多层校验增加运维复杂度；权限模型过细会拖慢业务迭代。

可测试性 Testability

定义：通过测试发现缺陷、验证质量的容易程度。

手段：组件可独立启动、依赖可注入（依赖倒置）、接口契约清晰、可观测性（日志/指标/链路追踪）。

代价：为可测试而拆分接口会增加类型与样板代码； 可观测性埋点有运行时开销。

可理解性 / 可维护性 / 复用性

定义：可理解性=读懂的难易；可维护性=修改与修复的综合成本；复用性=资产被再次使用的程度。

手段：一致的命名与分层约定、文档与视图、稳定的组件接口、去业务化的通用组件。

代价：为复用而抽象会让组件脱离具体场景，反而增加接入成本（复用不是免费的）。

答题技巧 质量属性之间是互相拉扯的：提高安全性要加密（伤性能），提高可用性要冗余（伤成本与一致性）， 提高可修改性要多加抽象层（伤性能与可理解性）。所以题目问「如何提高某质量属性」时， 只答手段会丢分，必须补一句代价与权衡——这正是架构工作的本质。

3.5 观察架构的角度与 4+1 视图

课件 2.4.3 列了六个观察角度：各利益相关者的角度、分析系统所处的环境（黑盒观点）、 分析系统的逻辑模型（白盒观点）、系统开发进程、 业务系统的组建和系统管理员方案的建设、确定各种方案的依据文档。 这六条其实就是「不同人关心不同侧面」的朴素表达，而工业界把它标准化成了4+1 视图。

为什么必须分视图？因为一张图放不下所有关注点：给运维看的部署拓扑和给程序员看的模块依赖， 画在同一张图里只会两边都看不懂。视图是同一份架构在不同关注点下的投影，不是四份不同的架构。

静态 · 结构

逻辑视图 Logical

系统提供哪些功能、由哪些类与对象协作实现，关注职责划分与依赖关系。

读者：设计人员 / 需求方　典型图：类图、对象图

静态 · 结构

开发视图 Development

代码怎么组织成模块、包、构件，如何编译、构建、分配给团队，关注可复用与可分工。

读者：程序员 / 构建负责人　典型图：包图、构件图

动态 · 行为

进程视图 Process

运行期有哪些进程、线程，如何并发、同步、通信，关注吞吐、性能与容错。

读者：系统集成人员　典型图：活动图、时序图、状态图

动态 · 行为

物理视图 Physical

软件部署到哪些硬件节点、网络如何连接，关注拓扑、可用性与伸缩。

读者：系统工程师 / 运维　典型图：部署图

+1 · 串联与验证

场景 / 用例 Scenarios

用若干关键用例把四个视图串起来，并检验它们是否自洽： 一个「考试提交」场景，会在逻辑视图里走哪些对象、开发视图里跨哪些模块、 进程视图里经过哪些线程、物理视图里落到哪些机器。

读者：全部利益相关者　作用：发现视图之间的矛盾，也是架构评审的抓手

所以「+1」不是第五个并列视图，而是验证与驱动：场景从需求中来，用来检验四个视图； 反过来，四个视图的取舍又由关键场景的优先级决定。回答「4+1 中 +1 是什么、有什么用」， 这两层意思都要写到。

常见错误 把 4+1 视图理解成「画五张图就完事」。视图的价值在一致性： 逻辑视图里有一个「订单服务」，进程视图里就应有对应的进程/线程， 物理视图里就应有承载它的节点。任何一处对不上，都是架构的漏洞。

3.6 参考架构、架构模式、设计模式：三个粒度

课件 2.3 把三者放在一起讲，核心是粒度与是否含业务：

  • 参考架构——「包含可以复用的部分」，是为完成一定业务目标而应用的架构的部分内容。 它可以包含各种结构模式和业务组件，因此范围最广。
  • 架构模式——与参考架构一样是软件结构的模板，但不包含解决具体业务领域问题的部分。 它的目标是把系统按一定策略分解为可扩展的子系统，并规定子系统之间的合作。
  • 设计模式——粒度最细，体现系统中可扩展的类的特殊作用，通过类的合作解决相关问题。

课件对三者关系的总结值得逐句记住：

  • 三者都可以包含组件；
  • 参考架构可以包含各种结构模式和业务组件；
  • 以参考架构为基础的系统不需要进行全部系统设计，组件可以复用，具有一定扩展性；
  • 参考架构的缺点：不一定完全适用，可能不完全符合要求；
  • 架构模式可以包含多个设计模式；参考架构内容更广泛，可以包含不同架构模式，还可以包括独立开发的部分。

用一句话概括层级关系：参考架构 ⊃ 架构模式 ⊃ 设计模式（范围）， 而复用粒度正好相反：参考架构复用整套结构与业务组件，架构模式复用子系统划分策略， 设计模式只复用几个类的协作方式。

3.7 架构风格概览（第 5 章展开）

架构模式落到「系统整体长什么样」，就是我们常说的架构风格。这里只建立索引， 每种风格的详细原理、优缺点与选型在第 5 章。

架构风格一句话主要提升主要代价
分层架构按抽象层次纵向切分，上层依赖下层可修改性、可理解性请求逐层穿透，性能损耗
MVC模型、视图、控制器分离，视图可多套可修改性、可复用性控制器易膨胀，简单页面过度设计
管道-过滤器数据流经一串过滤器逐步加工复用性、可组合性不适合交互式、难以共享状态
事件驱动组件通过事件异步通知，彼此不直接调用可扩展性、松耦合流程难追踪、最终一致
微服务按业务能力拆成独立部署的小服务可扩展性、独立交付分布式复杂度、运维与一致性成本
仓库 / 黑板组件围绕共享数据存储协作数据一致性、可扩展中心存储成为瓶颈与单点

记忆要点：没有最好的风格，只有与质量目标最匹配的风格。 选型时先写清「本次最重要的两个质量属性是什么」，再看哪种风格的代价可以接受。

3.8 架构工作过程：分析任务 → 结构设计任务 → 原型

课件 2.4 先给了一个前提：系统按实时性分为硬实时系统、软实时系统、非实时系统。 类型不同，架构的取舍完全不同——硬实时系统宁可牺牲吞吐也要保证最坏响应时间有上界， 非实时系统则可以为了吞吐做批处理。

分析任务（2.4.1）

  1. 明确系统的目的和主要任务；
  2. 系统应用流程符合客户的组织结构和流程结构（系统要适配业务，而不是让业务迁就系统）；
  3. 组织系统接口，可联系外部系统、使用者；
  4. 解决系统接口与外部环境交流上的技术问题；
  5. 在逻辑层上确定系统的结构和流程。

结构设计任务（2.4.2）

先看整体：整体系统的硬件架构；分布式系统要决定不同功能分配到不同计算机，并回答四个问题：

  • 软件在每台单机上的层次结构（静态）；
  • 系统整体架构策略，即系统的工作流程（动态）；
  • 如何测试；
  • 得到什么（准备的范围）。

单机软件则从「系统整体方案」推导到「单机软件设计」，要处理三件事：

  • 计算机的外部接口；
  • 系统划分为组件、结构组织，即接口及组件间的静态关系；
  • 对流程进行建模和转化（工作内容），注意组件的功能和协作流程，即组件间的动态关系。

注意这里又出现一次「静态 / 动态」二分：组件与接口是静态的，流程与协作是动态的。 这条主线贯穿全章，也是 4+1 视图中「结构视图 vs 行为视图」的来源。

原型（2.4.4）

架构不能只靠纸面推演，风险点要用原型验证。三种原型的区别见「横向对比」一节的表格： 水平原型求「广」，垂直原型求「深」，可行性原型求「稳」。

3.9 架构师：协调者与技术决策者

课件 2.5 用一句话定义了架构师的处境： 协调委托人、管理人员和开发团队，引导程序员，维持团队纪律， 并要求分析能力、设计能力、沟通能力、方案评估能力。 落到具体能力上分三块：

  • 技术能力——懂结构、懂模式、懂质量属性的实现手段，能判断技术方案的可行性；
  • 沟通能力——把技术取舍翻译成业务语言给委托人听，把架构约束讲清楚给开发团队听；
  • 构造软件架构过程中的决定——也就是架构决策：在信息不完备、资源有限的情况下做出选择，并为选择负责。

这三块里最容易考的是「为什么架构师需要沟通能力」。答案不是「因为要开会」， 而是因为架构的约束要被执行：如果开发团队不理解某个约束的由来，就会在进度压力下绕过它， 架构最终名存实亡。架构师的影响力来自被理解的决策，而不是职位。

架构决策案例解析：在线考试系统的提交链路

下面用一个贴近本课程场景的例子，演示「架构决策」该怎么想、怎么写。 案例背景：某高校在线考试系统，期末周同一时段约 3000 人在线答题， 考试结束前 5 分钟出现集中提交；现有系统是单体 Web 应用 + 单库，团队 4 人。

问题定位：这不是功能问题（提交功能本身是好的），而是非功能性质量问题—— 峰值吞吐不足、响应时间超标，且一旦提交失败会直接影响成绩，可用性要求也随之升高。 这正是课件说的「架构主要负责系统的非功能性质量」。

备选方案峰值吞吐运维复杂度交付速度故障影响面
A. 保持单体，只做垂直扩容低（受单库写入限制）最低最快全站
B. 单体 + 消息队列，提交异步化高（削峰填谷）中（多一个中间件）较快全站（但有重试兜底）
C. 拆微服务，提交单独成服务高高（注册、网关、链路追踪）慢仅提交服务

决策：选 B。理由是：峰值只是短时尖峰（5 分钟），用队列削峰即可， 不需要为尖峰长期承担微服务的运维成本；团队 4 人，方案 C 的复杂度会吃掉全部交付能力； 方案 A 无法解决单库写入瓶颈。 后果：提交接口改为「先落库、再异步判分」，用户立即看到「已提交」， 判分结果稍后刷新；需要补上幂等（同一份答卷重复提交不重复计分）和 补偿（消息丢失时的对账任务）两处设计，并接受「判分结果有秒级延迟」这一质量让步。

决策记录模板（可直接背） 背景（什么质量属性不达标、量化指标）→ 决策（选了什么）→ 备选与放弃理由（为什么不是另外两个）→ 后果（得到什么质量、付出什么代价、 新增哪些设计约束）→ 验证方式（压测指标、观察周期）。 能写出这五段，架构决策题基本满分。

3.10 架构文档：写什么、为什么写

课件 2.4.3 的最后一条观察角度是「确定各种方案的依据文档」—— 架构方案必须留下依据，否则下一次变更时没人知道当初为什么这么定。 架构文档不是「把图贴在一起」，它要能让不同读者各取所需。

文档内容回答什么问题主要读者
视图（逻辑/开发/进程/物理）系统长什么样、怎么分工、怎么部署开发、运维、集成
关键场景与质量属性目标为什么是这个结构、达标标准是什么全部利益相关者
架构决策记录（ADR）当初为什么这样选、放弃过什么后续维护者、评审者
接口契约与约束组件之间怎么调用、什么不能做开发团队
部署与运行视图装在哪、怎么扩、怎么监控运维、系统管理员
术语表与参考架构引用名词是否一致、复用了哪些既有结构新成员、外部评审

架构文档最常见的三个失败模式，也常被拿来出判断题：

  • 只画图不写理由——图能说明「是什么」，说明不了「为什么」，变更时无从判断能不能改；
  • 文档与代码脱节——文档写完就冻结，半年后成为误导；应把关键约束写进代码结构与自动化检查；
  • 一份文档给所有人看——不分读者，结果业务方看不懂、开发方嫌不够细。应按视图与关注点分开组织。

横向对比

#

本章的选择题几乎都出在「两个概念长得像」的地方，下面五张表按考点排列。

4.1 架构 vs 设计（最容易被问「有什么区别」）

对比维度架构（Architecture）设计（Design）
抽象层次高层，规定「结构与约束」逐层细化，规定「类与算法」
关注范围全局：组件划分、交互、部署、技术选型局部：模块内部、类职责、接口签名
主要目标承载非功能性质量实现功能并保证局部质量
决策数量少而重，每个都影响全局多而轻，多数可局部修改
变更成本极高，越晚改越贵较低，重构可控
时间位置设计阶段的初步结果，需求之后、详细设计之前架构确定后持续进行，贯穿开发全程
典型产出架构视图、架构决策记录、部署方案类图、时序图、接口定义、设计模式应用
可逆性基本不可逆，或代价不可接受可通过重构逐步调整

一句话记忆：架构决定「能不能改」，设计决定「改起来顺不顺」。 判断一个决定属不属于架构决策，看它改起来贵不贵、波及面广不广。

4.2 4+1 视图对比

视图关注点静态/动态主要读者典型 UML 图支撑的质量属性
逻辑视图功能由哪些类/对象协作实现静态为主设计人员、需求方类图、对象图功能、可理解性、可复用性
开发视图代码如何组织为模块/包/构件静态程序员、构建负责人包图、构件图可修改性、可维护性、复用性
进程视图进程/线程、并发、同步、通信动态系统集成人员活动图、时序图、状态图性能、吞吐、可用性
物理视图软件到硬件节点的部署与网络动态（运行期）系统工程师、运维部署图可用性、可伸缩性、安全性
场景（+1）关键用例串联并验证四个视图—全部利益相关者用例图、时序图全部（用于验证）

注意：进程视图与物理视图常被混淆。进程视图问「跑起来有几个执行体」，物理视图问「这些执行体装在哪台机器上」。

4.3 参考架构 vs 架构模式 vs 设计模式

对比维度参考架构架构模式设计模式
粒度整套系统或大部分结构子系统级类 / 对象级
是否含业务含业务组件不含业务领域问题不含业务领域问题
是否模板含可复用部分，不完全是模板是软件结构的模板是类协作的模板
复用方式整套结构 + 组件复用，可省去全部系统设计复用子系统划分与合作策略复用若干类的协作方式
包含关系可包含多种架构模式与业务组件可包含多个设计模式被架构模式包含
主要风险不一定完全适用，可能不符合要求照搬导致子系统划分与业务不匹配模式滥用，为模式而模式
典型例子某行业电商中台参考架构分层、MVC、管道-过滤器、微服务单例、观察者、策略、工厂方法

4.4 质量属性：非功能性 vs 功能性（按课件口径）

类别包含属性回答的问题由谁主要决定
非功能性质量 可管理性、可更改性/可扩展能力、可操纵性、简易性、移植性、性能、规模的可伸缩性、稳定性、可测试性、组件的独立性、可用性、可理解性、可维护性、复用性 系统「好不好用、好不好改、扛不扛得住」 架构（首要）
功能性质量 保障性、安全性、并行性/并发性 系统在「功能正确」之上是否可靠、安全、可并发 架构 + 详细设计共同决定

再次提醒：把安全性归入功能性质量是本课件的口径，与部分教材不同；考试按课件写。

4.5 三种架构原型对比

原型类型覆盖方式主要目的典型产物不适用的情况
水平原型广而浅：横跨多个功能，每个只做表面验证整体结构、界面流程、用户可接受度可点击的界面骨架、导航流程需要验证性能或算法可行性时
垂直原型窄而深：选一个功能，从界面到存储完整实现验证某条链路的技术方案是否可行一条端到端可运行的切片需要看整体轮廓与工作量时
可行性原型只针对高风险技术点做最小验证回答「这条路走不走得通」，控制技术风险技术验证报告、丢弃型代码风险已明确、只是工作量估算时

4.6 黑盒观点 vs 白盒观点

对比维度黑盒观点（系统所处的环境）白盒观点（系统的逻辑模型）
看什么系统对外表现：接口、输入输出、与外部系统的交互系统内部：组件、层次、职责与协作
对应视图物理视图、场景（部分）逻辑视图、开发视图、进程视图
主要读者客户、委托方、外部系统对接方开发团队、架构评审者
回答的问题「系统边界在哪、和谁交互」「内部怎么分、怎么协作」
典型风险忽略外部依赖的约束（如对方接口限流）陷入细节，看不到整体

易错点

#

下面 7 条都来自真实的失分场景，不是正文的复述。

  • 把「架构」简单等同于「高层设计」或「技术选型」。 架构的核心职责是建模结构的作用与系统的行为，并承载非功能性质量； 选了什么框架只是其中一个决策，不等于架构本身。答题时要落到「组件划分 + 交互 + 部署 + 策略」四件事上。
  • 认为架构可以脱离功能单独设计。 课件明确说「系统的功能以结构为基础，不能与之分离」。脱离功能谈结构，得到的只是一张好看的图； 反过来，结构不支持的功能后期很难靠编码补出来。
  • 把「安全性」当非功能性质量写。 本课程课件把保障性、安全性、并行性/并发性列在功能性质量下。 按课件口径作答；若需要展开，再补一句「通行教材亦有不同分类口径」，避免被判错。
  • 混淆架构模式与设计模式的粒度。 架构模式管子系统的分解与合作，设计模式管类/对象的协作。 说「观察者模式是一种架构模式」是错的；说「分层是一种设计模式」也不准确——它属于架构模式/架构风格。
  • 把参考架构当「标准答案」直接套用。 课件点明其缺点：不一定完全适用，可能不完全符合要求。 参考架构省掉的是「全部系统设计」，不是「判断适配性」——套用前必须逐条核对质量属性与业务约束。
  • 把 4+1 的「+1」当成第五个并列视图。 场景的作用是串联与验证四个视图：它从需求中来，用来检验视图是否自洽，并驱动架构取舍。 说「五个视图地位完全并列」是错的。
  • 把水平原型和垂直原型记反。 记忆法：水平＝地平线，看得远但看得浅（多功能、浅实现）； 垂直＝打井，范围窄但到底（单功能、端到端）。 可行性原型则是专攻技术风险的第三种，只验证「走不走得通」。

五句话记住本章

  1. 架构是需求与程序之间的蓝图，规定结构与实施流程，主要承担非功能性质量。
