架构模式：从分层、MVC 到微服务的选型地图

架构模式是「系统级」的复用经验：它规定了构件怎么分、连接件怎么连、约束是什么。 本章按系统软件、分布式软件、交互软件三族，把课件里的分层、管道-过滤器、插件、Broker、SOA、MVC 连同黑板、C/S、P2P、PAC、微服务、事件驱动等模式一次讲清，并落到「电商系统该选什么」的选型题上。

学习目标

读完后应能做到以下几点，每一条都可以自我检验。

  1. 能给出架构模式的定义，并说清它与「架构风格」「设计模式」「框架」三者的层次差别。
  2. 能画出分层、管道-过滤器、插件、Broker、SOA、MVC 六种模式的结构图，指出各自的构件、连接件与约束。
  3. 能对每种模式列出至少 3 条优点与 3 条代价，并把它们映射到性能、可修改性、可伸缩性、可用性等质量属性上。
  4. 能根据业务场景（如电商系统）在多种模式之间做选型，并用「变化点 + 质量属性 + 成本」三段式说明理由。
  5. 能识别常见误用：把 Broker 当成 Mediator、把 SOA 等同于微服务、认为分层越细越好、把插件当成普通功能扩展。

三族架构模式：本章的目录骨架

课件把典型架构模式按「面向什么系统」分成三族。先记住族，再记族里的模式，考试时不容易漏。

系统软件族

关注「一个进程内如何组织代码与数据流」。

分层 · 管道-过滤器 · 黑板

典型：操作系统、编译器、协议栈、批处理与数据分析。

关注「跨进程、跨机器如何定位、通信与协作」。

典型：CORBA、DNS、企业应用集成、互联网后端。

交互软件族

关注「用户界面与业务数据如何分离、如何响应变化」。

典型：桌面 GUI、Web 前端、移动端、实时通知。

核心概念

#

先统一术语，再逐张过模式卡；模式卡统一用「问题—方案—角色—优点—代价—场景—相关」七行，便于横向比较。

架构模式 Architectural Pattern

描述软件系统基本的组织结构：一组预定义的子系统、它们的职责、以及组织它们之间的规则。 它回答的是「系统由哪些大块组成、块之间怎么连、连的时候受什么约束」。

系统级 可复用经验

构件与连接件 Component & Connector

描述架构模式的两个基本词汇。构件是计算或存储的单元（层、过滤器、服务、插件、模型）； 连接件是构件之间的交互机制（过程调用、管道、事件总线、RPC、协议）。同一个构件换一种连接件，架构就变了。

描述语言 易考

架构风格 / 架构模式 / 设计模式 Style / Pattern

三者是不同粒度：架构风格是最抽象的结构族（如「分层」「数据流」）； 架构模式是风格的具体化（如「严格分层」「管道-过滤器」）；设计模式是类/对象级的协作方案（如观察者、策略）。 层级越高，影响面越大，改动成本也越高。

易混淆 层次

关注点分离 Separation of Concerns

把系统中不同的关注点（界面、业务、数据、通信、扩展）放进不同的构件，使每一部分只对一个变化原因负责。 本章几乎所有模式——分层、MVC、SOA、插件——本质都是它的不同实现方式。

第一性原理

质量属性权衡 Quality Trade-off

模式不是「只有好处」：分层提升可修改性却牺牲性能，微服务提升可伸缩性却带来分布式复杂度， 事件驱动提升解耦却牺牲可调试性。选型 = 在冲突的质量属性之间做取舍，而不是找「最好的模式」。

选型依据

架构视图 Architectural View

从某个视角对系统做的简化描述。课件复习了逻辑（功能）、开发（程序包）、运行（进程线程）、物理（部署）、 数据（持久化）五类视图。同一种模式在不同视图里呈现不同：分层在逻辑视图是层，在开发视图是包依赖。

课件按系统类型分族：系统软件（分层、管道-过滤器、黑板）、分布式软件（Broker、C/S、P2P）、 交互软件（MVC、PAC）。分类不是绝对的：SOA 与微服务属于分布式族的现代形态，事件驱动横跨交互与分布式。

记忆框架

选型三问 Three Questions

面对场景先问三句：① 变化点在哪（界面变、算法变、部署规模变？）； ② 哪个质量属性是硬约束（性能、可用性、可扩展？）； ③ 团队与运维能不能承担这个代价（分布式、插件治理、多版本）。 三问的答案基本能锁定候选模式。

分层架构

Layered Architecture 架构型
上下文/问题
系统功能庞杂、抽象层次混杂；希望把复杂系统切成可理解、可替换、可并行开发的块，并支持标准化与复用。
解决方案
按抽象程度把系统划成层次结构，每层向上提供服务、向下使用服务；层间只经接口与协议调用，下层不知道上层。
参与角色
层（Layer）、层接口、层内构件、协议/过程调用连接件、抽象准则（分层规则）。
优点
分解复杂、易于理解；层稳定可标准化；变更影响局部；接口稳定支持并行开发与替换；支持复用。
代价
层次划分依赖经验、没有唯一解；跨层数据逐层传递使性能下降；多层调用难调试；性能压力下可能被迫合并层，破坏逻辑独立性。
适用场景
协议栈（OSI/TCP-IP）、操作系统（Windows NT）、企业应用（表现层/业务层/持久化层）、各类框架。
相关模式
微内核（内核 + 可插拔层）、管道-过滤器（顺序处理链）、MVC（交互系统里的三层变体）。

管道-过滤器

Pipes and Filters 架构型
上下文/问题
面向数据流的系统：加工过程不应是一个整体，需要易于扩展、尽量并行、单个步骤可复用。
解决方案
按处理阶段把任务拆成单一职责的过滤器，过滤器只读输入、变换、写输出；过滤器之间用管道连接并缓存数据。
参与角色
过滤器（输入端口/输出端口）、管道（连接件，被动传输与缓存）、数据源与数据汇、管道数据类型定义。
优点
简单（整体行为 = 各过滤器行为的组合）；可重用（过滤器不知道上下游）；易维护扩展（增删换过滤器）；天然支持并发与流水线。
代价
批处理模型不适合交互式应用；每个过滤器都要做完整的输入→输出转换，批量转换开销大；两条相关数据流之间通信困难；有名管道增加解析/反馈成本。
适用场景
UNIX shell 管道、编译器（词法→语法→语义→中间代码→优化→目标代码）、图像/信号处理、ETL 与日志处理。
相关模式
分层（同样是顺序抽象，但连接件是调用而非数据流）、黑板（共享数据 vs 流式传递）、事件驱动（推送 vs 拉取）。

插件 / 微内核

Plugin / Microkernel 架构型
上下文/问题
软件要长期稳定，又需要第三方或后续团队扩展功能；现有代码不允许修改，同时要灵活，符合开闭原则。
解决方案
核心（宿主）只定义扩展点（接口/契约），插件实现接口并由插件管理者在运行时加载、注册、实例化；没有插件时系统仍可正常运行。
参与角色
应用（宿主 host）、插件管理者、插件接口（扩展点）、具体插件（plug-in）、契约（contract）。
优点
关注点分离（每个插件职责单一）；便于第三方扩展；核心保持精简；支持多版本并存；插件可独立测试。
代价
初始加载与运行期管理开销随插件增多而上升；扩展必须通过接口，插件与接口强依赖；接口一旦发布难改；需处理隔离、安全与版本兼容。
适用场景
IDE（Eclipse）、浏览器扩展、Office 插件、构建工具、微内核操作系统、规则可配置的业务系统。
相关模式
装饰/策略（对象级替换，没有公开的运行时扩展接口）、分层（微内核常与分层组合）、SOA（服务注册与发现）。

经纪人模式

Broker 架构型
上下文/问题
大型系统必须能「长大」：单机很快到极限，组件要分布到多台机器，架构要适应性能变化；组件间需要解耦又要通信，且平台/语言可能异构。
解决方案
客户—客户端代理—Broker—服务端代理—服务器。服务在 Broker 登记；客户按逻辑名称请求服务，Broker 定位并转发；代理负责序列化与反序列化。
参与角色
Client、Client-side Proxy、Broker、Server-side Proxy、Server。
优点
通信与功能分离；接口不变即可更换服务实现；客户不知道服务器物理地址（位置透明）；平台与语言独立；可把大型系统分布到多台机器。
代价
Broker 是中心查询点，容错性差、可能成为瓶颈；间接调用增加通信开销；代理依赖 Broker，更换 Broker 需重新适配；调试、安全与治理复杂。
适用场景
CORBA、Internet/DNS、RPC 与消息中间件、服务注册与发现。
相关模式
Mediator（同进程、1:n 转发）、SOA（Broker 隐藏物理地址，SOA 公开服务契约）、微服务（注册中心是 Broker 思想的延续）。

面向服务的架构

Service-Oriented Architecture 架构型
上下文/问题
业务流程一旦调整就引起系统大改，系统难维护、成本剧增；遗留系统要集成，跨组织要对接。
解决方案
以服务为中心：把业务流程直接构建为服务组合，每个应用场景对应一个服务；服务通过契约暴露、可注册发现、可编排；层次为业务流程→应用服务→基本服务。
参与角色
服务提供者、服务消费者、服务注册中心（服务目录）、服务契约/接口、服务总线与编排。
优点
按业务流程组织，服务与接口一目了然；分解应用服务与基本服务，降低复杂性；可复用；接口不变时实现可动态更换；遗留系统可封装接入。
代价
服务划分过细会让结构复杂；多层服务间通信增加额外开销；对网络速率要求高；业务流程必须明确定义并做好文档与治理。
适用场景
企业应用集成（EAI）、遗留系统封装、B2B 流程对接、银行/电信等复杂 C/S 系统。
相关模式
Broker（SOA 的通信基础设施）、微服务（SOA 的轻量化、去中心化演进）、分层（服务层次划分）。

模型-视图-控制器

Model-View-Controller 架构型
上下文/问题
用户界面经常变，但不应牵动其余程序；同一份信息要以多种形式展示；数据一变，所有展示要同步更新。
解决方案
把交互系统拆成模型（数据与加工）、视图（表示逻辑）、控制器（用户输入）三部分；视图订阅模型，控制器解释输入并调用模型，模型变化后通知视图。
参与角色
Model（核心功能，封装数据与加工）、View（展示模型数据，含控制元素）、Controller（接收并解释输入、控制模型与视图状态）。
优点
模型与界面分别设计；改界面不动模型；模型可单独测试；同一应用可配多套界面。
代价
频繁更新时通知开销影响性能；小应用拆成多个类反而增加实现开销；控制器容易膨胀成「上帝类」。
适用场景
交互式软件：桌面 GUI、Web 应用、移动端界面层。
相关模式
观察者（模型通知视图）、组合（视图树）、策略（视图/控制器可替换）、MVP/MVVM（MVC 的演进）。

黑板模式

Blackboard 架构型
上下文/问题
问题没有确定的求解算法，需要多个知识源协作、逐步逼近答案；解空间大、过程不确定（识别、规划、约束求解）。
解决方案
一块共享数据结构（黑板）+ 若干独立知识源（KS）+ 控制器；控制器根据黑板当前状态决定激活哪个知识源，知识源读黑板、写黑板。
参与角色
黑板（共享数据与状态）、知识源（独立求解器）、控制器（调度策略）、触发条件。
优点
适合非确定性与启发式问题；知识源可独立开发、替换、扩展；支持增量求解；数据与算法解耦。
代价
控制策略难设计；黑板访问需要同步与一致性控制；没有显式调用链，性能与可调试性差；知识源之间存在隐式依赖。
适用场景
语音/图像识别、信号处理、编译器优化、专家系统、约束求解。
相关模式
仓储（共享数据但无调度）、管道-过滤器（流式传递 vs 共享黑板）、事件驱动（黑板变化触发知识源）。

客户/服务器

Client/Server 架构型
上下文/问题
多个客户端要共享集中的数据与服务，需要统一的安全与数据管理，客户端又希望尽量轻。
解决方案
服务器集中提供数据与服务，客户端发起请求、服务器响应；可二层（客户直连数据库）或三层（客户—应用服务器—数据库）。
参与角色
客户端、服务器、请求-响应协议、中间件（三层架构中的应用服务器）。
优点
数据与安全集中管理；客户端轻；成熟、易理解；服务可被多客户端复用。
代价
服务器是瓶颈与单点；客户端与服务器经协议耦合，版本升级要两端配合；规模扩展主要靠升级服务器。
适用场景
数据库服务器、Web 应用、文件服务器、企业内网信息系统。
相关模式
Broker（在 C/S 上加位置透明与代理）、P2P（去中心化）、三层架构（C/S 的纵向分层）。

点对点

Peer-to-Peer 架构型
上下文/问题
要避免中心服务器的单点与瓶颈，让节点既消费也贡献资源；系统需大规模可扩展、低成本。
解决方案
节点对等，每个节点既是客户又是服务器；在物理网络之上构建覆盖网络（overlay）负责寻址与路由；可用纯 P2P 或带超级节点的混合模式。
参与角色
对等节点、覆盖网络、索引/路由机制（如 DHT）、超级节点（混合模式）。
优点
可扩展、无单点瓶颈；资源利用率高；天然容错；部署成本低。
代价
一致性与信任难保证；节点异构、随时上下线；查找与路由开销大；管理与审计困难。
适用场景
BitTorrent、区块链、即时通信、边缘资源共享。
相关模式
C/S（集中 vs 对等）、Broker（中心索引 vs 分布式哈希）、微服务（服务网格是「去中心化通信」的另一种形态）。

显示-抽象-控制

Presentation-Abstraction-Control 架构型
上下文/问题
交互系统既有层次结构（窗口套窗口），又有多个并发的交互任务；MVC 对这种层次化、多代理的界面支持不足。
解决方案
把系统组织成若干「代理」的层次结构，每个代理内部再分表示（显示）、抽象（数据与功能）、控制（协调）三部分；父子代理通过控制层协作。
参与角色
代理（agent）、表示、抽象、控制。
优点
支持层次化交互与多任务并发；关注点分离比 MVC 更细；适合复杂 GUI。
代价
代理数量多、结构复杂；控制流分散难理解；实现与调试成本高。
适用场景
复杂桌面应用、CAD、多媒体交互系统。
相关模式
MVC（PAC 是它的层次化扩展）、分层、MVP。

微服务架构

Microservices 架构型
上下文/问题
单体应用难以独立部署与按需扩展；多个团队并行开发互相阻塞；不同模块技术诉求不同；需要快速迭代与故障隔离。
解决方案
按业务能力拆成小型自治服务，独立部署、独立数据存储、轻量通信（HTTP/RPC/消息），去中心化治理 + 自动化部署与监控。
参与角色
微服务、API 网关、注册中心、配置中心、服务网格、CI/CD 流水线。
优点
独立部署与伸缩；团队自治；技术异构；故障隔离；服务粒度细、迭代快。
代价
分布式复杂性（网络、事务、一致性）；运维监控成本高；数据一致性难；服务边界难划；端到端测试难。
适用场景
互联网大规模业务、多团队协作、频繁发布、模块伸缩需求差异大的系统。
相关模式
SOA（继承服务化、去掉中心总线）、Broker（注册发现）、事件驱动（最终一致性）。

事件驱动 / 隐式调用

Event-Driven / Implicit Invocation 架构型
上下文/问题
构件需要在不知道对方身份的情况下响应变化；希望松耦合、易扩展，并支持异步与并发。
解决方案
构件发布事件而不指定接收者；其他构件注册兴趣，事件发生时被「隐式调用」；由事件总线/分发器负责匹配与投递。
参与角色
事件生产者、事件、事件总线/分发器、事件消费者、订阅注册表。
优点
强解耦；易扩展（加订阅者不改发布者）；支持异步与并发；适合系统演化与集成。
代价
控制流隐式、调用链难追踪；事件顺序、幂等、丢失需专门处理；系统整体行为难预测；错误处理复杂。
适用场景
GUI 事件、消息中间件、微服务集成、EDA、物联网。
相关模式
观察者（设计模式版）、发布-订阅（带代理的架构版）、MVC（模型通知视图）。

发布-订阅

Publish-Subscribe 架构型
上下文/问题
多对多通信，发布者不应知道订阅者是谁；消息需要按主题过滤、可异步、可持久化。
解决方案
发布者向主题/频道发消息，订阅者按主题订阅，由消息代理路由；代理负责缓冲、持久化、重试与分发。
参与角色
Publisher、Subscriber、Topic/Channel、Message Broker。
优点
空间解耦（互不相识）、时间解耦（异步）、同步解耦（不必同时在线）；可扩展、可广播、可过滤。
代价
代理的运维与可用性成本；消息顺序、重复、一致性难保证；调试与追踪困难；订阅关系管理复杂。
适用场景
Kafka/RabbitMQ 类消息系统、IoT 数据采集、通知与日志、微服务事件集成。
相关模式
观察者（进程内、直接持有引用）、事件驱动（更宽泛的架构风格）、Broker（代理即 Broker 的演化）。

模型-视图-呈现器

Model-View-Presenter 架构型
上下文/问题
MVC 中视图仍依赖模型（观察者），UI 逻辑难以单元测试；Web 场景下视图无法直接观察模型变化。
解决方案
引入 Presenter：它持有 View 接口与 Model，承担全部展示逻辑；View 变成被动视图，只渲染并提供事件回调。
参与角色
Model、View（接口，被动）、Presenter。
优点
View 完全被动、易于 mock 与测试；Presenter 与具体视图解耦；适合 Web 与移动端。
代价
Presenter 容易膨胀；接口数量多；视图更新要手动同步，样板代码多。
适用场景
Android、GWT、WinForms 等界面技术受限、需要高可测试性的场景。
相关模式
MVC（前身）、MVVM（进一步用数据绑定消除样板）。

模型-视图-视图模型

Model-View-ViewModel 架构型
上下文/问题
希望消除 MVP 里大量手写的视图同步代码，让 UI 与状态自动保持一致，同时保持 UI 逻辑可测试。
解决方案
ViewModel 暴露数据与命令，View 通过数据绑定声明式地与之同步；ViewModel 不引用 View，便于测试。
参与角色
Model、View、ViewModel、绑定引擎（框架提供）。
优点
双向绑定减少样板代码；ViewModel 可单测；前后端分离与响应式 UI 友好。
代价
绑定出错难调试；大型项目绑定开销与内存占用；过度绑定会降低可读性与性能。
适用场景
WPF、Vue/React（响应式思想）、Android DataBinding。
相关模式
MVP、MVC、观察者（绑定即观察者的一种实现）。

解释器 / 虚拟机

Interpreter / Virtual Machine 架构型
上下文/问题
需要在运行时解释执行自定义语言、规则或脚本；行为要可配置、可移植，不能每次改动都重新编译宿主程序。
解决方案
定义语言语法并实现解释引擎：把程序表示成抽象语法树或字节码，由解释器/虚拟机执行；OO 中的解释器模式是其类级映射。
参与角色
解释器/执行引擎、AST 或字节码、上下文（环境）、指令/规则对象。
优点
行为可在运行时改变；可移植；规则外置便于业务人员维护；适合 DSL。
代价
解释执行性能低于编译执行；语言与引擎的设计维护成本高；调试、安全沙箱复杂。
适用场景
规则引擎、SQL、正则表达式、脚本引擎、JVM 类虚拟机。
相关模式
插件（扩展点）、分层（虚拟机栈式分层）、管道-过滤器（编译阶段流水线）。

仓储模式

Repository 架构型
上下文/问题
领域逻辑直接拼 SQL 访问数据库，导致业务依赖具体存储、难以测试、查询逻辑散落各处。
解决方案
在领域层与数据映射层之间提供「类似集合」的抽象，封装查询与存储，隔离数据库技术细节。
参与角色
Repository 接口、Repository 实现（DAO/ORM）、领域对象、数据映射器。
优点
领域层不依赖数据库；存储可替换；可用内存实现做单元测试；查询逻辑集中。
代价
抽象容易泄漏（复杂查询与性能优化难）；过度封装；事务边界管理复杂。
适用场景
DDD 领域模型、企业应用、分层架构中的持久化层。
相关模式
分层（仓储位于持久化层）、DAO、CQRS（读写模型分离）。

命令查询职责分离

CQRS 架构型
上下文/问题
读写负载差异大、模型诉求不同：写要强一致与校验，读要高并发与复杂查询，同一模型两头受气。
解决方案
把命令（写）与查询（读）分离成不同的模型与服务，可独立扩展与优化；常用事件同步读模型，配合事件溯源。
参与角色
Command、Command Handler、写模型、Query、读模型、同步机制。
优点
读写独立优化与扩展；模型各自简化；适合高并发与复杂报表查询。
代价
最终一致性；同步机制与重复代码；整体复杂度上升；简单 CRUD 场景得不偿失。
适用场景
高并发交易系统、报表与看板、事件溯源系统。
相关模式
事件驱动、微服务、仓储。

结构与实现

#

这一节按课件的六个小节顺序展开：先给结构示意图，再讲参与者与动态行为，最后落到「怎么实现」和「代价从哪来」。 读图时始终盯住两件事：构件是什么、连接件是什么。

一、分层架构：把「抽象层次」变成可依赖的边界

分层模式把系统组织成层次结构，各层之间是客户/服务器关系：上层是客户，下层是服务器。 每一层内部高度内聚、抽象程度一致，并通过接口隐藏实现。连接件是协议与过程调用。 最关键的约束只有两条：上层可以使用下层的服务，下层不能使用上层；每层只对相邻层可见。

结构示意图 1 · 分层架构（严格分层与层桥接）

应用层 面向特定应用问题只调用功能层
功能层 通用业务功能，可被多个应用复用只调用核心层
核心层 最一般、最稳定的基础能力只调用系统层
系统层 操作系统 / 硬件抽象最底层

严格分层：第 n 层只依赖第 n−1 层，只为上一层提供服务，通过接口使用服务——实现简单、替换容易，但请求要逐层穿越。 层桥接（松弛分层）：允许某层直接调用下方所有层，减少穿越开销，代价是层与层之间出现「短路」，抽象边界被削弱。 课件举的 Windows NT 就是非严格分层：内核与 I/O 管理需要直接访问硬件。

参与者与职责

  • 层（Layer）：一组抽象级别一致的构件，对外只暴露接口。
  • 层接口：定义该层向上提供的服务，是替换实现时唯一需要保持稳定的东西。
  • 协议 / 过程调用：连接件，规定层间交互的格式与顺序。
  • 分层规则：约束调用方向与可见性，是「模式」区别于「随便分几个包」的关键。

实现要点（课件「分层系统的实现」五步）

  1. 为分层定义抽象准则，确定抽象层次；
  2. 给每一层命名，明确它的任务与对外提供的服务；
  3. 为每层定义接口，独立实现各层；
  4. 确定相邻层的通信方式，尽量降低相邻层耦合；
  5. 设计错误处理策略（异常在哪层转换、在哪层终止）。

答题技巧 简答「分层的优点」按「理解—变更—开发—复用」四条写：分解复杂易于理解；层稳定可标准化、变更影响局部； 接口确定后可并行开发与集成测试；标准接口允许不同实现，支持复用。 答「缺点」必须点出性能与分层本身没有唯一正确答案这两条，否则容易被判不完整。

二、管道-过滤器：把数据处理变成一条流水线

面向数据流的系统里，如果整个加工过程写成一坨，就无法扩展、无法并行、无法复用单个步骤。 管道-过滤器把每个处理阶段做成一个过滤器（有输入端口和输出端口），过滤器之间用管道连接并缓存数据。 过滤器彼此独立：不共享状态、不知道上下游是谁，因此最终结果与各过滤器的执行顺序无关（只取决于连接拓扑）。

结构示意图 2 · 管道-过滤器（线性管线与分叉拓扑）

数据源source → 管道 → 过滤器 A词法分析 → 管道 → 过滤器 B语法分析 → 管道 → 过滤器 C语义分析 → 管道 → 数据汇sink

拓扑可以分叉与汇合：同一份输入可以并行送给多个过滤器，多个过滤器的输出也可以汇入同一个下游。 三种常见变体：管线（Pipelines）把拓扑限制为线性序列；有界管线（Bounded Pipes）限制管道中能容纳的数据量； 类型定义管道（Type Pipes）明确规定相邻过滤器之间的数据类型。

过滤器做什么、管道做什么

元素职责课件给出的三类加工
过滤器（构件）读取输入、加工转换、写出输出；独立实体，无共享状态提取部分数据 / 补充部分数据（计算、附加）/ 修改部分数据
管道（连接件）传输并缓存数据，是被动元素，体现数据流的实现—

实现步骤（课件「管道和过滤器的实现」）

  1. 把系统任务分成几个独立的处理阶段；
  2. 定义每个管道传输的数据格式；
  3. 决定管道的连接方式（线性、分叉、汇合）；
  4. 设计和实现过滤器；
  5. 设计出错处理；
  6. 建立处理流水线。

注意 管道-过滤器的本质是批处理：每个过滤器都要完成「整批输入 → 整批输出」的转换， 所以它天然不适合交互式应用，也不擅长维持两条相互独立又有关联的数据流之间的通信。 课件还特别提到「有名管道」：通过命名管道传数据会增加解析或反馈工作，反而降低效率。

三、插件架构：把「变化」做成可安装的部件

插件模式解决的是「软件要稳定，又必须让第三方持续扩展」的矛盾。做法是：扩展点用接口表示， 插件实现这些接口，由插件管理者在运行时加载、注册与实例化；即使一个插件都不装，宿主也能正常运行。 注意课件那句提醒——插件不是简单的功能扩展：它要求存在固定的、公开的、可在运行时扩展的接口。

结构示意图 3 · 插件 / 微内核（核心 + 扩展点 + 插件）

插件 A：图片导出
插件 B：语法检查
插件 C：第三方主题
插件管理者
Plugin Manager 按插件接口识别插件、按类型查找、负责实例化
扩展点：IExtension
扩展点：IViewer
扩展点：ICommand

左侧是具体插件，中间是管理者，右侧是宿主定义的扩展点（接口）。三者合起来就是实现层面的 宿主程序（host）+ 插件（plug-in）+ 契约（contract）。 插件与具体应用解耦的关键在于：应用只认识接口，实例化与装配交给管理者。

参与者与职责

  • 应用（宿主）：功能可扩展的组件，定义扩展点并在合适时机调用插件。
  • 插件管理者：根据插件接口识别所有插件、找到指定类型插件、负责实例化与生命周期。
  • 插件接口（扩展点）：具体插件的抽象，也是宿主与插件之间唯一的契约。
  • 具体插件：接口的实现，不能独立运行，不依赖应用内部流程。

课件的「动态行为」强调两点：特定应用与插件实例解耦、插件管理者负责插件实例化。 所以插件模式的实现难点不在接口定义，而在发现机制（扫描目录、读配置、ServiceLoader、OSGi）与 隔离机制（类加载器、权限、版本）。

四、Broker：让分布式调用对客户「位置透明」

大型系统必须能「成长」：单机很快到极限，组件要分布到多台计算机，架构要能适应性能变化，而且不能推倒重来。 但组件之间又不可能完全不依赖。Broker 的答案是：把「找谁」这件事从客户代码里拿走，交给中间人。 服务器把服务登记到 Broker，客户按逻辑名称请求服务，Broker 定位并转发；两端各有一个代理负责序列化与反序列化。

结构示意图 4 · Broker（客户—客户端代理—经纪人—服务端代理—服务器）

Client客户 → Client-side Proxy序列化 → 请求 → Broker定位 / 转发 / 登记 → 转发 → Server-side Proxy反序列化 → 调用 → Server服务实现

Broker 必须了解服务器，服务器提供的服务必须向它登记；客户则完全不需要知道服务器的物理位置。 角色不是静态的：同一个组件既可能是服务器，也可能是客户（例如服务 A 调用服务 B 时）。 登记 → 查询 → 转发 → 调用 → 回传，一次远程调用要走完这五步。

参与者与职责

  • Client：实现需求，调用服务。
  • Client-side Proxy：对客户而言代表服务器；接收请求、序列化、传给 Broker。
  • Broker：负责客户与服务器之间的通信；管理服务提供者与服务之间的对应关系。
  • Server-side Proxy：对服务器而言代表客户；把请求反序列化，生成服务方法调用信息。
  • Server：提供服务的类或组件。

动态行为：一次调用要经过几步

  1. 服务器启动，把「逻辑服务名 → 实际地址」登记到 Broker；
  2. 客户调用本地代理，就像调用本地方法；
  3. 客户端代理把调用序列化成与平台无关的消息，发给 Broker；
  4. Broker 按逻辑名查表，把消息转发给对应的服务端代理；
  5. 服务端代理反序列化并调用真正的服务器方法；
  6. 返回值沿原路反向传回（同样经过序列化与反序列化）。

代价的根源 Broker 的四大缺点全部来自「多了一个中心 + 多了一跳」： 中心查询点的容错性差、可能成为瓶颈；间接调用增加通信开销； 代理依赖 Broker，更换 Broker 必须重新适配。所以 Broker 适合「位置透明比极致延迟更重要」的场景。

五、SOA：以业务流程为线索组织服务

业务流程一改，系统就得大改——这是传统单体企业应用的顽疾。SOA 的思路是： 把一个业务流程直接构建为一个计算机系统，把应用场景分配给服务组件， 服务的边界与业务流程对齐，于是流程调整时只需要重组服务。 服务的层次是：业务流程 → 应用服务（应用场景）→ 基本服务。

结构示意图 5 · SOA 的服务层次与角色协作

业务流程层 下单→支付→发货→售后编排
应用服务层 订单服务 / 支付服务 / 物流服务一个应用场景一个服务
基本服务层 用户、库存、账户、通知可复用

横向看角色协作：服务提供者发布服务契约到服务注册中心（服务目录）， 服务消费者查目录、绑定契约、发起调用。契约（接口）是唯一稳定的东西，实现可以动态更换。

六、MVC：交互系统的三段式分工

界面经常变，但业务不该跟着变；同一份数据要用不同形式展示；数据一改，所有展示都要同步。 MVC 把交互系统拆成三块：模型管数据与加工，视图管表示，控制器管输入解释。 课件把它称作「交互系统的重要事项」，本质是关注点分离在界面层的落地。

结构示意图 6 · MVC 的组件交互与依赖方向

用户user → 事件 → Controller解释输入、调用模型 → 调用 → Model业务数据与加工
Model状态变化 → 通知 / 视图回拉 → View展示模型数据 ← 选择 / 更新 ← Controller控制视图状态

依赖方向的关键：View 依赖 Model（读数据、订阅变化），Controller 依赖 Model 与 View， 而 Model 不依赖 View 与 Controller。这正是「改界面不用改业务」的结构性保证。 模型通知视图有两种风格：被动模式由控制器在数据改动后通知视图；主动模式由模型自己广播（推或拉）。

三个角色的职责边界

角色职责不该做什么
模型 Model执行业务流程；存储所有业务数据；封装数据加工；状态变化时通知视图不处理输入输出；不考虑视图与控制器的实现
视图 View展示模型中的数据；包含交互控制元素不解释事件，一律转交控制器
控制器 Controller接收用户输入；把事件与数据翻译成模型方法调用；控制模型状态与视图状态不写业务规则；不直接操作数据库

MVC 内部其实藏着三个设计模式

  • 观察者：模型状态变化 → 通知所有视图刷新（MVC 的「主动模式」就是观察者）。
  • 组合：视图本身是一棵树（窗口、面板、控件），对整棵树的刷新可以统一处理。
  • 策略：视图与控制器的行为可以替换（同一模型配不同视图/控制器，如只读视图、编辑视图）。

MVC 的两种通知风格 被动模式：模型完全被动，控制器在修改数据后主动通知视图刷新，实现简单、时序可控，但控制器要知道所有视图。 主动模式：模型维护观察者列表，状态一变就广播，视图自动更新，扩展新视图无需改控制器，代价是通知链隐式、可能影响性能。

选型实战：电商系统该选什么架构？

题目常这么出：「某电商系统包含商品、订单、支付、库存、物流、客服、后台报表， 要求支撑大促峰值、支持多团队并行开发、允许第三方商家接入、后台运营界面频繁调整。请给出架构方案并说明理由。」 下面按变化点 → 质量属性 → 模式 → 代价与缓解四步拆解。

第一步：识别变化点（决定哪些地方需要模式）

变化点变化频率影响范围对应模式
运营后台界面、活动页样式极高只影响展示层MVC / MVVM
支付渠道、物流承运商、促销规则高局部可插拔插件 / 策略 / 适配器
大促流量（读多写少、峰值数十倍）周期性容量与部署微服务 + 缓存 + CQRS
第三方商家 / 外部系统接入中接口契约SOA / 开放平台（服务契约）
业务域拆分与团队边界低但影响大系统骨架微服务（按业务能力）

第二步：把质量属性排优先级

  • 硬约束：大促期间的高并发与可伸缩性、支付链路的可用性、下单接口的响应时间。
  • 重要但可让步：多团队并行开发效率（可用服务边界解决）、第三方接入的开放性。
  • 可接受代价：报表允许分钟级延迟（因此 CQRS 的最终一致可接受）；非核心链路允许降级。

第三步：组合方案（没有单一模式能覆盖全部）

电商系统架构方案（分层 + 微服务 + 事件驱动 + 插件 + MVC）

接入层 CDN / 网关 / BFFMVC 的 Controller 在此解释请求
业务服务层 商品 / 订单 / 支付 / 库存 / 物流微服务，按业务能力拆分、独立数据库
集成层 消息队列（订单事件、库存扣减、通知）事件驱动 / 发布-订阅，最终一致
扩展层 支付渠道插件 / 促销规则引擎插件 + 解释器
数据层 主库 + 读库 + 缓存 + 报表库仓储 + CQRS

每个微服务内部仍是分层（接口层—业务层—持久化层，仓储隔离数据库）； 服务之间用事件驱动解耦，避免下单时同步等待所有下游； 面向商家与外部系统的能力以服务契约暴露（SOA 思想）， 运营后台用 MVC/MVVM，支付渠道与促销规则用插件 + 解释器做运行时扩展。

第四步：说明代价与缓解（这是拉开分差的部分）

选用的模式换来的好处引入的代价缓解手段
微服务独立伸缩、故障隔离、团队自治分布式事务与一致性、运维复杂事件驱动 + 最终一致、Saga、服务网格与统一监控
事件驱动削峰填谷、服务解耦消息重复/丢失、调用链难追踪幂等消费、消息持久化、全链路追踪
分层服务内结构清晰、可测试跨层调用开销严格分层 + 只对关键路径做层桥接
插件 / 解释器支付渠道、规则热扩展加载开销、接口版本管理契约版本化、插件沙箱与灰度
CQRS读扩展、报表不拖累交易最终一致、同步代码只对报表与商品详情等读多场景使用

选型题的答题模板 ① 先声明「没有银弹，按变化点与质量属性选型」；② 列出 2–3 个变化点并各配一个模式； ③ 画出组合结构（分层 + 服务 + 事件 + 插件）；④ 明确说出代价与缓解； ⑤ 最后给一句「演进路径」：先单体分层，规模上来后再按业务边界拆服务。 只写「用微服务因为先进」一定扣分。

易错点

#

这些是学生答卷里真实出现过的错误，也是判断题最爱设的陷阱。

  • 把 Broker 与 Mediator 混为一谈。 Mediator 中的同事对象处在同一个系统内，通过中介者通信，是 1:n 转发； Broker 负责在分布式系统中定位接收组件，是 1:1 的请求转发，还要处理序列化、位置透明与跨平台。 一句话记：Mediator 解决「对象太多互相引用」，Broker 解决「服务在哪儿、怎么跨机器调」。
  • 认为 SOA 就是微服务。 SOA 强调中心化的服务总线、较粗的服务粒度与契约治理；微服务强调去中心化、细粒度、独立数据库与自动化运维。 微服务是 SOA 的一种轻量化演进，但「服务化」不等于「微服务化」。答题时必须写出至少两点差别（治理方式、粒度/数据）。
  • 把「分层越细越好」当结论。 分层有明确代价：数据要逐层传递，性能下降；多层调用难调试；为了性能常被迫合并层，反而破坏逻辑独立性。 分层的难点恰恰是「找不到唯一正确的抽象层次」。
  • 以为插件就是「加了个功能」。 课件的原话是「插件不是简单的功能扩展」：必须有固定的、公开的、可在运行时扩展的接口（扩展点）， 并且插件不能独立运行、不依赖应用内部流程。装饰器与策略模式虽然也能换行为，但没有这样的公开扩展点。
  • 说管道-过滤器适合交互式系统。 它本质是批处理：每个过滤器要做完整的「整批输入 → 整批输出」转换，因此不适合交互式应用， 也难以维持两条相关数据流之间的通信。需要交互应选 MVC/事件驱动。
  • 认为 MVC 里模型依赖视图。 依赖方向是单向的：View 依赖 Model，Controller 依赖 Model 与 View，Model 不依赖任何视图。 一旦模型里出现 refreshView()，MVC 的结构性优点就消失了。
  • 把观察者模式、事件驱动、发布-订阅当成同义词。 观察者是对象级设计模式，主题直接持有观察者引用；事件驱动是架构风格，发布者不指定接收者； 发布-订阅必须有消息代理，双方互不相识。层次、耦合方式、同步性三点都不同。
  • 只背优点，不答代价。 简答题按「定义 + 作用 + 代价」三段给分。每种模式至少准备两条代价： 分层的性能、管道-过滤器的交互性、插件的加载与接口依赖、Broker 的中心瓶颈、 SOA 的通信开销、MVC 的通知开销、微服务的分布式复杂度。

选型口诀

三问定模式 问变化点：界面变 → MVC/MVVM；算法或规则变 → 策略/插件/解释器；规模变 → 微服务/分层伸缩。 问数据形态：数据流式加工 → 管道-过滤器；共享状态协作 → 黑板/仓储；跨机器调用 → Broker/SOA/微服务。 问代价承受力：团队能运维分布式吗？能治理插件版本吗？能接受最终一致吗？答不上来就退回更简单的方案。
