创建型模式：把「new」这件事从客户端手里拿走

创建型模式抽象了实例化过程，让系统独立于对象「如何被创建、组合和表示」。五个 GoF 创建型模式加一个课程补充的简单工厂，本质上都在回答同一个问题：当具体类必须变化时，如何让调用方不必跟着改。

考试重点约 35 分钟创建型 ×5高频设计题
开始阅读看五个模式直接自测
第 4 章 · 子页面 模式总览 创建型 ×5 结构型 ×7 行为型 ×11

学习目标

读完这一页，应当能独立完成下列动作。

  1. 能说出创建型模式共同的两条主旋律：封装「用哪些具体类」与隐藏「实例如何被创建和组装」。
  2. 能画出工厂方法、抽象工厂、建造者、单例四种模式的类图，并指出各自的抽象角色与具体角色。
  3. 能在给定需求（换主题、换数据库、换日志后端、造复杂对象）时，判断该用哪一种创建型模式。
  4. 能解释单例的五种写法（饿汉/懒汉/双重检查/静态内部类/枚举）各自的问题，尤其是并发与反射破坏。
  5. 能区分「工厂方法 vs 抽象工厂」「建造者 vs 工厂」「原型 vs 克隆构造函数」三组高频混淆点。

知识地图

创建型模式的共同骨架：客户端只认抽象，具体类被关进工厂/建造者/原型里。

问题

  • 客户端直接 new 具体类 → 硬编码依赖
  • 产品类型要变，客户端跟着改
  • 构造步骤多、顺序不能错
  • 对象创建代价高，想复用已有实例

角色

  • Product 抽象产品
  • ConcreteProduct 具体产品
  • Creator / Factory 工厂
  • Director / Builder / Prototype / Singleton

协作

  • 客户端只持有抽象类型
  • 工厂决定实例化哪个子类
  • 建造者按稳定步骤装配
  • 原型靠 clone 复制自身

代价

  • 类数量成对增加
  • 抽象工厂难以新增产品等级
  • 单例引入全局状态与并发问题
  • 原型要处理深/浅拷贝
02

核心概念与模式卡

#

先把「产品族 / 产品等级结构 / 延迟实例化」这些词说清，否则五个模式会糊成一团。

创建型模式 Creational Patterns

把对象的创建与使用分离。系统不需要知道要创建哪个具体类、实例怎么被组装，只面向抽象编程。符合单一职责原则：创建是创建，使用是使用。

总览GoF 三大类之一

产品等级结构 Product Hierarchy

同一抽象产品下的所有具体产品构成的继承层次。例如 Button → WindowsButton / MacButton。一个等级结构 = 一条继承链。

术语抽象工厂

产品族 Product Family

位于不同产品等级结构中、但属于同一「品牌/系列」的一组产品。例如 Windows 主题下的 WindowsButton + WindowsText。抽象工厂保证你拿到的永远是同一族的产品。

术语易混淆

简单工厂 Simple Factory

一个静态方法 + 一串 if/else，按参数返回不同子类。不属于 GoF 23 种，但课程把它当作工厂家族的入门形态。新增产品要改工厂判断逻辑，违反开闭原则。

非 GoF课程补充

工厂方法 Factory Method

把「实例化哪一个具体产品」推迟到子类。Creator 只声明抽象工厂方法，ConcreteCreator 决定返回哪个 ConcreteProduct。工厂与产品形成平行的类层次。

GoF类创建型

抽象工厂 Abstract Factory

面向多个产品等级结构的工厂：一个工厂一次创建一整个产品族。增加新产品族容易，增加新产品等级结构要改所有工厂，这是它的开闭原则「倾斜」。

GoF对象创建型

建造者 Builder

把「复杂对象的构造步骤」与「最终表示」分离。Director 固定装配顺序，Builder 子类决定每个零件长什么样。适合步骤稳定、零件易变的对象。

GoF对象创建型

原型 Prototype

通过复制已有实例来创建新对象，而不是 new + 重新初始化。关键在于 clone() 的浅拷贝 / 深拷贝语义，以及「类名对客户端不可见」时也能造对象。

GoF对象创建型

单例 Singleton

保证一个类只有一个实例并提供全局访问点。它同时是创建型模式里唯一「限制数量」的模式，代价是引入全局状态、难以测试、并发与反射都可能破坏它。

简单工厂模式

Simple Factory Pattern 创建型
意图
定义一个工厂类，根据参数返回不同子类的实例，客户端不直接 new。
别名
静态工厂方法（Static Factory Method）
适用场景
工厂负责创建的对象比较少；客户端只知道参数、不关心创建细节。
参与角色
Factory、Product（抽象产品）、ConcreteProduct（具体产品）
主要代价
工厂类职责过重，新增产品必须改工厂判断逻辑，违反开闭原则。

工厂方法模式

Factory Method Pattern 创建型
意图
定义一个创建对象的接口，让子类决定实例化哪一个类；使一个类的实例化延迟到其子类。
别名
虚拟构造器（Virtual Constructor）、多态工厂
适用场景
一个类不知道它所需对象的类；一个类希望由子类指定创建哪个对象；需要把创建任务委托给多个工厂子类之一。
参与角色
Product、ConcreteProduct、Creator、ConcreteCreator
主要代价
每增加一个产品就要增加一个工厂，类个数成对增长。

抽象工厂模式

Abstract Factory Pattern 创建型
意图
提供一个创建一系列相关或相互依赖对象的接口，而无须指定它们具体的类。
别名
Kit（套件）
适用场景
系统由多个产品族中的一个来配置；同一产品族的产品必须一起使用；想对外只暴露接口不暴露实现。
参与角色
AbstractFactory、ConcreteFactory、AbstractProduct、Product、Client
主要代价
增加新的产品等级结构（新种类产品）要改抽象工厂及所有子类，开闭原则只倾斜一半。

建造者模式

Builder Pattern 创建型
意图
将一个复杂对象的构建与其表示分离，使同样的构建过程可以创建不同的表示。
别名
生成器模式
适用场景
产品内部结构复杂；构建算法稳定但零件易变；需要按固定顺序装配、或需要分步构造。
参与角色
Builder、ConcreteBuilder、Director、Product
主要代价
难以应付构建算法本身的变化；类的数量增加，对简单对象是过度设计。

原型模式

Prototype Pattern 创建型
意图
用原型实例指定创建对象的种类，并通过拷贝这些原型来创建新的对象。
别名
克隆（Clone）
适用场景
创建新对象成本过大（数据库、网络、大量计算）；系统要保存对象状态、或类名不应对客户端暴露。
参与角色
Prototype（声明 clone）、ConcretePrototype、Client
主要代价
必须正确实现深拷贝，否则原型与副本共享可变子对象；带循环引用的对象图深拷贝实现困难。

简单工厂的简化形态

Static Factory on Abstract Product 创建型
意图
把静态工厂方法直接写在抽象产品类里，让抽象产品同时兼任子类的工厂。
别名
抽象产品兼任工厂（课程「简单工厂模式的简化」）
适用场景
产品族很小、不值得单独建一个工厂类；希望调用方少记一个类名。
参与角色
AbstractProduct（同时充当 Factory）、ConcreteProduct
主要代价
抽象产品类职责变重（既定义接口又负责创建），违反单一职责；扩展仍要改产品类。

原型管理器

Prototype Manager 创建型
意图
用一个注册表（Map）保存若干原型对象，客户端按键取原型并 clone，从而在运行时动态增删产品种类。
别名
原型注册表（Prototype Registry）
适用场景
需要动态注册/注销可复制的对象；产品种类由配置决定，客户端不应硬编码类名。
参与角色
Prototype、ConcretePrototype、PrototypeManager（注册表）、Client
主要代价
注册表需要管理生命周期；每个原型都必须正确实现深拷贝。

单例模式

Singleton Pattern 创建型
意图
保证一个类仅有一个实例，并提供一个全局访问点来获取它。
别名
单件模式
适用场景
系统只需要一个窗口管理器/文件系统/配置中心/连接池；需要严格控制唯一实例且允许子类化扩展。
参与角色
Singleton（静态 instance + 静态 Instance() 方法）
主要代价
引入全局状态，单元测试难隔离；反射、序列化、多类加载器都能破坏唯一性。

01

简单工厂模式 Simple Factory Pattern

创建型

意图：定义一个工厂类，它可以根据参数的不同返回不同类的实例，被创建的实例通常都具有共同的父类。客户端只需「消费」产品，不必知道创建细节。

动机 / 问题场景

课程用一个点餐场景引入：PizzaConsumer.orderPizza(String type) 里写着一长串 if (type.equals("cheese")) pizza = new CheesePizza();。每增加一种 Pizza，这段客户端代码就要改一次，直接违反「业务需求变化时客户端代码尽量不变」的原则。把创建逻辑搬到服务端的一个 SimplePizzaFactory.createPizza(type) 里之后，新增 Pizza 只需改服务端，客户端一行不动。

结构

工厂集中了全部创建逻辑；产品是一棵继承树。客户端只依赖 Product 与 Factory 两个抽象。

  • Factory —— 工厂角色，含必要的判断逻辑，决定何时创建哪一个具体产品类的实例。
  • Product —— 抽象产品角色，定义所有具体产品的公共接口。
  • ConcreteProduct —— 具体产品角色，实现 Product 接口，被工厂创建。

协作要点

  1. 客户端把「要什么」的参数（如 "cheese"）传给工厂的静态方法。
  2. 工厂内部用 if/else 或 switch 匹配参数，new 出对应子类。
  3. 工厂把对象向上转型为 Product 返回，客户端只看到抽象类型。
  4. 客户端调用 Product 上声明的方法完成业务，完全不感知具体类名。

适用场景

  • 工厂类负责创建的对象比较少，判断逻辑不会膨胀成几百行。
  • 客户端只知道参数，不关心创建细节，甚至不需要记住具体类名。
  • 需要把「创建哪一族实现」的决策集中到一处配置（如读取 XML 参数）时。

优缺点

优点
  • 把创建与使用分离，降低耦合，两者可以独立修改。
  • 客户端代码对新增产品无感（前提是工厂在服务端）。
  • 配合配置文件可以在不改 Java 源码的情况下更换产品。
代价 / 缺点
  • 工厂类职责过重，一旦它出问题整个系统受影响，是典型的上帝类。
  • 新增产品必须修改工厂的判断分支，违反开闭原则——这是它最致命的问题。
  • 产品类型很多时工厂方法内部的业务逻辑会非常复杂，难维护。

参考实现

易错点 · 把简单工厂当成 GoF 模式来答。GoF 23 种里没有简单工厂，它属于「工厂家族的入门形态」。简答题问「工厂模式有哪几种形态」时，可以答简单工厂 / 工厂方法 / 抽象工厂三种，但要说明只有后两种是 GoF 模式，简单工厂违反开闭原则。

工厂方法模式 Factory Method Pattern

创建型

意图：定义一个用于创建对象的接口，让子类决定实例化哪一个类。Factory Method 使一个类的实例化延迟到其子类。

动机 / 问题场景

课程用日志组件举例：有 FileLog 和 DBLog 两个实现，抽象父类是 Log。如果客户自己 new FileLog()，客户代码就绑死在具体子类上；新增 EventLog（写 Windows 事件日志）时，所有 new 过日志的地方都要改。解决办法是把「new 哪个」交给工厂子类，客户端只持有 Log 与 LogFactory 两个抽象。

结构

继承

工厂层次与产品层次一一对应、平行生长：ConcreteFactory 的 factoryMethod 返回对应的 ConcreteProduct。anOperation() 里调用抽象的 factoryMethod()，实际执行的是子类版本——这就是「延迟到子类」。

  • Product —— 定义工厂方法所创建的对象的接口（抽象产品）。
  • ConcreteProduct —— 实现 Product 接口的具体产品。
  • Creator —— 声明返回 Product 类型的工厂方法；可给出默认实现（返回默认 ConcreteProduct）；通常在某个业务方法里调用工厂方法。
  • ConcreteCreator —— 重定义工厂方法，返回一个 ConcreteProduct 实例。

协作要点

  1. 客户端创建某个 ConcreteCreator（或从配置里拿到它）。
  2. 客户端调用 Creator 上的业务方法 anOperation()。
  3. anOperation() 内部调用抽象的 factoryMethod()。
  4. 动态绑定到 ConcreteCreator 的实现，new 出对应的 ConcreteProduct。
  5. 产品以 Product 抽象类型返回并使用，客户端全程不知道具体类。

适用场景

  • 一个类不知道它所需要的对象的类：只知道接口，不知道实现。
  • 一个类希望通过子类来指定创建哪个对象。
  • 需要把创建任务委托给多个工厂子类之一，客户端无需关心是哪一个。
  • 产品结构较复杂、需要一条与产品平行的工厂继承链时。

优缺点

优点
  • 新增产品只需新增一个工厂子类，不修改已有代码，满足开闭原则。
  • 为子类提供「挂钩」：用工厂方法在类内部创建对象比直接 new 更灵活。
  • 连接平行的类层次，具体工厂与具体产品一一对应，结构清晰。
代价 / 缺点
  • 每增加一个产品就要增加一个工厂类，类个数成对增长，系统复杂度上升。
  • 引入了额外的抽象层，简单场景下属于过度设计。
  • 客户端仍需决定实例化哪个具体工厂，选择逻辑只是被挪走而非消失。

与相似模式的区别

维度简单工厂工厂方法抽象工厂

新增产品族——加具体工厂（易）

参考实现

易错点 · 把工厂方法写成了「一个工厂类里的 switch」。如果 createLog() 内部还是 if (type == ...)，那只是把简单工厂套了个抽象类的壳，新增产品仍要改工厂，开闭原则并没有被满足。工厂方法的判定标准是：新增产品时只新增类、不修改已有类。

03

抽象工厂模式 Abstract Factory Pattern

创建型

意图：提供一个创建一系列相关或相互依赖对象的接口，而无需指定它们具体的类。它面向的是多个产品等级结构，一次创建一整个产品族。

动机 / 问题场景

换桌面主题是最经典的例子：开始按钮、任务栏、菜单栏、工具栏会一起变，而且色调必须一致。如果每个控件都用各自的工厂方法创建，谁来保证它们来自同一套主题？抽象工厂的做法是：一个 ThemeFactory 同时负责造按钮和文本框，WindowsFactory 造出来的必然是 Windows 家族。课程里的迷宫例子同理：MazeFactory 一次造出 Maze / Room / Wall / Door，换成 BombedMazeFactory 后整座迷宫的部件风格统一改变。

结构

创建

横向看是产品族（同一工厂造出的一套），纵向看是产品等级结构（同一类控件的继承链）。

  • AbstractFactory —— 声明创建抽象产品对象的操作接口（一组 createProductX）。
  • ConcreteFactory —— 实现创建具体产品的操作，一个具体工厂对应一个产品族。
  • AbstractProduct —— 为一类产品对象声明接口。
  • Product —— 定义一个被具体工厂创建的产品对象。
  • Client —— 只使用 AbstractFactory 与 AbstractProduct 声明的接口。

协作要点

  1. 客户端持有 AbstractFactory 引用（通常在启动时按配置注入一个具体工厂）。
  2. 客户端调用 createProductA() 与 createProductB()。
  3. 具体工厂分别 new 出同族的 ConcreteProductA1 / B1。
  4. 客户端拿到的一组对象必然属于同一产品族，风格/协议自洽。
  5. 想换整套实现时，只换具体工厂的实例，客户端代码不动。

适用场景

  • 系统不应当依赖产品类实例如何被创建、组合和表达的细节。
  • 系统中有多于一个产品族，而每次只使用其中某一族。
  • 属于同一产品族的产品将一起使用，这个约束必须在设计中体现出来。
  • 提供一个产品类库，只想暴露接口而非实现。

优缺点

优点
  • 隔离具体类的生成，客户端不需要知道什么被创建，更换整族实现很容易。
  • 保证客户端始终只使用同一产品族的对象，不会出现「Windows 按钮配 Linux 文本框」。
  • 增加新的产品族（新具体工厂）无需修改已有系统。
代价 / 缺点
  • 增加新的产品等级结构（新种类产品）要改 AbstractFactory 接口及所有子类，开闭原则出现「倾斜」。
  • 抽象工厂把所有可能被创建的产品集合都规定死了，接口很重。
  • 类层次比工厂方法更深，理解成本更高。

面对的产品等级结构1 个多个（≥2）
抽象工厂的职责只声明 1 个工厂方法声明一组 create 方法
扩展新产品的代价加一个工厂子类（易）改接口 + 所有子类（难）
扩展新产品族不适用加一个具体工厂（易）
典型场景日志、解析器换皮肤、跨平台 UI、多数据库方言

参考实现

易错点 · 把「新增产品族」和「新增产品等级结构」混为一谈。抽象工厂的扩展性是有方向的：加一族（如新增 DarkFactory）很容易，只需新增一个具体工厂；加一个新品种（如新增 CheckBox 等级结构）很难，要改 AbstractFactory 接口和每一个具体工厂。这就是教材反复强调的「开闭原则的倾斜性」，答题时必须点出来。

04

建造者模式 Builder Pattern

创建型

意图：将一个复杂对象的构建与它的表示分离，使得同样的构建过程可以创建不同的表示。

动机 / 问题场景

课程用「游戏场景中造房子」举例：房子由地板、墙壁、窗户、门、天花板五部分组成，构建步骤是固定的（先地板再墙再门窗），但具体组件极易变化（罗马式房子、中式房子、雪屋）。如果每换一种房子就写一个构造函数，参数会爆炸；如果让客户端自己按顺序装配，顺序一错就造出畸形对象。建造者把「步骤」固化在 Director 里，把「零件长什么样」交给 ConcreteBuilder。

结构

Director+ construct()
持有 builder 引用
Builder+ buildPartA() / buildPartB() / buildPartC()
+ getResult()
继承
ConcreteBuilder+ buildPartX()
+ getResult()
装配
Product复杂对象

Director 只认识 Builder 接口：buildPartA → buildPartB → buildPartC → getResult，顺序固定。

  • Builder —— 为创建一个 Product 对象的各个部件指定抽象接口。
  • ConcreteBuilder —— 实现 Builder 接口以构造和装配产品的各个部件；定义并提供获取最终产品的接口。
  • Director —— 构造一个使用 Builder 接口的对象，负责安排装配顺序。
  • Product —— 表示被构造的复杂对象，由多个部件组成。

协作要点

  1. 客户端创建 Director 与某个 ConcreteBuilder。
  2. 把 ConcreteBuilder 传给 Director（或让 Director 持有它）。
  3. Director 调用 construct()，按固定顺序依次调用 buildPartX。
  4. ConcreteBuilder 在每一步里创建并组装自己的部件。
  5. 客户端通过 getResult() 取回成品，全程不关心装配顺序。

适用场景

  • 需要生成的产品对象有复杂的内部结构（由多个部件组成）。
  • 创建复杂对象的算法稳定，或者建造者模式需要强制一定的生成顺序。
  • 当构造过程允许被构造的对象有不同的表示时。
  • 需要「分步构造」并在中途做校验、或需要不可变对象（Builder 链式调用）。

优缺点

优点
  • 产品的内部表象可以独立变化，客户端不必知道产品内部组成的细节。
  • 每一个 Builder 都相对独立，与其他 Builder 无关，可替换。
  • 对构造过程有更精细的控制，能强制装配顺序、能做逐步校验。
  • 把构建代码与表示代码彻底分开。
代价 / 缺点
  • 难以应付「分步骤构建算法」本身的需求变动——步骤一变，Director 要改。
  • 会引入 Builder / ConcreteBuilder / Director / Product 多个类，对简单对象是过度设计。
  • 客户端必须知道有哪些具体 Builder 可选。

与相似模式的区别

维度建造者抽象工厂
关注点分步装配一个复杂对象一次性创建一族相关对象
返回时机最后一步 getResult() 才产出每次 create 立刻返回一个产品
产品结构一个复杂对象（组合体）多个平级产品
扩展方向新增一种表示（新 Builder）新增一个产品族（新 Factory）
典型场景组装电脑、构建 SQL、造房子换皮肤、跨平台 UI

参考实现

易错点 · 把建造者和工厂当成同一个东西。工厂模式关心「创建哪一个类」，一次调用返回一个完整对象；建造者关心「怎样一步步装配」，返回时机在最后一步。判断口诀：产品是「一个」还是「一堆」→ 建造者；产品是「一族」→ 抽象工厂。另外建造者的步骤是稳定的，工厂的产品种类是变化的。

原型模式 Prototype Pattern

创建型

意图：用原型实例指定创建对象的种类，并且通过拷贝这些原型创建新的对象。客户端不需要知道具体类名，只需要一个 clone() 方法。

动机 / 问题场景

设想一个图形编辑器：用户画好一个复杂图形（含几十个子图元、样式、图层），现在要复制粘贴出第二个。如果重新 new 再逐个属性赋值，既要知道具体类，又要重新走一遍昂贵的初始化。原型模式让对象自己负责复制自己——Graphic.clone() 返回一个同类型的新对象，客户端只面向 Graphic 接口操作，新增图形类型时复制逻辑一行不用改。

结构

Prototype+ clone(): Prototype
实现
ConcretePrototypeAConcretePrototypeB
Client 调用 clone()
Client只持有 Prototype 引用

若对象有可变子对象，必须做深拷贝，否则副本与原对象共享同一份数据。

原型模式把「创建」这个职责下放给对象自己，客户端只发一条 clone 消息。

  • Prototype —— 声明一个克隆自身的接口（Java 里通常是 Cloneable + clone()）。
  • ConcretePrototype —— 实现克隆操作，返回一个与自身类型相同的副本。
  • Client —— 通过调用原型的 clone 方法得到新对象，不需要知道具体类名。

协作要点

  1. 客户端持有一个原型注册表（Map<String, Prototype>）或直接持有原型引用。
  2. 客户端调用 prototype.clone()。
  3. 具体原型复制自身内部状态，返回新实例（浅拷贝或深拷贝）。
  4. 客户端按需修改副本的少量属性，得到目标对象。

适用场景

  • 创建新对象的成本过大（访问数据库、网络请求、大量计算）。
  • 系统要保存对象的状态，而对象状态变化很小（配合备忘录模式做撤销）。
  • 需要避免创建与产品类层次平行的工厂类层次。
  • 类名不应对客户端暴露（如通过配置注册一批原型）。

优缺点

优点
  • 可以在运行时动态增加或删除产品种类，客户端无需改动。
  • 对「创建代价高」的对象，克隆往往比重新构造快得多。
  • 可以用「深拷贝 + 少量修改」代替「完整重新构造」，简化复杂对象的创建。
代价 / 缺点
  • 必须正确实现深拷贝，否则原型与副本共享可变子对象，一处修改两处生效。
  • 带循环引用的对象图深拷贝实现困难，容易栈溢出。
  • 每个具体原型都要实现 clone，类数量不少；Java 的 Cloneable 语义也常被误用。

与相似模式的区别

维度原型工厂方法
创建方式复制已有实例由工厂 new 出实例
需要知道类名不需要具体工厂内部需要
初始状态继承原型的当前状态总是全新的初始状态
适合场景创建代价高、状态复杂产品种类需要动态扩展

参考实现

易错点 · 以为 clone() 默认就是深拷贝。Java 的 Object.clone() 是逐字段浅拷贝：基本类型复制值，引用类型只复制地址。如果原型里有 List、数组、其他可变对象，副本与原型会共享同一份数据，改一个另一个也变。必须在 clone 里对每个可变字段重新构造，或者改用「序列化 + 反序列化」实现深拷贝。

单例模式 Singleton Pattern

创建型

意图：保证一个类仅有一个实例，并提供一个全局访问点。

动机 / 问题场景

系统中只能有一个窗口管理器、一个文件系统、一个配置中心、一个连接池。用全局变量可以访问，但无法阻止别人再 new 一个。更好的办法是让类自己负责保存唯一实例：构造函数私有化，对外只暴露一个静态的 getInstance()。课程用 C++ 版本来讲，Java 版本要点一致：私有构造 + 静态成员 + 静态访问方法。

结构

Singleton- static instance: Singleton
- Singleton()
+ static getInstance()
唯一实例
instance自身唯一实例
Client通过 getInstance() 访问

类图里 Singleton 既是被创建者，也是自己的工厂——这是它与其他创建型模式最大的不同。

  • Singleton —— 定义静态的 instance 成员与静态的 Instance() 操作，构造函数为 protected/private。
  • Client —— 通过类名直接调用 Singleton.getInstance()，无法自行 new。

协作要点

  1. 客户端第一次调用 getInstance()。
  2. 方法检查静态成员是否为空；为空则 new 出唯一实例并保存。
  3. 后续调用直接返回已保存的实例。
  4. 客户端通过该实例调用业务方法，全局共享同一份状态。

适用场景

  • 当类只能有一个实例，而且用户可以从一个众所周知的访问点访问它时。
  • 当这个唯一实例应当通过子类化可扩展，且客户无需更改代码就能使用扩展实例时。
  • 需要严格控制全局资源（配置、缓存、线程池、日志器）时。

优缺点

优点
  • 对唯一实例的受控访问：类自己封装实例，可严格控制客户何时、怎样访问。
  • 缩小命名空间：是对全局变量的改进，避免污染全局名字空间。
  • 允许对操作和表示的精化：可以有子类，运行时用扩展类的实例配置应用。
代价 / 缺点
  • 引入全局状态，模块间产生隐式依赖，单元测试难以隔离（需 mock 单例）。
  • 并发环境下需要额外同步，写法不当会出现双实例或性能问题。
  • 反射、序列化、多个类加载器都能破坏唯一性，需要额外防护。
  • 违反单一职责：既管业务又管生命周期。

与相似模式的区别

维度单例静态工具类
是否有实例有唯一实例，可实现接口、可继承无实例，只有静态方法
能否多态可以（面向接口注入）不能
生命周期可控（懒加载 / 饿汉）类加载即初始化
测试友好度需 mock，较差静态方法难替换，也差

参考实现

易错点 · 以为加了 synchronized 就万事大吉，或忘了 volatile。双重检查锁里，instance = new DclSingleton() 不是原子操作：分配内存 → 初始化对象 → 把引用赋给 instance，可能被重排序。没有 volatile 时，另一个线程可能看到「引用已非空但对象还没初始化完」的状态。另外反射可以调用私有构造（setAccessible(true)）造出第二个实例，只有枚举写法能天然挡住反射与序列化。

答题技巧被问「创建型模式有什么用」时，先答两条主旋律（封装「用哪些具体类」、隐藏「实例如何创建与组装」），再点出符合单一职责：创建与使用分离；最后举一例（换数据库只换工厂）。三句话答完，比罗列五个模式更得分。

表三：建造者 vs 工厂 / 原型 vs 单例 两组高频混淆

易混组合区别要点判断口诀
建造者 vs 抽象工厂建造者分步装配一个复杂对象，最后 getResult 才产出；抽象工厂一次创建一族平级产品，每次 create 立即返回。「一个复杂对象」→ 建造者；「一族相关对象」→ 抽象工厂。
原型 vs 工厂方法原型靠复制已有实例，新对象继承原型的当前状态；工厂每次 new 出全新初始状态的对象。要「保持状态复制」→ 原型；要「全新对象」→ 工厂。
单例 vs 静态工具类单例有实例、可实现接口、可继承、生命周期可控；静态工具类无实例、不能多态。需要多态或注入 → 单例；纯函数集合 → 静态工具类。
简单工厂 vs 工厂方法简单工厂用一个静态方法集中判断；工厂方法把判断分散到各个工厂子类。新增产品要改判断逻辑 → 简单工厂；只新增类 → 工厂方法。

记忆线索五个创建型模式其实对应五种「推迟创建」的方式：工厂方法 → 推迟到子类；抽象工厂 → 推迟到具体工厂对象；建造者 → 推迟到最后一步；原型 → 推迟到已有实例；单例 → 推迟到首次访问。抓住「推迟到哪里」这一条线，五个模式就不会记串。

05

易错点

#

下面每一条都来自真实作业与考卷，注意它们不是「知识点复述」，而是「学生常犯的具体错误」。

  • 把简单工厂算作 GoF 23 种之一。GoF 书里没有简单工厂。它的判断逻辑集中在一个静态方法里，新增产品必须改这段逻辑，直接违反开闭原则。考试若问「23 种模式分类」，创建型只有 5 种：工厂方法、抽象工厂、建造者、原型、单例。
  • 认为工厂方法一定满足开闭原则，却把 switch 塞进了抽象工厂方法里。判定标准不是「有没有抽象类」，而是新增产品时是否只新增类、不修改已有类。如果 create() 里还有 if (type == ...)，那只是给简单工厂套了层壳。
  • 把抽象工厂的扩展方向记反。抽象工厂加产品族容易（新增一个具体工厂即可），加产品等级结构难（要改 AbstractFactory 接口和所有具体工厂）。这就是教材说的「开闭原则的倾斜性」，答反了等于没答。
  • 单例只写「私有构造 + 静态实例」，不提并发与破坏。完整的单例答案必须覆盖：懒加载与线程安全（双重检查锁需 volatile）、反射可通过 setAccessible 破坏私有构造、序列化反序列化会产生新实例、多类加载器环境各自一份。枚举写法是唯一能同时防住反射与序列化的方案。
  • 原型模式的 clone 直接返回 super.clone() 就交卷。Object.clone() 是浅拷贝，引用字段只复制地址。原型里有 List、数组、其他可变对象时，副本与原型共享数据，必须手动重建每个可变字段（或序列化往返）实现深拷贝。
  • 建造者只写 Builder 不写 Director，或让 Director 直接 new 产品。Director 的职责是固化装配顺序，它只能依赖 Builder 抽象；一旦 Director 里出现 new RomanHouse()，「同样的构建过程可以创建不同的表示」这个意图就彻底失效了。
