行为型模式：把「谁在什么时候做什么」从代码里抽出来

行为型模式刻画运行时的复杂控制流，重点不在类与对象的结构，而在它们之间如何交互、如何分配职责。十一个模式的共同目标是：把「算法」「状态」「请求」「遍历」这些易变的控制逻辑，从硬编码的分支与调用中解放出来，变成可替换、可组合、可复用的对象。

学习目标

行为型是本章分值最高、也最容易混的部分，读完应当能：

  1. 能说出行为型模式的两条划分轴：类行为型（继承分派，只有模板方法与解释器）与对象行为型（组合分派）。
  2. 能画出策略、状态、命令、观察者、责任链五个高频模式的类图，并说清请求/状态的流转路径。
  3. 能区分「策略 vs 状态」「策略 vs 模板方法」「中介者 vs 观察者」「命令 vs 策略」四组必考辨析。
  4. 能解释访问者模式的「双重分派」，并说明它为什么难以新增元素类。
  5. 能在给定场景（审批流、撤销重做、状态机、事件通知、算法切换）中选出正确的行为型模式。

知识地图

按课程给的「类间关系」分组记，比按字母顺序记有效得多。

按关系分组

  • 父类与子类：策略、模板方法
  • 两个类之间：备忘录、状态
  • 类的状态：观察者、迭代器、责任链、命令
  • 通过中间类：访问者、中介者、解释器

核心角色

  • Context / State / Strategy
  • Subject / Observer
  • Handler / Command / Receiver
  • Visitor / Element / Mediator

协作方式

  • 委托：Context 转发给策略/状态
  • 广播：Subject 遍历通知观察者
  • 传递：请求沿责任链下传
  • 回调：父类调用子类原语操作

常见代价

  • 类数量增加、小对象变多
  • 控制流隐式，调试困难
  • 状态/策略需客户端感知
  • 访问者难以新增元素类

核心概念与模式卡

#

行为型模式数量最多（11 个），先掌握「划分轴 + 四组辨析」，再逐个记结构，效率最高。

行为型模式 Behavioral Patterns

对不同对象之间划分责任和算法的抽象化。不仅描述类与对象的结构，更关注它们之间的交互与通信，刻画运行时的复杂控制流。

总览GoF 三大类之一

类行为型模式 Class Behavioral

使用继承机制在类间分派行为，通过多态分配父类与子类的职责。十一个里只有模板方法与解释器属于这一类。

分类易错

对象行为型模式 Object Behavioral

使用对象复合而不是继承来分配行为，通过对象关联分配多个类的职责。大部分行为型模式都属于这一类（合成复用原则）。

分类合成复用

好莱坞法则 Hollywood Principle

「别来找我，让我来找你」——父类调用子类的操作，而不是子类调用父类。模板方法正是这一反向控制结构的体现，也是依赖倒置的一种形式。

模板方法核心概念

双重分派 Double Dispatch

访问者模式的精髓：element.accept(visitor) 先按元素的具体类型分派一次，再在 accept 里调用 visitor.visitXxx(this) 按访问者的具体类型分派一次。两次动态绑定共同决定执行哪个方法。

访问者高频

推模型 vs 拉模型 Push / Pull

观察者模式的通知方式：推模型把变更细节随通知一起传给观察者，简单；拉模型只发「我变了」，由观察者回查主题，更灵活、耦合更低。

观察者易混淆

宏命令 Macro Command

命令模式与组合模式的结合：CompositeCommand 持有一组命令，execute() 时遍历执行所有子命令，实现「一组操作」的批量执行与撤销。

命令组合应用

钩子方法 Hook Method

模板方法里的可选步骤：抽象类给出空实现或默认实现，子类可选择性地覆盖，从而在不改变算法骨架的前提下影响流程走向。

Subject、ConcreteSubject、Observer、ConcreteObserver
主要代价

State Pattern 行为型
意图
允许一个对象在其内部状态改变时改变它的行为，对象看起来似乎修改了它的类。
别名

适用场景
对象行为取决于其状态且必须在运行时改变；操作中含有庞大的多分支条件语句且分支依赖状态。
参与角色
Context、State、ConcreteState
主要代价
状态类数量增加；状态转移逻辑分散在各状态类中，整体流程不易一眼看清。

策略模式

Strategy Pattern 行为型
意图
定义一系列算法，把它们一个个封装起来，并且使它们可相互替换，使算法可独立于使用它的客户而变化。
别名

适用场景
许多相关类仅行为有异；需要算法的不同变体；需要替换大量条件语句。
参与角色
Strategy、ConcreteStrategy、Context
主要代价
客户端必须了解各策略的差异才能选择；策略类数量增加。

意图
使多个对象都有机会处理请求，从而避免请求发送者与接收者之间的耦合，将对象连成一条链并沿链传递请求直到被处理。
别名
责任链
适用场景
多个对象可处理同一请求，具体由谁处理运行时确定；处理者集合与顺序需动态指定。
参与角色
Handler（抽象处理者，含 successor）、ConcreteHandler、Client
主要代价
不保证请求一定被处理；链过长影响性能；调试时请求路径不直观。

访问者模式

Visitor Pattern 行为型
意图
表示一个作用于某对象结构中的各元素的操作，使你在不改变各元素类的前提下定义作用于这些元素的新操作。
别名
—
适用场景
对象结构包含很多不同接口的类，需对其施加依赖具体类的操作；需避免这些操作「污染」元素类。

Visitor、ConcreteVisitor、Element、ConcreteElement、ObjectStructure
主要代价
每新增一个元素类，就要改 Visitor 接口及所有具体访问者——开闭原则反向倾斜。

模板方法模式 Template Method Pattern

行为型

意图：定义一个操作中的算法骨架，而将一些步骤延迟到子类中。模板方法使得子类可以不改变一个算法的结构即可重定义该算法的某些特定步骤。

动机 / 问题场景

课程用「本科生培养」举例：教育部制定纲领性流程——军训 → 学文化课 → 做毕业设计 → 毕业，这个骨架是固定的；各学校负责具体环节怎么做，细节是变化的。另一个例子是银行账户计息：活期与定期的计息流程完全一样（取账户类型 → 取利率 → 算金额 → 相乘），只是 getAccountType() 和 getInterestRate() 的返回值不同。

结构

TemplateMethod() 在抽象类里写死调用顺序，primitiveX() 是抽象方法，由子类实现——父类调用子类，这就是「好莱坞法则」。

模板方法定义骨架（不变），原语操作由子类实现（可变），钩子方法提供可选扩展点。

  • AbstractClass —— 定义抽象的原语操作（primitive operation），子类重定义它们以实现算法步骤；实现模板方法定义算法骨架。
  • ConcreteClass —— 实现原语操作以完成算法中与特定子类相关的步骤。
  • 钩子方法 —— 抽象类中给出默认/空实现的方法，子类可选择覆盖以影响流程。

协作要点

  1. Client 创建 ConcreteClass 实例，以 AbstractClass 类型引用它。
  2. Client 调用 templateMethod()（注意：调用的是父类定义的方法，通常 final）。
  3. templateMethod() 按固定顺序调用各原语操作。
  4. 多态绑定到 ConcreteClass 的实现，完成具体步骤。
  5. 若存在钩子方法，子类的覆盖结果会影响流程分支。

适用场景

  • 具有统一的操作步骤或操作过程，但各步骤的具体细节不同。
  • 需要固定算法骨架，防止子类破坏执行顺序。
  • 多个类有公共行为需要提取到父类，同时保留差异点作为扩展点。

优缺点

优点
  • 代码复用：把子类的公共行为提取到父类，消除重复。
  • 反向控制结构（好莱坞法则），体现依赖倒置，父类掌握流程主导权。
  • 通过钩子方法提供灵活扩展点，同时不破坏算法骨架。
代价 / 缺点
  • 继承耦合：子类受限于父类骨架，骨架一变所有子类受影响。
  • 类的数量随变体增加而增长；Java 单继承限制使子类难以再继承其他类。
  • 模板方法步骤过多时，父类会变得臃肿、难以理解。

与相似模式的区别

维度模板方法策略
实现手段继承（父类定义骨架）组合（Context 持有 Strategy）
变化范围算法步骤的实现整个算法可替换
绑定时机编译期（继承关系固定）运行期（可动态切换）
控制方向父类调用子类（反向控制）Context 委托 Strategy
适用流程固定、细节可变算法多变、需要运行时切换

参考实现

易错点 · 把模板方法写成 public 且非 final，让子类随意覆盖。模板方法的全部价值在于固定算法骨架。如果子类可以覆盖它，执行顺序就能被随意改写，「骨架不变」的意图立刻失效。工程上应把 templateMethod() 声明为 final，只把 primitive 操作留成 abstract/protected。

命令模式 Command Pattern

行为型

意图：将一个请求封装为一个对象，从而使你可用不同的请求对客户进行参数化；对请求排队或记录请求日志，以及支持可撤销的操作。

动机 / 问题场景

课程用「文本编辑器的撤销/重做」举例：早期实现里，MenuItem（Copy/Paste）被点击时直接调用 Document 的方法，命令发出者与接收者硬编码耦合，而且没有任何数据结构保存「做过什么」，所以无法实现 Undo/Redo。改造后把每个操作封装成 CopyCommand、PasteCommand，MenuItem 只持有一个 Command 引用，命令对象可以入栈、可以记录日志，撤销就是弹出栈顶并调用 undo。

Invoker 只认识 Command 抽象，完全不知道 Receiver 是谁——这是请求发送者与接收者解耦的关键。

  • Command —— 声明执行操作的接口（execute，可选 undo/redo）。
  • ConcreteCommand —— 将一个接收者对象绑定于一个动作；调用接收者相应操作，实现 execute。
  • Invoker —— 要求该命令执行这个请求（如 MenuItem、按钮）。
  • Receiver —— 知道如何实施与执行一个请求相关的操作（如 Document）。
  • Client —— 创建一个具体命令对象并设定它的接收者。

协作要点

  1. Client 创建 ConcreteCommand，并指定它的 Receiver。
  2. Client 把该命令交给某个 Invoker 保存。
  3. Invoker 通过调用 Command 的 execute() 提交请求。
  4. ConcreteCommand 调用 Receiver 的一个或多个操作以执行请求。
  5. （可选）Invoker 把命令压入历史栈，撤销时调用 undo()。

适用场景

  • 系统需要将请求调用者与请求接收者解耦，使两者不直接交互。
  • 需要在不同时间指定请求、将请求排队和执行。
  • 需要支持命令的撤销（Undo）与恢复（Redo）。
  • 需要把一组操作组合起来，即支持宏命令。

优缺点

优点
  • 请求者不直接与接收者交互，彻底消除了彼此之间的耦合。
  • Command 对象可以像其他对象一样被操纵和扩展（入队、序列化、日志）。
  • 可以装配成复合命令（CompositeCommand），实现批量执行与批量撤销。
  • 满足开闭原则：新增 Command 无需修改已有类。
代价 / 缺点
  • 每个命令都要一个具体类，命令种类多时类数量膨胀。
  • 撤销需要 Receiver 配合保存足够的历史信息，实现成本不低。
  • 简单的一次性调用场景下属于过度设计。

与相似模式的区别

维度命令策略
关注点封装请求（做什么 + 谁来做）封装算法（怎么做）
是否持有接收者通常持有 Receiver 并调用其方法不持有接收者，只实现算法
典型用途排队、日志、撤销重做、宏命令运行时切换算法、消除条件分支

参考实现

易错点 · 撤销时按正序调用 undo，或忘记 undo 需要逆序。宏命令的 undo() 必须按与 execute 相反的顺序执行，否则依赖前序状态的命令会算错（例如先插入再删除的复合操作）。另外 undo 必须能判断「是否已执行过」，重复撤销会造成状态错乱。

解释器模式 Interpreter Pattern

行为型

意图：给定一个语言，定义它的文法的一种表示，并定义一个解释器，这个解释器使用该表示来解释语言中的句子。

动机 / 问题场景

当系统需要反复解释执行某种简单语言时（如正则表达式、SQL 的 WHERE 子句、业务规则表达式 age > 18 && city == "北京"），如果每遇到一种语法就写一段 if/else 解析，代码会迅速失控。解释器模式把文法规则映射成类：终结符（变量、常量）对应 TerminalExpression，非终结符（与、或、大于）对应 NonterminalExpression，整个表达式就变成一棵语法树，求值即递归遍历这棵树。

语法树：非终结符节点持有子表达式，interpret 递归下降求值；Context 提供全局变量。

  • AbstractExpression —— 声明一个抽象的解释操作 interpret(Context)，所有节点共用。
  • TerminalExpression —— 实现与文法中终结符相关的解释操作（如变量、常量）。
  • NonterminalExpression —— 实现文法中非终结符的解释操作，通常递归调用子表达式的 interpret。
  • Context —— 包含解释器之外的一些全局信息（如变量到值的映射）。
  • Client —— 构建语法树（通常由 Parser 完成），调用 interpret。

协作要点

  1. Client 按文法把句子解析成一棵 AbstractExpression 语法树。
  2. Client 创建 Context（保存变量等全局信息）。
  3. Client 调用根节点的 interpret(context)。
  4. 非终结符节点递归调用子节点的 interpret，终结符节点从 Context 取值。
  5. 结果逐层向上返回，得到整个句子的解释结果。

适用场景

  • 文法简单、句子结构可表示为抽象语法树。
  • 效率要求不高（解释执行通常比编译执行慢）。
  • 需要频繁扩展文法、或需要把规则与执行代码分离（如规则引擎、DSL）。

优缺点

优点
  • 易于改变和扩展文法：新增一种语法只需新增一个表达式类。
  • 实现文法较为容易（递归下降即可）。
  • 把语法规则与执行逻辑分离，规则可配置、可持久化。
代价 / 缺点
  • 文法复杂时类的数量急剧膨胀，每个规则一个类，系统难以维护。
  • 解释执行效率低，不适合复杂或高性能要求的语言。
  • 对大型语言来说，手写解释器不如用编译器生成工具（ANTLR 等）。

易错点 · 以为解释器模式适合实现复杂语言（如完整 SQL）。解释器的适用前提是文法简单。文法一复杂，规则类数量会指数级膨胀，而且解释执行效率很低。真正的语言实现应该用编译器/解析器生成工具，或者干脆用现成的表达式引擎。考试若问「解释器模式的缺点」，第一条就是「文法复杂时类数量爆炸、维护困难」。

迭代器模式 Iterator Pattern

行为型

意图：提供一种方法顺序访问一个聚合对象中的各个元素，而又不暴露该对象的内部表示。

动机 / 问题场景

课程指出集合对象天生承担两个职责：存储内部数据（根本属性）与遍历内部数据（既可变化、又可分离）。如果用 List 就暴露下标、用树就要暴露节点，客户端会被迫了解每种聚合的内部结构；而且「顺序遍历 / 逆序遍历 / 前中后序遍历」的实现混在聚合类里，聚合会越来越臃肿。迭代器把遍历职责抽出来，聚合只负责存储，遍历方式可以任意扩展。

结构

聚合负责创建迭代器，迭代器负责跟踪遍历位置——两个职责彻底分开。

  • Aggregate —— 定义创建相应迭代器对象的接口（createIterator）。
  • ConcreteAggregate —— 实现创建相应迭代器的接口，返回 ConcreteIterator 的实例。
  • Iterator —— 定义访问和遍历元素的接口（first / next / isDone / currentItem）。
  • ConcreteIterator —— 实现迭代器接口，遍历集合时跟踪当前位置。

协作要点

  1. Client 向 ConcreteAggregate 请求一个迭代器（createIterator()）。
  2. Client 用 first() 定位到第一个元素。
  3. 循环调用 isDone() 判断是否结束、currentItem() 取当前元素、next() 前进。
  4. 迭代器内部维护自己的游标，聚合的内部结构对 Client 完全不可见。

适用场景

  • 访问一个聚合对象的内容而无需暴露它的内部表示。
  • 支持对聚合对象的多种遍历（正序、逆序、过滤）。
  • 为遍历不同的聚合结构提供一个统一的接口（多态迭代）。

优缺点

优点
  • 支持以不同的方式遍历一个聚合，换一个迭代器实例即可。
  • 简化了聚合的接口：遍历接口从聚合移到迭代器，聚合职责更单一。
  • 同一个聚合上可以有多个遍历，每个迭代器保持自己的遍历状态。
  • Client 与聚合解耦，聚合内部数据结构变化不影响客户端。
代价 / 缺点
  • 对简单聚合（如数组）来说增加了一层间接，略有多余。
  • 迭代器与聚合需要保持同步：聚合在遍历过程中被修改，迭代器可能失效。
  • 多线程环境下迭代器通常不是线程安全的。

与相似模式的区别

维度迭代器访问者
目的顺序遍历元素对元素施加新操作
是否修改元素不修改，只读访问可读可写，可累积结果
扩展方向新增遍历方式新增操作

中介者模式 Mediator Pattern

行为型

意图：用一个中介对象来封装一系列的对象交互。中介者使各对象不需要显式地相互引用，从而使其耦合松散，而且可以独立地改变它们之间的交互。

动机 / 问题场景

课程用「企业管理系统」举例：采购、销售、库存、物流、供应商、资产六个模块互相调用，任意一个模块变动都要跟踪所有关联模块，形成一张网状依赖图。引入中介者后，网状变成星形：每个模块只跟中介者通信，模块之间不再有直接引用。另一个经典例子是网络拓扑：五台计算机两两直连需要 10 条链路，接一台交换机后只需 5 条。对话框（登录/注册切换）也是中介者的典型应用。

结构

网状（n×(n-1)/2 条关系）变成星形（n 条关系）：交互复杂性集中到中介者一处。

  • Mediator —— 定义与各同事（Colleague）对象通信的接口。
  • ConcreteMediator —— 通过协调各同事对象实现协作行为；了解并维护它的各个同事。
  • Colleague —— 维护一个中介者对象的引用；每个同事在需要与其他同事通信时，与中介者通信。

协作要点

  1. 同事对象状态变化时，调用 mediator.notify(this, event) 上报。
  2. 中介者收到通知后，根据发送者与事件类型决定如何处理。
  3. 中介者调用其他相关同事的方法，完成协调。
  4. 同事之间全程没有直接引用，交互逻辑集中在中介者一处。

适用场景

  • 一组对象以定义良好但复杂的方式进行通信，产生的相互依赖结构混乱且难以理解。
  • 一个对象引用很多对象并直接通信，导致难以复用该对象。
  • 想定制一个分布在多个类中的行为，而又不想生成太多子类。

优缺点

优点
  • 减少了子类生成：把分散在多个对象间的行为集中到中介者，改变行为只需生成中介者子类。
  • 各 Colleague 松耦合，可以独立改变和复用。
  • 简化对象间关联：用一对多交互替代多对多交互，更易理解、维护和扩展。
  • 封装变化：交互关系的变化只影响中介者代码，同事类无需修改。
代价 / 缺点
  • 控制集中化：交互的复杂性变成中介者的复杂性，中介者可能膨胀成难以维护的巨型对象。
  • 中介者需要和每个 Colleague 交互，与系统耦合度较大，难以在系统间复用。
  • 中介者只应处理对象间交互，不应承担本可由同事独立完成的工作。

与相似模式的区别

易错点 · 把中介者写成「什么都管」的上帝类。中介者的职责边界是只协调对象间的交互，不负责同事能独立完成的工作。教材明确指出「中介者只处理对象间交互，不负责对象能独立处理的部分」，并且点出它的缺点：控制集中化会让中介者变成难于维护的庞大对象，而且因为与每个同事都耦合，难以在系统间复用。

备忘录模式 Memento Pattern

行为型

意图：在不破坏封装性的前提下，捕获一个对象的内部状态，并在该对象之外保存这个状态，以便以后可以将该对象恢复到原先保存的状态。

动机 / 问题场景

课程在讲命令模式时已经埋了伏笔：命令对象要支持 Undo，就必须有地方保存「执行前的状态」，而直接暴露对象的内部字段会破坏封装。备忘录模式给出三方分工：Originator（发起人，自己负责生成和恢复快照）、Memento（备忘录，只存状态、对外不透明）、Caretaker（管理者，只负责保存/取出快照，绝不修改内容）。编辑器的撤销栈、游戏的存档点、数据库事务回滚都是这个结构。

结构

Caretaker只保存 Memento，不读内容

Originator 创建并读取 Memento；Caretaker 只搬运

关键约束：Memento 的状态对 Caretaker 不可见（宽接口给 Originator，窄接口给其他人）。

  • Originator —— 发起人：创建一个备忘录以记录当前内部状态；使用备忘录恢复内部状态。
  • Memento —— 备忘录：存储 Originator 的内部状态；防止 Originator 以外的对象访问它。
  • Caretaker —— 管理者：负责保存备忘录；不能对备忘录的内容进行操作或检查。

协作要点

  1. Client 需要保存状态时，向 Originator 请求一个 Memento。
  2. Originator 创建 Memento，把自己的内部状态快照进去。
  3. Client（或 Caretaker）把 Memento 保存起来（压栈、存文件）。
  4. 需要恢复时，把 Memento 交回 Originator，调用 restore(memento)。
  5. Originator 从 Memento 中取回状态，自身恢复。

适用场景

  • 必须保存一个对象在某一个时刻的（部分）状态，以便之后恢复。
  • 如果一个用接口来让其他对象直接得到这些状态，将会暴露实现细节并破坏封装。
  • 需要撤销/回滚、事务、存档点功能。

优缺点

优点
  • 保持封装的边界：状态的保存与恢复由 Originator 自己完成。
  • 简化了 Originator：把状态管理职责交给 Caretaker，Originator 专注业务。
  • 提供了可靠的恢复机制，是实现 Undo/Redo、事务回滚的基础。
代价 / 缺点
  • 保存大量快照会占用大量内存（需要配合「只存增量」或限制历史长度）。
  • Caretaker 需要负责快照的生命周期管理，否则容易内存泄漏。
  • 若状态包含大对象或外部资源句柄，快照的实现会更复杂。

与相似模式的区别

维度备忘录原型
目的保存/恢复对象状态通过拷贝创建新对象
是否产生新对象产生快照对象（不参与业务）产生可用的新业务对象
关注点状态的历史创建的成本
典型场景撤销栈、存档、事务回滚复制粘贴、缓存对象模板

参考实现

易错点 · 让 Caretaker 直接读写 Memento 里的状态字段。备忘录模式的核心约束是封装：Memento 对外应是窄接口（Caretaker 只能整体保存/传递，不能读取内容），只有 Originator 能用宽接口读写状态。如果 Caretaker 能随意修改快照内容，封装被破坏，「不破坏封装性地保存状态」这一意图就不成立了。

观察者模式 Observer Pattern

行为型

意图：定义对象间的一种一对多的依赖关系，当一个对象的状态发生改变时，所有依赖于它的对象都得到通知并被自动更新。

动机 / 问题场景

课程从「用户界面与业务逻辑分离」讲起：GUI 出现后，几乎所有面向对象框架都支持把界面从应用其他部分划分出来。但分割成相互协作的类也带来新问题——需要维护相关对象间的一致性，而为维持一致性又会让各类紧密耦合、降低可重用性。观察者模式解决这个矛盾：Subject 只知道「有一批 Observer 关心我」，不知道它们是谁、会做什么；新增视图无需修改 Model。Java 的 ActionListener、MVC 的 Model-View 刷新都是这个结构。

结构

Subject+ attach(o) / detach(o)
+ notify()
继承

+ getState() / setState()
notify() 遍历 observers 逐个 update

继承
ConcreteObserver- observerState
+ update()

一对多：Subject 持有 Observer 列表；状态变化时遍历调用 update，完成广播。

  • Subject —— 抽象主题：提供注册（attach）和删除（detach）观察者对象的接口。
  • ConcreteSubject —— 具体主题：状态变化时向各个观察者发出通知。
  • Observer —— 抽象观察者：为希望在主题变化时获得通知的对象定义一个更新接口。
  • ConcreteObserver —— 具体观察者：维护指向具体主题的引用，实现 update 使自身状态与主题一致。

协作要点

  1. 观察者调用 subject.attach(this) 注册自己。
  2. 主题内部状态改变（setState）。
  3. 主题调用 notify()，遍历观察者列表。
  4. 对每个观察者调用 update()（推模型带数据，拉模型只发通知）。
  5. 观察者更新自身状态，必要时回查主题获取最新数据；不再需要时 detach。

适用场景

  • 当一个抽象模型有两个方面，其中一个方面依赖于另一个方面，将二者封装在独立对象中使它们可以独立改变和复用。
  • 一个对象的改变需要同时改变其他对象，但不知道具体有多少对象有待改变。
  • 一个对象必须通知其他对象，但又不能假定其他对象是谁（不希望紧密耦合）。

优缺点

优点
  • Subject 与 Observer 之间松耦合，可以各自独立改变。
  • 广播通信时 Subject 无须指定具体 Observer，Observer 可自行决定是否订阅。
  • 符合开闭原则：新增观察者无需修改主题代码。
  • 高内聚、低耦合。
代价 / 缺点
  • 松耦合导致代码关系不明显，有时难以理解（通知是隐式的）。
  • 一个 Subject 被大量订阅时，广播通知可能有效率问题。
  • 忘记 detach 会造成内存泄漏；通知顺序不确定，链式更新难调试。

与相似模式的区别

维度观察者发布-订阅中介者
耦合方式主题知道观察者接口双方互不相识，经事件通道同事只认识中介者
拓扑一对多多对多星形
通知方向单向广播双向集中转发
层级设计模式（对象级）架构风格 / 集成模式设计模式（对象级）

参考实现

易错点 · 在 notify 里直接遍历观察者原列表。如果某个观察者在 update() 中调用 attach/detach，遍历原列表会抛 ConcurrentModificationException。必须先复制一份列表再遍历（如 new ArrayList<>(observers)）。另外注意：观察者模式中 Subject 直接持有 Observer 引用，一旦引入事件通道就演进为发布-订阅，属于架构层解耦，不能再叫观察者模式。

状态模式 State Pattern

行为型

意图：允许一个对象在其内部状态改变时改变它的行为。对象看起来似乎修改了它的类。

动机 / 问题场景

课程用「人有多种状态」举例：开心时唱歌、请客，失恋时撞墙，中奖时疯狂购物——同一个对象在不同状态下对同一事件有完全不同的反应。如果用一个类实现，代码会变成巨大的 switch (state)：每加一个状态就要改所有方法，每加一个方法就要改所有分支。状态模式把每个状态抽成一个类，Context 持有当前状态对象，把请求委托给它，状态类自己决定是否以及如何转移到下一个状态。TCP 连接（建立/监听/关闭）是最经典的例子。

结构

+ request()
request() 委托给 state.handle()；state 可回写 context 切换状态
State+ handle()
继承
ConcreteStateA+ handle()ConcreteStateB+ handle()

与策略模式类图几乎一样，区别在于：状态类知道其他状态并负责转移，策略之间互不相识。

  • Context —— 定义客户感兴趣的接口；维护一个 ConcreteState 子类实例，该实例定义当前状态。
  • State —— 定义一个接口，封装与 Context 的一个特定状态相关的行为。
  • ConcreteState —— 每一个子类实现一个与 Context 的一个状态相关的行为，并可触发状态转移。

协作要点

  1. Client 调用 Context 的 request()。
  2. Context 把请求委托给当前 state 对象的 handle()。
  3. ConcreteState 根据自身逻辑处理请求。
  4. 若满足转移条件，ConcreteState 调用 context.setState(newState) 切换状态。
  5. 后续请求由新的状态对象处理——客户无须知道切换逻辑。

适用场景

  • 一个对象的行为取决于它的状态，并且它必须在运行时根据状态改变行为。
  • 一个操作中含有庞大的多分支条件语句，且这些分支依赖于对象的状态。
  • 状态数量有限且状态转移规则明确（状态机场景）。

优缺点

优点
  • 将与状态相关的行为局部化，把状态的切换逻辑放到 State 派生类中。
  • 动作完成后可以自动切换到下一个状态，客户无须知道具体切换逻辑。
  • 消除庞大的条件分支语句，符合开闭原则（新增状态只需新增类）。
  • 实现逻辑与动作解耦：每个 ConcreteState 只需知道本状态可能过渡到哪些状态及条件。
代价 / 缺点
  • 状态类数量增加，类的层次变复杂。
  • 状态转移逻辑分散在各状态类中，整体状态机流程不易一眼看清（需要看全所有类）。
  • 若状态很多且转移规则频繁变化，维护成本会上升。

与相似模式的区别

维度状态策略
类图几乎一致（Context 持有抽象 + 子类实现）几乎一致
目的对象行为随内部状态改变而改变让算法可相互替换
状态/策略是否知道彼此ConcreteState 知道其他状态并负责转移ConcreteStrategy 互不相识
谁决定切换状态类自己（内部触发）客户端（外部注入）
典型场景TCP 连接、订单状态机、电梯排序算法、折扣策略、压缩算法

参考实现

易错点 · 认为状态模式和策略模式可以互换，因为类图一样。类图确实几乎相同，但意图与切换机制不同：状态模式中 ConcreteState 知道其他状态、由状态类自己触发转移，行为随内部状态改变而改变；策略模式中 ConcreteStrategy 互不相识，由客户端选择注入，算法之间是平等可替换关系。答题时必须点出「谁负责切换」这一条。

策略模式 Strategy Pattern

行为型

意图：定义一系列算法，把它们一个个封装起来，并且使它们可相互替换。本模式使得算法可独立于使用它的客户而变化。

动机 / 问题场景

课程用「点坐标数组排序」举例：可以按 X 坐标排、按 Y 坐标排、按到原点距离排。最初的做法是在 PointArray 里写 SortA/SortB/SortC 三个方法，再用条件语句选择——算法被硬编码进使用它的类，类变得复杂难维护。策略模式把每个算法抽成独立的 ConcreteStrategy 类，Context 只持有一个 Strategy 引用，运行时想换就换。图书折扣的例子同理：不打折、固定减 1 元、打 85 折，三种策略可自由切换。

结构

+ contextInterface()
contextInterface() 委托给 strategy.algorithmInterface()
Strategy+ algorithmInterface()
实现

Context 依赖 Strategy 抽象（依赖倒置），具体算法在运行期注入，可自由替换。

  • Strategy —— 定义所有支持的算法的公共接口；Context 使用这个接口调用某个 ConcreteStrategy 定义的算法。
  • ConcreteStrategy —— 以 Strategy 接口实现某具体算法。
  • Context —— 用一个 ConcreteStrategy 对象来配置；维护一个对 Strategy 对象的引用；可定义接口让 Strategy 访问它的数据。

协作要点

  1. Client 创建某个 ConcreteStrategy 对象。
  2. Client 把它注入 Context（构造参数或 setter）。
  3. Client 调用 Context 的业务方法。
  4. Context 把算法相关的部分委托给 strategy.algorithmInterface()。
  5. 需要换算法时，Client 注入另一个 ConcreteStrategy 即可，Context 代码不变。

适用场景

  • 许多相关的类仅仅是行为有异：「策略」提供了一种用多个行为中的一个来配置一个类的方法。
  • 需要使用一个算法的不同变体。
  • 算法使用了客户端不应知道的数据，用以避免暴露复杂的、与算法相关的数据结构。
  • 一个类定义了多种行为，且这些行为在操作中以多个条件语句的形式出现——用策略代替条件语句。

优缺点

优点
  • 相关算法系列：Strategy 类层次为 Context 定义了一系列可供重用的算法。
  • 替代继承：算法与使用算法的对象分离，客户可在运行时动态选择算法。
  • 消除条件语句：把行为封装在独立类中，消除 if/else 或 switch。
  • 易于切换、易于理解、易于扩展。
代价 / 缺点
  • Client 必须知道多个不同策略，才能选择合适的那个（选择逻辑没有消失，只是转移了）。
  • 策略类数量增加，小程序里可能显得啰嗦。
  • 与常规环境类实现相比，Context 与 Strategy 之间的信息流费用偏高（多一层调用）。

与相似模式的区别

维度策略状态模板方法命令
实现手段组合组合继承组合
变化对象整个算法行为随状态变算法的某些步骤整个请求
切换者客户端状态类自身编译期确定（子类）Invoker / 客户端
是否持有接收者否否（持有 Context 引用）—通常持有 Receiver
典型场景折扣、排序、压缩状态机、TCP框架流程骨架撤销、队列、日志

参考实现

易错点 · 认为用了策略模式，客户端就完全不需要知道具体算法。策略模式消除的是 Context 内部的条件语句，但选择哪个策略的责任转移到了客户端。教材明确指出这是它的缺点之一：「Client 必须知道多个不同策略，以便配置」。要真正做到客户端无感，需要再配一个简单工厂或配置表来隐藏选择逻辑。

责任链模式 Chain of Responsibility Pattern

行为型

意图：使多个对象都有机会处理请求，从而避免请求的发送者与接收者之间的耦合关系。将这些对象连成一条链，并沿着这条链传递该请求，直到有一个对象处理它为止。

动机 / 问题场景

课程用「员工请假」举例：经理能批 2 天以内，超过就上报总监；总监能批 5 天以内，再超过就上报总经理；加薪只有总经理有权处理。如果写成一个大 if/else if 判断 ManagerLevel，每调整一次权限就要改这段代码。责任链把每个处理者抽成一个类，每个处理者持有后继者引用，能处理就处理，不能处理就 next() 传下去。课程还给了「击鼓传花」的例子：PlayerA/B/C/D 连成链，鼓声停下时持有花的人执行动作。

结构

责任链可以是直线、环或树形；最常见的是直线型。链的组装在客户端完成，因此顺序可在运行时改变。

每个处理者只知道自己的后继者，不知道整条链的结构——这是解耦的关键。

  • Handler —— 声明一个处理请求的接口，并实现后继链（持有 successor 引用、提供 setSuccessor）。
  • ConcreteHandler —— 实现抽象处理者声明的接口：能处理就处理，否则把请求转发给它的后继者。
  • Client —— 向链上的具体处理者对象提交请求（通常是链首）。

协作要点

  1. Client 创建各个 ConcreteHandler，并调用 setSuccessor 把它们连成链。
  2. Client 向链首提交请求。
  3. 链首判断自己能否处理：能则处理并结束；不能则调用 successor.handleRequest()。
  4. 请求沿链向下传递，直到有处理者接手，或到达链尾（无人处理）。

适用场景

  • 有多个对象可以处理一个请求，具体哪个对象处理在运行时自动确定。
  • 处理请求的对象集合与顺序由客户端根据当前应用状态在运行时动态决定。
  • 一个处理者可以根据应用状态和请求类型，把请求传递给不同的处理者。
  • 客户与处理链中的对象都不需要知道到底用哪个对象处理请求。

优缺点

优点
  • 降低耦合度：请求发送者无需知道请求会被哪个对象处理，链中对象也无需知道链的结构。
  • 增强给对象分配职责的灵活性：可在运行时动态增加或修改责任链。
  • 符合开闭原则：新增处理者只需新增类并重新组装链。
代价 / 缺点
  • 不保证被接受：请求可能到达链尾仍无人处理（需要兜底处理者）。
  • 链过长时性能下降；消息传递不当可能出现循环重复执行。
  • 调试时请求路径不直观，难以追踪到底是谁处理的。

与相似模式的区别

维度责任链装饰器命令
链的结构处理者可选择是否继续传递装饰器必定转发给内层不涉及链
目的找到能处理请求的对象动态增加职责封装请求
是否都执行通常只有一个处理者执行每一层都执行（前后加动作）由 Invoker 决定
后继者可动态设置、可为空固定为被包装对象—

参考实现

易错点 · 认为请求一定会被处理。GoF 明确指出责任链的一个效果是「不保证被接受」：请求可能一直传到链尾都没有处理者接手。工程上必须提供兜底处理者（DefaultHandler）或在链尾打印告警。另外注意链可以组成环，若不慎形成环，请求会无限循环——这也是教材提到的「消息的循环重复执行」风险。

访问者模式 Visitor Pattern

行为型

意图：表示一个作用于某对象结构中的各元素的操作。它使你可以在不改变各元素的类的前提下定义作用于这些元素的新操作。

动机 / 问题场景

课程用「计算机硬件」举例：Hardware 有 CPU 和 Harddisk 两个子类。现在要加一个「显示型号」的功能，明天要加「显示运行状态」，后天要加「统计功耗」——每加一个功能就要改所有元素类，元素类会被各种不相关的操作「污染」。访问者模式把操作抽成 Visitor 层次：元素类只需实现一个 accept(visitor)，新功能就是新增一个 ConcreteVisitor。课程还给了 ITest1/ITest2 的例子，说明没有访问者时客户端只能写 if (x is ITest1) ... else if (x is ITest2)。

accept 里回调 visitor 的对应方法，形成「双重分派」——元素类型与访问者类型共同决定执行哪个操作。

  • Visitor —— 为对象结构中的每一个 ConcreteElement 类声明一个 visit 操作。
  • ConcreteVisitor —— 实现 Visitor 接口的操作，每个操作实现算法的一部分。
  • Element —— 定义一个 accept 操作，它以一个访问者为参数。
  • ConcreteElement —— 实现 Element 的 accept 操作（通常是 visitor.visitXxx(this)）。
  • ObjectStructure —— 能枚举元素；可提供高层接口允许访问者访问其元素；可以是 Composite 或集合。

协作要点

  1. Client 创建一个 ConcreteVisitor 对象。
  2. Client 遍历 ObjectStructure，对每个元素调用 accept(visitor)。
  3. ConcreteElement 的 accept 调用 visitor.visitXxx(this)（第一次分派：元素类型）。
  4. 进入 ConcreteVisitor 的对应方法（第二次分派：访问者类型），执行具体操作。
  5. 访问者可沿途累积结果，最后返回给 Client。

适用场景

  • 一个对象结构包含很多类对象，它们有不同的接口，而你想对这些对象实施一些依赖于其具体类的操作。
  • 需要对一个对象结构中的对象进行很多不同的并且不相关的操作，而你想避免让这些操作「污染」这些对象的类。
  • 当该对象结构被很多应用共享时，用 Visitor 模式让每个应用仅包含需要用到的操作。
  • 定义对象结构的类很少改变，但经常需要在此结构上定义新的操作。

优缺点

优点
  • 不修改具体元素类就可以增加新操作（通过元素的 accept 接受一个 visitor 对象实现）。
  • 把相关的操作集中到一个 ConcreteVisitor 中，元素类保持纯粹。
  • 可以跨元素累积状态（如统计总和），这在逐个元素的普通方法里很难做到。
代价 / 缺点
  • 不易频繁增加元素类：每增加一个元素类，就要在 Visitor 接口中增加一个方法，并修改所有 Visitor 子类——开闭原则反向倾斜。
  • 破坏封装：访问者为了操作元素，往往需要元素暴露足够的内部信息。
  • 元素类层次必须相对稳定，否则维护成本极高。

核心机制双重分派（accept + visit）游标跟踪位置递归组合
典型场景编译器 AST、报表导出、静态分析集合遍历文件系统、UI 容器

参考实现

易错点 · 认为访问者模式符合开闭原则，可以随意扩展。它的开闭原则是单向的：增加新操作容易（新增一个 ConcreteVisitor），但增加新元素类很难（要在 Visitor 接口加方法，并修改所有 Visitor 子类）。课程原话：「每当被访问对象接口变化时，我们不得不修改这个访问接口，这违反了面向对象的开-闭原则」。所以适用前提是「元素类结构稳定、操作经常变化」，答反了等于没答。

答题技巧行为型模式的简答题有固定套路：先写意图（GoF 原话），再写解决什么耦合，然后写结构角色，最后写代价。如果题干问「区别」，务必答到「谁负责切换 / 谁持有谁 / 是否知道彼此」这一层，只答「类图一样」是拿不到分的。

易错点

#

行为型是最容易「看起来都懂、一考就错」的部分。以下六条都是真实失分点。

  • 把策略模式和状态模式当成同一个模式。类图确实几乎一致，但意图与切换机制完全不同：策略由客户端注入、策略之间互不相识、目的是算法可替换；状态由状态类自己触发转移、状态之间知道彼此、目的是行为随状态改变。答「类图一样所以一样」是最典型的失分。
  • 说访问者模式完全符合开闭原则。它的开闭是单向的：加新操作容易（新增 ConcreteVisitor），加新元素类很难（要改 Visitor 接口及所有子类）。课程明确说「每当被访问对象接口变化时，不得不修改访问接口，这违反了开-闭原则」。适用前提必须写成「元素结构稳定、操作经常变化」。
  • 把模板方法写成可被子类覆盖的 public 方法。模板方法的全部价值在于固定算法骨架。若子类能覆盖它，执行顺序就能被改写，「骨架不变」的意图失效。应声明为 final，只把原语操作留成抽象方法。
  • 责任链默认请求一定有人处理。GoF 明确「不保证被接受」。请求可能一路传到链尾无人处理，必须提供兜底处理者。另外链若成环会导致无限循环，这也是教材点出的风险。
  • 观察者 notify 时直接遍历原列表。观察者可能在 update() 中调用 attach/detach，直接遍历原列表会抛 ConcurrentModificationException。必须先复制列表再遍历。另外忘记 detach 会造成内存泄漏。
  • 认为迭代器模式就是「给聚合加一个 getAt(i)」。迭代器的判据是遍历状态被封装进独立的迭代器对象，聚合只提供 createIterator()。如果客户端仍自己控制下标访问 getAt(i)，既暴露了内部表示，也无法支持同一聚合上的多个并发遍历。
