结构型模式：用「组合」而不是「继承」搭出更大的结构

结构型模式关心如何把类或对象组合成更大的结构，就像用积木搭出复杂形状。七个模式共用一条主线：把「继承」这种编译期强耦合，换成「组合/聚合」这种运行期弱关联，从而让抽象与实现、对象与子系统、整体与部分都能独立变化。

学习目标

读完这一页，应当能独立完成下列动作。

  1. 能说出「类结构型模式」与「对象结构型模式」的划分依据，并指出只有适配器有类/对象两种形态。
  2. 能画出适配器、装饰器、代理三者的类图并说清它们「都包一层」却意图完全不同。
  3. 能解释桥接模式为什么能把 m×n 个子类降成 m+n 个，并说清「脱耦」的含义。
  4. 能区分组合模式（树）与装饰器模式（链）在结构上的异同。
  5. 能在给定场景（旧接口改造、动态加功能、远程访问、大量小对象）中选出正确的结构型模式。

知识地图

七个模式可以按「解决什么问题」归成四组，记组比记单个更容易。

问题

  • 接口不兼容，不能一起工作
  • 抽象与实现被继承绑死
  • 动态加功能，不想改类
  • 对象太多、访问太远、太复杂

角色

  • 适配器：Target / Adaptee
  • 桥接：Abstraction / Implementor
  • 组合：Component / Leaf / Composite
  • 装饰器·代理：与主体同接口

协作

  • 转换接口后转发请求
  • 抽象持有实现引用
  • 递归处理子节点
  • 包一层，转发前后加动作

代价

  • 多一层间接，调试变难
  • 类数量增加
  • 小对象多、理解成本高
  • 某些模式牺牲了透明性
02

核心概念与模式卡

#

结构型模式的分类轴有两条：按「目的」（类/对象）和按「手段」（继承/组合）。先分清这两条，七个模式的位置就不会错。

结构型模式 Structural Patterns

处理类或对象的组合，把简单结构拼成更大的结构。目标是让系统在扩展时不必改动已有结构，即用组合替代继承。

总览GoF 三大类之一

类结构型模式 Class Structural

通过继承组合类，一般只存在继承与实现关系。七种里只有类适配器属于这一类，其余都是对象结构型。

分类易错

对象结构型模式 Object Structural

通过关联/聚合在一个类里持有另一个类的实例，再委托它完成任务。依据合成复用原则，大部分结构型模式都是这一类。

分类合成复用

合成复用原则 Composition over Inheritance

优先使用组合/聚合而不是继承。继承是「白箱复用」，父类细节对子类可见、编译期绑定；组合是「黑箱复用」，只依赖接口、运行期可替换。

原则核心思想

脱耦 Decoupling

桥接模式的核心术语：把抽象与实现之间的继承（强关联）改为聚合（弱关联）。强关联编译期确定、不可动态改变；弱关联运行期可替换。

桥接术语

透明性 vs 安全性 Transparency vs Safety

组合模式的经典权衡：把 add/remove 提到 Component 里叫透明（叶子节点调用会抛异常），放在 Composite 里叫安全（但失去一致性接口）。

组合易混淆

内部状态 vs 外部状态 Intrinsic / Extrinsic

享元模式的关键：内部状态存在享元对象里、与场景无关、可共享；外部状态随场景变化、由客户端保存并在调用时传入、不可共享。

享元核心概念

包装器 Wrapper

适配器与装饰器的共同别名。两者都「包一层」，但适配器改接口不改功能，装饰器不改接口只加功能——这是最常考的一句辨析。

辨析高频

七个模式卡（速览）

先记住每个模式的「一句话意图 + 一句话代价」，下一节再逐个展开结构。

适配器模式

Adapter Pattern 结构型
意图
将一个类的接口转换成客户希望的另一个接口，使原本接口不兼容的类可以一起工作。
别名
包装器（Wrapper）
适用场景
要复用已有类但其接口不符；想创建一个可与不相关/不可预见类协同工作的可复用类。
参与角色
Target、Adaptee、Adapter、Client
主要代价
类适配器受单继承限制；对象适配器多一层转发，实现较复杂。

桥接模式

Bridge Pattern 结构型
意图
将抽象部分与它的实现部分分离，使它们都可以独立地变化。
别名
Handle / Body（柄体模式）
适用场景
不希望在抽象与实现间有固定绑定；两者都需通过子类扩展；实现细节要对客户透明。
参与角色
Abstraction、RefinedAbstraction、Implementor、ConcreteImplementor
主要代价
要求设计之初就能正确识别出两个变化维度，识别错反而增加复杂度。

组合模式

Composite Pattern 结构型
意图
将对象组合成树形结构表示「部分-整体」层次，使客户端对单个对象和组合对象的使用具有一致性。
别名
合成模式、部分-整体模式
适用场景
想表示对象的部分-整体层次结构；希望忽略组合对象与单个对象的不同，统一使用。
参与角色
Component、Leaf、Composite、Client
主要代价
过度泛化的接口让设计过于抽象；叶子节点可能被迫实现无意义的 add/remove。

装饰器模式

Decorator Pattern 结构型
意图
动态地给一个对象添加一些额外的职责。就增加功能而言，比生成子类更灵活。
别名
包装器（Wrapper）
适用场景
不影响其他对象的前提下动态、透明地给单个对象加职责；职责可撤销；子类扩展会爆炸时。
参与角色
Component、ConcreteComponent、Decorator、ConcreteDecorator
主要代价
产生许多小对象，学习与调试困难；使用装饰时不应依赖对象标识。

外观模式

Facade Pattern 结构型
意图
为子系统中的一组接口提供一个统一的高层接口，使子系统更容易使用。
别名
门面模式
适用场景
为复杂子系统提供简单入口；解除客户与子系统内部实现的依赖；为分层结构定义每层入口。
参与角色
Facade、Subsystem classes、Client
主要代价
增加一层间接调用；子系统的功能被门面限制；子系统接口变化会波及门面。

包装器家族对照

Wrapper Family 结构型
意图
把适配器、装饰器、代理三个「都包一层」的模式放在一起对照，避免在类图题里互相冒充。
别名
三兄弟（Adapter / Decorator / Proxy）
适用场景
题干出现「包装」「转发」「增强」「控制访问」等模糊措辞时，用本卡逐项排除。
参与角色
三者结构均为「实现/继承同一抽象 + 持有一个真实对象 + 转发请求」。
主要代价
只看类图无法区分，必须结合意图判断：改接口 / 加功能 / 控访问。

享元模式

Flyweight Pattern 结构型
意图
运用共享技术有效地支持大量细粒度的对象。
别名
轻量级模式
适用场景
系统中有大量相似对象、耗费大量内存；对象外部状态接近而内部状态与环境无关；需要缓冲池。
参与角色
Flyweight、ConcreteFlyweight、UnsharedConcreteFlyweight、FlyweightFactory
主要代价
把状态拆成内/外部，增加实现复杂度；以时间换空间，查找有额外开销。

代理模式

Proxy Pattern 结构型
意图
为其他对象提供一种代理以控制对这个对象的访问。
别名
Surrogate（替身）
适用场景
远程代理、虚拟代理、保护代理、智能引用代理（缓存、计数、加锁）。
参与角色
Subject、RealSubject、Proxy、Client
主要代价
请求多经过一层，响应可能变慢；某些代理（如远程）引入网络异常处理复杂度。

01

适配器模式 Adapter Pattern

结构型

意图：将一个类的接口转换成客户希望的另一个接口。适配器让原本因接口不兼容而无法一起工作的类可以协同工作。

动机 / 问题场景

课程用一个很形象的类比：团队要对外提供 S 类服务，但团队里没人会做，只有团队外的 A 会。要么把 A 招安进来（类适配器：继承 A 同时实现 S 接口），要么派 B 去对接、B 干活时向 A 请教（对象适配器：B 实现 S 接口，内部持有一个 A）。现实中的例子是电源转接头：插座是两孔，电器是三角插头，转接头不改变电的本质，只改变接口形状。

结构

Client只认 Target 接口
调用 request()
Target+ request()
Adapter 实现 Target，同时持有/继承 Adaptee
Adapter+ request()
→ 转调 specificRequest()
转发
Adaptee+ specificRequest()

适配器不新增功能，只做「接口翻译」：把 request() 的调用翻译成 specificRequest()。

  • Target —— 定义 Client 使用的、与特定领域相关的接口。
  • Adaptee —— 已存在的、需要被适配的接口（接口与 Target 不兼容）。
  • Adapter —— 负责把 Adaptee 的接口适配成 Target 接口。
  • Client —— 与符合 Target 接口的对象协同工作，不知道 Adaptee 的存在。

协作要点

  1. Client 针对 Target 接口编程，调用 request()。
  2. 实际执行的是 Adapter 的 request() 实现。
  3. Adapter 内部把调用转发给 Adaptee 的 specificRequest()（可能做参数转换）。
  4. Adaptee 完成真正的业务，结果原路返回，Client 全程不知道 Adaptee。

适用场景

  • 想使用一个已存在的类，但它的接口不符合要求。
  • 想创建一个可以复用的类，该类能与接口不一定兼容的其他类协同工作。
  • 想使用一些已存在的子类，但无法通过子类化匹配接口——此时用对象适配器适配其父类接口。

优缺点

优点
  • 将目标类与适配者类解耦，增加了类的透明性与复用性。
  • 灵活性和扩展性好：换一个适配者只需换一个适配器。
  • 对象适配器可以同时适配一个类的所有子类，比类适配器更灵活。
代价 / 缺点
  • 类适配器采用继承，属于静态结构，且受 Java 单继承限制（只能适配一个类）。
  • 对象适配器实现过程较复杂，需要额外的转发代码。
  • 多了一层间接调用，调试时调用链变长。

与相似模式的区别

维度类适配器对象适配器装饰器
实现手段继承 Adaptee + 实现 Target持有 Adaptee 引用 + 实现 Target继承/实现 Component
接口改变接口改变接口不改变接口
功能不改变功能不改变功能增强功能
适配范围只能适配一个具体类可适配该类及其所有子类装饰同接口的任意实现
耦合程度高（编译期绑定）低（运行期可替换）低

参考实现

易错点 · 把适配器和装饰器混为一谈，只说「都是包装」。两者的关键差别是接口是否改变：适配器把 Adaptee 的接口转换成 Target，Client 看到的是全新的方法名；装饰器保持 Component 接口不变，只是在转发前后加动作，因此可以层层嵌套且对客户完全透明。口诀：适配器改接口不改功能，装饰器加功能不改接口。

02

桥接模式 Bridge Pattern

结构型

意图：将抽象部分与它的实现部分分离，使它们都可以独立地变化。

动机 / 问题场景

课程用「同一模块跨平台使用」举例：模块 A 和 B 要同时跑在 X、Y 两个操作系统上。用继承的做法是 A-X、A-Y、B-X、B-Y 四个类；每加一个模块或一个平台，类数量按 m×n 爆炸。桥接的做法是：把「平台」抽象成 Implementor 层次，把「模块」抽象成 Abstraction 层次，Abstraction 持有一个 Implementor 引用，于是 m 个模块 + n 个平台 = m+n 个类。窗口与窗口实现的例子同理。

结构

Abstraction+ operation()
持有 implementor
继承
RefinedAbstraction+ operation()
operation() 委托给 implementor.operationImpl()
Implementor+ operationImpl()
继承
ConcreteImplementorAConcreteImplementorB

两个独立的继承层次，中间用一条「聚合」的桥连接——这就是「桥接」名字的由来。

  • Abstraction —— 定义抽象类的接口，并维护一个指向 Implementor 类型对象的引用。
  • RefinedAbstraction —— 扩充由 Abstraction 定义的接口（模块侧的扩展）。
  • Implementor —— 定义实现类的接口，不一定要与 Abstraction 的接口一致，甚至可以完全不同。
  • ConcreteImplementor —— 实现 Implementor 接口并定义它的具体实现（平台侧的扩展）。

协作要点

  1. Client 创建某个 ConcreteImplementor，把它注入给 RefinedAbstraction。
  2. Client 调用 Abstraction 的 operation()。
  3. operation() 内部把请求委托给持有的 implementor。
  4. ConcreteImplementor 完成平台相关的实现细节。
  5. 运行期可以替换 implementor，即动态改变实现。

适用场景

  • 不希望在抽象和它的实现部分之间有一个固定的绑定关系。
  • 类的抽象以及它的实现都应该可以通过生成子类的方法加以扩充。
  • 实现部分的修改应对客户不产生影响，即实现细节要对客户透明。
  • 想对客户完全隐藏抽象的实现部分。

优缺点

优点
  • 分离接口及其实现部分：实现可以在运行时刻配置，甚至动态替换。
  • 提高可扩充性：抽象与实现两个维度可以独立扩充，类数量从 m×n 降到 m+n。
  • 实现细节对客户透明，客户只看到 Abstraction。
代价 / 缺点
  • 要求在设计之初就能正确识别出「两个独立变化的维度」，识别错会白增复杂度。
  • 引入了额外的抽象层次，对只有一个变化维度的场景是过度设计。
  • 聚合关系的引入让对象图更复杂，调试时要跨两个层次看。

与相似模式的区别

维度桥接适配器策略
目的分离抽象与实现，两者独立变化让不兼容的接口能协作封装可互换的算法
结构特征两个继承层次 + 聚合桥一个类实现目标接口并转发Context 持有 Strategy
设计时机设计之初（预防性）事后补救（已有类无法改）设计之初或重构
关注点结构维度接口兼容算法选择

参考实现

易错点 · 以为桥接和适配器都是「连接两个东西」，所以可以互换。适配器是事后补救：两个类已经存在、接口不兼容，用一个 Adapter 硬接起来；桥接是事前设计：预见到抽象与实现会各自演化，一开始就把它们分成两个层次。考试若问「桥接与适配器的区别」，第一句就答设计时机，第二句答目的（适配器改接口，桥接分离抽象与实现）。

组合模式 Composite Pattern

结构型

意图：将对象组合成树形结构来表示「部分-整体」的层次结构，使得用户对单个对象和组合对象的使用具有一致性。

动机 / 问题场景

课程用「计算机」举例：计算机由机箱、显示器、键盘、鼠标组成；机箱里又有主板、CPU、硬盘、显卡、电源；主板里还有网卡……如果客户端要统计整台机器的价格，难道要写一堆 if (是机箱) ... else if (是CPU) ...？组合模式把「单一对象（Leaf）」和「组合对象（Composite）」统一到 Component 接口下，客户端调用 operation() 时，Composite 递归调用子节点的 operation，整棵树的遍历就自然完成了。

结构

Component+ operation()
+ add() / remove() / getChild()
实现
Leaf+ operation()Composite+ operation()
+ add() / remove()
Composite 持有 0..* 个 Component（自引用）
childrenList<Component>

Composite 里存的是 Component 的集合，所以组合对象里既能放叶子，也能放另一个组合对象——树就长出来了。

  • Component —— 为组合对象声明接口；声明访问和管理子组件的接口（add/remove/getChild）。
  • Leaf —— 叶节点对象，没有子节点，定义图元对象的行为。
  • Composite —— 定义复合部件的行为，存储子部件，并在 operation 里递归转发给子部件。
  • Client —— 通过 Component 接口操纵组合部件中的对象。

协作要点

  1. Client 拿到一个 Component 引用（可能是 Leaf，也可能是 Composite）。
  2. Client 调用 operation()。
  3. 若接收者是 Leaf，直接处理请求。
  4. 若接收者是 Composite，先遍历子部件，对每个子部件调用 operation()（递归）。
  5. 转发前后可以执行一些辅助操作（如累加统计、加缩进）。

适用场景

  • 想表示对象的部分-整体层次结构（树形）。
  • 希望用户忽略组合对象与单个对象的不同，统一使用组合结构中的所有对象。
  • 需要对整棵树做统一操作（统计、渲染、遍历、校验）。

优缺点

优点
  • 定义了包含基本对象和组合对象的类层次结构，客户代码被简化。
  • 一致地使用组合对象和单个对象，客户端不需要写类型判断。
  • 容易增加新类型的组件（新增一个 Leaf 或 Composite 子类即可）。
代价 / 缺点
  • 设计过于泛化：为了让叶子也能被统一对待，Component 接口可能被迫包含无意义的操作。
  • 「透明性 vs 安全性」两难：add/remove 放 Component 则叶子要抛异常，放 Composite 则失去统一接口。
  • 树很深时递归可能栈溢出；共享节点（一个子节点有多个父）会让语义变复杂。

与相似模式的区别

维度组合装饰器
结构形态树（一个节点可有多个子节点）链（每层只包一个对象）
目的表示部分-整体层次，统一对待动态增加职责
子节点数量0..*固定 1 个
递归方向向下遍历所有子节点向内委托给被包装者
典型场景文件系统、UI 容器、组织架构Java IO 流、加边框/滚动条

易错点 · 把 add/remove 只写在 Composite 里，却声称客户端可以完全一致地使用。这正是「透明性 vs 安全性」的取舍：若 add/remove 只声明在 Composite 上，客户端要统一处理就必须先做类型判断（if (node instanceof Composite)），一致性被破坏；若提到 Component 上（透明方案），叶子必须实现它并抛异常。答题时要明确指出选了哪一边、代价是什么，而不是笼统说「组合模式让客户端统一对待」。

装饰器模式 Decorator Pattern

结构型

意图：动态地给一个对象添加一些额外的职责。就增加功能来说，装饰模式比生成子类更为灵活。

动机 / 问题场景

课程用「画可以加画框、蒙玻璃」和「穿衣服」举例，最经典的例子是咖啡加调料：有多种咖啡，也可以加牛奶、豆浆、摩卡，而且可以叠加（摩卡 + 双份牛奶）。用继承的话，「咖啡 × 调料组合」会产生爆炸性的子类数量；用装饰器则是：new Mocha(new Milk(new Espresso()))，每个装饰器包住同类型的组件，在转发前后加自己的逻辑，层层嵌套、运行期组合。

结构

Component+ operation()
实现
ConcreteComponent+ operation()Decorator- component: Component
+ operation()
继承
ConcreteDecoratorA+ operation()
+ addedBehavior()
Decorator 既 is-a Component，又 has-a Component

装饰器的关键结构：它同时「继承」和「持有」Component，所以可以无限套娃且仍是一个 Component。

  • Component —— 定义对象接口，可以给这些对象动态添加职责。
  • ConcreteComponent —— 定义一个具体的对象，也可以给这个对象添加一些职责。
  • Decorator —— 维持一个指向 Component 对象的指针，并定义一个与 Component 接口一致的接口。
  • ConcreteDecorator —— 向组件添加职责（在转发前后执行附加动作）。

协作要点

  1. Client 创建 ConcreteComponent。
  2. Client 用 ConcreteDecorator 一层层包住它，每层都保存被包装者的引用。
  3. Client 对最外层调用 operation()。
  4. 每个装饰器在转发给内层之前/之后执行自己的附加动作。
  5. 请求逐层向内传递到 ConcreteComponent，结果逐层向外返回并可能被修饰。

适用场景

  • 在不影响其他对象的情况下，以动态、透明的方式给单个对象添加职责。
  • 处理那些可以撤销的职责（去掉最外层装饰即可）。
  • 当不能采用生成子类的方法扩充时：独立扩展组合会爆炸，或类定义被隐藏/不能用于继承。

优缺点

优点
  • 比静态继承更灵活：运行期可任意组合装饰。
  • 避免在层次结构高层的类有太多特征，「即用即付」——不需要的特征不必付出代价。
  • 符合开闭原则：新增功能只需新增一个装饰器类。
代价 / 缺点
  • 会产生许多小对象，学习和调试困难（一层层剥开才知道实际类型）。
  • 装饰链过长时性能与可读性都下降。
  • 使用装饰时不应依赖对象标识：装饰后的对象与被装饰对象不是同一个对象，equals 语义可能失效。

与相似模式的区别

维度装饰器适配器代理继承
接口不改变改变（转换）不改变不改变
功能增强不改变控制访问（可能增强）增强
绑定时机运行期，可叠加编译期/运行期，单层运行期，单层编译期
对象数量多层包装，每层一个对象一层一层1 个
设计意图动态加职责接口兼容控制访问静态复用

参考实现

易错点 · 把装饰器写成「继承 Component 但不持有 Component」，结果变成普通子类。装饰器必须同时 is-a 和 has-a Component：只继承不持有，就无法在运行期包装任意实现，退化成静态继承；只持有不继承，就无法被当成 Component 继续嵌套。另外注意 super.operation() 与 inner.operation() 的区别——装饰器应委托给被包装对象，而不是父类。

外观模式 Facade Pattern

结构型

意图：为子系统中的一组接口提供一个一致的界面，外观模式定义了一个高层接口，让子系统更容易使用。

动机 / 问题场景

课程用「毕业生办离校手续」举例：学生要跑教务处、后勤处、图书馆、公安处，交学生证、身份证、借书证、饭卡，换回毕业证、学位证、派遣证……如果每个毕业生都自己一个个部门跑，流程复杂且容易漏。学校设一个「毕业手续代办处」，学生只跟代办处打交道，代办处内部去协调各部门。这就是外观模式：客户只认识 Facade，子系统之间、子系统与客户之间的耦合都被切断。

结构

Client只认识 Facade
调用 operationWrapper()
Facade+ operationWrapper()
协调
SubSystem1SubSystem2SubSystem3

外观模式是「单向」的：Client → Facade → Subsystem。子系统不知道 Facade 存在，也不引用它。

  • Facade —— 知道哪些子系统类负责处理请求；将客户的请求代理给适当的子系统对象。
  • Subsystem —— 实现子系统的功能；处理由 Facade 指派的任务；没有 Facade 的任何相关信息。
  • Client —— 通过 Facade 使用子系统，不需要了解内部结构。

协作要点

  1. Client 调用 Facade 提供的高层方法（如 trip(to, days)）。
  2. Facade 按业务顺序调用多个子系统的方法。
  3. 各子系统各自完成自己的职责，彼此之间不需要知道对方。
  4. Facade 汇总结果（或直接返回）给 Client。

适用场景

  • 要为复杂子系统提供一个简单接口，定义高层接口使子系统更易使用。
  • 想解除客户程序与抽象类具体实现部分的依赖，提高子系统的独立性与可移植性。
  • 需要构建层次结构的子系统时，用 Facade 定义每层的入口点。

优缺点

优点
  • 对客户端屏蔽子系统组件，减少客户端需要处理的对象数目。
  • 实现子系统与客户之间的松耦合，子系统内部变化不影响客户。
  • 不限制客户直接使用子系统类——Facade 只是便利入口，不是强制门禁。
代价 / 缺点
  • 增加了附加的方法调用（多一层转发）。
  • 子系统中类的功能受到外观的限制（若客户只用 Facade，就只用到被包装的能力）。
  • 子系统接口改变会导致外观跟着改变，Facade 需要同步维护。

与相似模式的区别

维度外观适配器中介者
面向对象一个子系统（多个类）一个已有类一组相互通信的同事对象
目的简化接口、降低客户与子系统的耦合转换接口使其兼容把网状交互收敛为星形
是否改变接口提供新的简化接口转换为客户期望的接口同事间不再直接引用
子系统是否知道它不知道Adaptee 通常不知道 Adapter同事知道中介者

参考实现

易错点 · 把外观模式说成「必须禁止客户直接访问子系统」。GoF 明确写了外观模式不限制客户应用子系统类：它只是提供一个便利的统一入口，需要精细控制的客户仍然可以直接调用子系统。另外要区分外观与适配器：外观是多对一（多个子系统 → 一个简化接口），适配器是一对一（一个不兼容接口 → 一个目标接口）。

享元模式 Flyweight Pattern

结构型

意图：运用共享技术有效地支持大量细粒度的对象。享元是一个可共享的对象，通过共享相同/相似对象来减少内存占用。

动机 / 问题场景

课程用「同型号轿车」举例：用 Car 类创建若干同型号轿车，它们的 height、width、length 完全相同，只有 color、power 不同。如果每个对象都存一份尺寸，几千辆车就是几千份重复数据。享元的做法是把尺寸抽成 CarData（内部状态，可共享），Car 只持有 CarData 的引用 + 自己的 color/power（外部状态）。围棋棋子是另一个经典例子：黑白两种棋子只有颜色不同，位置由客户端传入。

结构

Client保存外部状态（坐标等）
getFlyweight(key)
FlyweightFactory- pool: Map
+ getFlyweight(key)
返回共享实例
Flyweight+ operation(extrinsicState)
实现
ConcreteFlyweight内部状态UnsharedConcreteFlyweight不共享

工厂维护享元池；客户端每次调用 operation 时把外部状态作为参数传进来。

  • Flyweight —— 描述一个接口，通过这个接口 flyweight 可以接受并作用于外部状态。
  • ConcreteFlyweight —— 实现 Flyweight 接口，并为内部状态增加存储空间；该对象必须可共享。
  • UnsharedConcreteFlyweight —— 指那些不需要共享的 Flyweight 子类（Flyweight 接口使共享成为可能，但不强制共享）。
  • FlyweightFactory —— 负责创建和管理 flyweight 对象，维护一个享元池；保证合理共享。

协作要点

  1. Client 用「键」向 FlyweightFactory 请求享元对象。
  2. 工厂先查享元池：存在则直接返回，不存在则创建并放入池中。
  3. Client 拿到共享的享元对象，自己保存外部状态。
  4. Client 调用 operation(extrinsicState)，把外部状态作为参数传入。
  5. 享元结合内部状态与传入的外部状态完成计算。

适用场景

  • 系统中有大量相似对象，这些对象耗费大量内存。
  • 细粒度对象都具备较接近的外部状态，而内部状态与环境无关（对象没有特定身份）。
  • 需要缓冲池 / 对象池的场景（连接池、线程池、字符串常量池）。

优缺点

优点
  • 大幅减少对象数量，节省内存（空间性能好）。
  • 把内部状态集中管理，外部状态外置，职责更清晰。
  • 享元池天然支持复用，减少创建/销毁开销。
代价 / 缺点
  • 把状态拆成内部/外部，增加了实现复杂度，客户端要负责保存外部状态。
  • 以时间换空间：每次取享元都要查池，查找有额外时间复杂度。
  • 享元对象不可变（共享前提），因此不能存放随场景变化的数据。

与相似模式的区别

维度享元单例对象池
实例数量多个（按内部状态区分）唯一一个多个，按需借还
共享粒度按 key 共享同类对象全局唯一借出期间独占
关注点节省内存控制唯一性复用昂贵资源
典型例子棋子颜色、字符字形配置中心数据库连接池

参考实现

易错点 · 把「随场景变化的状态」也放进享元对象里。享元对象必须可共享，共享的前提是不可变。如果把棋子的坐标（外部状态）也存进 Chesspiece，那么所有黑子会共用同一个坐标，落子立刻出错。判断标准：与场景无关、能共享的 → 内部状态；随场景变化的 → 外部状态，由客户端保存。

代理模式 Proxy Pattern

结构型

意图：为其他对象提供一种代理以控制对这个对象的访问。

动机 / 问题场景

课程用「大图片加载慢」和「远程对象访问慢」举例：对象是一个几十 MB 的图片，打开页面时立刻加载会卡死，可以先放一个占位 Proxy，等真正需要显示时再去创建 RealSubject；对象在远端服务器上，直接调用受网络延迟影响，可以让本地 Proxy 代表它，把调用打包成网络请求。课程的游戏代练例子也很直观：GamePlayerProxy 与被代理的 GamePlayer 实现同一接口，代理在转发前后记录打怪时间、计算升级耗时。

结构

Client只持有 Subject
request()
Subject+ request()
Proxy 与 RealSubject 实现同一接口
Proxy- realSubject
+ request()RealSubject+ request()
代理在适当时机转发
真实对象真正的业务实现

代理与真实主体接口完全一致，客户端感觉不到差别；差别在于代理可以「在转发前后做手脚」。

  • Subject —— 定义 RealSubject 和 Proxy 的共用接口，这样在任何使用 RealSubject 的地方都可以使用 Proxy。
  • RealSubject —— 定义 Proxy 所代表的真实实体。
  • Proxy —— 保存一个引用使得代理可以访问实体，并提供一个与 Subject 相同的接口；控制对实体的存取，可能负责创建和删除它。
  • Client —— 维持一个对 Subject 的引用。

协作要点

  1. Client 调用 Subject 接口上的 request()。
  2. 实际进入 Proxy 的 request()。
  3. Proxy 在转发前后执行控制逻辑：权限检查、延迟创建、缓存命中判断、加锁、计数。
  4. Proxy 在适当时机把请求转发给 RealSubject。
  5. RealSubject 完成业务并返回，Proxy 可能对结果做后处理。

适用场景

  • 远程代理：为一个位于不同地址空间的对象提供局部代表。
  • 虚拟代理：需要创建开销很大的对象时，先缓存/延迟创建。
  • 保护代理：控制对原始对象的访问，按权限过滤。
  • 智能引用代理：对象被引用时提供额外操作，如记录访问次数、加锁、写时复制。

优缺点

优点
  • 引入间接层，可以在不修改目标对象的前提下增加控制逻辑（缓存、权限、日志）。
  • 保护了真实对象，防止客户端直接访问带来的风险。
  • 对客户端透明：客户端只看到 Subject 接口。
代价 / 缺点
  • 请求多经过一层，响应时间可能增加。
  • 某些代理（远程代理）需要处理网络异常、序列化等额外复杂度。
  • 代理与真实对象必须保持接口同步，接口一改两处都要改。

与相似模式的区别

维度代理装饰器适配器
接口与 Subject 完全相同与 Component 完全相同转换成 Target
目的控制访问（门卫）动态添加职责接口兼容
是否增加功能可能（缓存/日志），但核心是控制核心就是加功能不加功能
对象创建常负责创建/销毁真实对象被装饰对象由外部创建被适配对象由外部提供
层数通常一层可多层嵌套一层

参考实现

易错点 · 认为「代理和装饰器都是包装，所以可以互相替代」。两者结构几乎一样（同接口 + 持有引用 + 转发），但意图不同：代理的核心是控制访问（门卫），通常由代理自己创建/管理真实对象，一般只有一层；装饰器的核心是动态增加职责，被装饰对象由客户端传入，可以多层嵌套。课程原话：代理是一个「门卫」，装饰是动态扩展实际对象的功能。

答题技巧结构型模式最常考「类图 + 一句话区别」。记住这条主线：适配器改接口、装饰器加功能、代理控访问、外观简入口、桥接分维度、组合成树、享元省内存。七个动词记住，选择题基本不会错。

易混组合核心区别判断口诀

外观 vs 中介者外观是单向（客户 → 外观 → 子系统，子系统不知道外观）；中介者是双向（同事之间通过中介者互相通信，同事知道中介者）。简化入口 → 外观；协调互交 → 中介者。
享元 vs 单例单例保证全局唯一一个实例；享元按 key 维护一族可共享实例，通常配合工厂 + 池。唯一 → 单例；共享池 → 享元。

记忆线索结构型模式只有两种「手段」：继承（类结构型，只有类适配器）与组合/聚合（对象结构型，其余六个）。所有模式都在做同一件事——用运行期的弱关联替换编译期的强关联，也就是合成复用原则的七种具体实现。

易错点

#

以下每条都对应一个真实的失分点，尤其在类图题与「区别」简答题中。

  • 把适配器和装饰器都说成「包装器」，不做区分。两者别名都叫 Wrapper，但适配器改变接口、不改变功能，装饰器不改变接口、增强功能。考试写「都是包装模式」等于没答区别，必须点出「接口是否改变」这个判据。
  • 认为桥接模式中的 Implementor 接口必须与 Abstraction 接口一致。GoF 明确指出 Implementor 的接口不一定要与 Abstraction 的接口完全一致，甚至可以完全不同。Abstraction 只是把请求委托过去，两者是「抽象—实现」关系而非「同构」关系。
  • 组合模式里把 add/remove 只写在 Composite 上，却声称客户端完全一致。这是「透明性 vs 安全性」的取舍。放在 Composite 上是安全方案，但客户端统一处理前必须做类型判断，一致性被破坏；放在 Component 上是透明方案，代价是叶子节点要抛异常。答题必须说明选了哪一边。
  • 把享元的「外部状态」也塞进享元对象。享元对象必须可共享，前提是不可变。随场景变化的外部状态必须由客户端保存、调用时作为参数传入。把坐标存进棋子对象，所有黑子就会共用同一坐标。
  • 说外观模式「禁止客户直接访问子系统」。GoF 明确：外观模式不限制客户应用子系统类，它只是提供一个更方便的统一入口。说成「强制门禁」是常见错误。另外外观是「多对一」，适配器是「一对一」。
  • 认为代理和装饰器可以互换，因为类图一样。类图相似但意图相反：代理是门卫（控制访问，常自己创建真实对象，通常一层）；装饰器是功能扩展（被装饰对象由客户端传入，可多层嵌套）。简答题只写结构不写意图，最多拿一半分。
