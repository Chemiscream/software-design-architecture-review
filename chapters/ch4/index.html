第 4 章 · 面向对象设计模式

GoF 23 种设计模式：从「记住名字」到「选对模式」

本章覆盖创建型 5 种、结构型 7 种、行为型 11 种共 23 个 GoF 模式。考试既考「这个模式的意图与结构」，也考「这个场景该用哪个模式」。本页是全景索引：先用一张总表建立整体印象，再用决策树练习选型，最后通过对比表把容易混淆的模式两两钉死。

学习目标

本章体量大（三份课件共 350 页），必须靠结构化记忆。读完应当能：

  1. 能默写 23 种模式的三类归属：创建型 5、结构型 7、行为型 11，并说出每类解决什么问题。
  2. 能对任意一个模式，用「意图 + 结构 + 代价」三句话讲清，并画出核心类图。
  3. 能在给出业务场景时，沿着决策树选出 1–2 个候选模式并说明取舍。
  4. 能辨析至少 8 组高频易混模式：工厂方法/抽象工厂、适配器/装饰器/代理、策略/状态、中介者/观察者等。
  5. 能指出每个模式「不适用的场景」，避免过度设计——这是设计题拿高分的关键。

知识地图

23 个模式不是 23 个孤立知识点，而是三条主线上的 23 个节点。

创建型 ×5

  • 封装「用哪些具体类」
  • 隐藏实例如何创建组装
  • 工厂方法 / 抽象工厂
  • 建造者 / 原型 / 单例

结构型 ×7

  • 用组合替代继承
  • 适配器 / 桥接 / 组合
  • 装饰器 / 外观 / 享元
  • 代理（控制访问）

行为型 ×11

  • 划分职责与算法
  • 模板方法 / 命令 / 解释器
  • 迭代器 / 中介者 / 备忘录
  • 观察者 / 状态 / 策略 / 责任链 / 访问者

答题主线

  • 意图（GoF 原话）
  • 结构（角色 + 关系）
  • 协作（请求怎么走）
  • 代价（不适用的场景）
02

模式分类与 23 种速查表

#

先建立分类框架，再用一张总表把 23 个模式压成可背诵的形式。

创建型模式 ×5

抽象实例化过程，让系统独立于对象如何被创建、组合和表示。两条永恒主旋律：封装「用哪些具体类」、隐藏「实例如何创建组装」。

进入创建型专题 →

工厂方法 · 抽象工厂 · 建造者 · 原型 · 单例

结构型模式 ×7

处理类或对象的组合，用运行期的弱关联（组合/聚合）替换编译期的强关联（继承）。七个模式是合成复用原则的七种具体实现。

进入结构型专题 →

适配器 · 桥接 · 组合 · 装饰器 · 外观 · 享元 · 代理

行为型模式 ×11

对不同对象之间划分责任和算法的抽象化，关注它们之间的交互与通信，刻画运行时的复杂控制流。数量最多、分值最高。

进入行为型专题 →

责任链 · 命令 · 解释器 · 迭代器 · 中介者 · 备忘录 · 观察者 · 状态 · 策略 · 模板方法 · 访问者

两条分类轴

按目的：创建型 / 结构型 / 行为型。按范围：类模式（继承，编译期确定）与对象模式（运行期可变）。两轴交叉得到 6 类，其中类结构型只有类适配器，类行为型只有模板方法与解释器。

四个必须先说清的术语

后面三张专题页会反复用到这些词，先把定义钉死。

设计模式 Design Pattern

针对有一定复杂度的软件系统中普遍存在、重复出现的结构与套路，用来解决特定场景下具有一般性的设计问题。它不是代码库，而是可复用的设计方案。

术语基础

模式的四个要素 Four Elements

名字（便于交流的词汇）、问题（何时适用）、解决方案（元素、关系、协作）、效果（优缺点与取舍）。答题时按这四项展开最稳妥。

术语答题框架

模式 vs 框架 Pattern vs Framework

模式比框架更抽象、是更小的体系结构元素；框架比模式更特例化。框架规定应用的体系结构，模式是被反复使用的设计经验。

辨析高频

反模式 Anti-Pattern

被反复使用却有害的「解法」，例如上帝类、面条代码、把单例当全局变量用。识别反模式与识别模式同样重要。

术语易错

如何选择模式

#

选型是设计题的核心能力：先走决策树，再用三栏清单交叉验证。

如何选择模式：三步决策树

第一步判断「问题属于哪一类」，第二步在该类内按「变化点」定位候选，第三步用对比表排除干扰项。下图是前两步的压缩版。

图中列出 19 个最常用的模式；备忘录、迭代器、中介者、访问者、解释器见下方三栏清单。

三栏选型清单（按问题关键词直接查）

创建型：谁负责 new？

全局只要一个实例单例
复制已有对象更便宜原型
复杂对象、分步装配建造者
一族产品要配套创建抽象工厂
一种产品多个实现工厂方法

结构型：怎么组合？

接口不兼容适配器
运行期动态加功能装饰器
控制对对象的访问代理
部分-整体树形结构组合
抽象与实现两维度桥接
子系统入口太复杂外观
大量小对象耗内存享元

行为型：职责怎么分？

算法可互换策略
行为随状态改变状态
骨架固定、步骤可变模板方法
请求要撤销/排队命令
状态变化要广播观察者
沿链找处理者责任链
对象间互交太乱中介者
保存/恢复状态备忘录
不暴露内部地遍历迭代器
不改变元素加新操作访问者
解释简单文法解释器

选型第一原则：先问「变的是什么」设计题最常见的失分不是选错模式，而是没想清楚变化点。拿到题目先回答三个问题：① 需求变化时，最可能改的是哪一部分？② 这部分现在是硬编码在哪里的？③ 把它抽成对象后，谁来负责选择？三问答清楚，模式自然浮现；答不清楚就套模式，一定是过度设计。

三个「不要用」的反面清单

不要为了用模式而用模式

只有两个实现、且可预见不会增加时，直接用 if/else 比工厂方法更清晰。模式的价值在于应对变化，没有变化就没有价值。

不要在小程序里上抽象工厂

抽象工厂会一次性引入 AbstractFactory + N 个 ConcreteFactory + 多个产品等级结构。只有一个产品族、且不打算扩展时，简单工厂足够。

不要用单例代替全局状态管理

单例会带来隐式依赖与测试困难。能用依赖注入传进来的对象，就不要做成单例；单例只适合真正「全局唯一」的资源（配置、连接池）。

不要忽视模式之间的组合

真实系统里模式是组合使用的：命令 + 备忘录做撤销、组合 + 访问者做遍历统计、抽象工厂 + 单例做全局配置工厂。答题时点出组合关系会加分。

04

跨模式横向对比

#

跨类别的对比才是选择题的重灾区。下面三张表把「看着像、其实不同」的模式两两钉死。

表一：跨类别高频辨析（8 组）

易混组合核心区别判断口诀
工厂方法 vs 抽象工厂工厂方法面对1 个产品等级结构；抽象工厂面对多个，一次创建一族产品。「一族」→ 抽象工厂；「一种」→ 工厂方法。
建造者 vs 抽象工厂建造者分步装配一个复杂对象，最后 getResult 才产出；抽象工厂一次创建一族平级产品。「一个复杂对象」→ 建造者。
适配器 vs 装饰器适配器改接口不改功能；装饰器不改接口只加功能。看接口是否改变。
装饰器 vs 代理装饰器目的是加功能、可多层嵌套；代理目的是控访问、常自己创建真实对象、通常一层。「门卫」→ 代理；「穿衣服」→ 装饰器。
组合 vs 装饰器组合是树（多个子节点、向下递归）；装饰器是链（固定一个、向内委托）。「树」→ 组合；「链」→ 装饰器。
策略 vs 状态策略由客户端注入、策略间互不相识；状态由状态类自身转移、状态间知道彼此。「谁切换」决定一切。
中介者 vs 观察者中介者是星形双向（同事知道中介者）；观察者是一对多单向广播（Subject → Observer）。「协调互交」→ 中介者。
命令 vs 策略命令封装请求（持有 Receiver，支持 undo/排队）；策略封装算法（不持有接收者）。「可撤销」→ 命令。

表三：三类模式的「共同主旋律」

答题技巧简答题问「XX 模式与 YY 模式的区别」时，按固定三段写：① 意图不同（各自的 GoF 定义关键词）；② 结构不同（谁持有谁、接口是否改变）；③ 适用场景不同（举一个只有 A 适用、只有 B 适用的例子）。三段齐了基本满分，只写「类图一样/不一样」最多给一半。

05

易错点

#

以下 12 条是整章最高频的失分点，按「分类错误 → 结构错误 → 意图错误」排列。

  • 把简单工厂算作 GoF 23 种之一。GoF 23 种里没有简单工厂，创建型只有工厂方法、抽象工厂、建造者、原型、单例 5 种。简单工厂是课程补充的入门形态，且违反开闭原则。
  • 把「类模式 / 对象模式」与「创建型 / 结构型 / 行为型」混成一个轴。这是两条独立的分类轴：按目的分三类，按范围分类模式（继承）与对象模式（运行期可变）。两轴交叉得 6 类，其中类结构型只有类适配器，类行为型只有模板方法与解释器。
  • 抽象工厂的扩展方向记反。抽象工厂加产品族容易（新增具体工厂）、加产品等级结构难（改接口 + 所有子类）。访问者恰好相反：加操作容易、加元素类难。这两个「倾斜方向相反」是高频考点。
  • 把适配器、装饰器、代理三者混为一谈。三者都是「包一层」，但：适配器改接口不改功能；装饰器不改接口加功能、可多层嵌套；代理不改接口控访问、常自己创建真实对象、通常一层。
  • 策略模式和状态模式只说「类图一样」。类图确实几乎一致，但切换机制完全不同：策略由客户端注入、策略间互不相识；状态由状态类自身触发转移、状态间知道彼此。答题必须答到「谁负责切换」这一层。
  • 把观察者模式等同于发布-订阅。观察者模式中 Subject 直接持有 Observer 引用；发布-订阅在两者之间插入事件通道/代理，双方互不相识，属于架构层解耦。严格说后者已不是 GoF 观察者模式。
  • 模板方法的模板方法写成可覆盖的普通方法。模板方法必须固定算法骨架，工程上应声明为 final；只把原语操作留成 abstract/protected。否则子类改写顺序，模式失效。
  • 原型模式的 clone 直接 return super.clone() 就交卷。Object.clone() 是浅拷贝，引用字段只复制地址。原型里有 List、数组等可变对象时必须手动重建，否则副本与原对象共享数据。
  • 责任链默认请求一定被处理。GoF 明确「不保证被接受」，必须提供兜底处理者；链若成环会导致无限循环。
  • 组合模式里 add/remove 只写在 Composite 上，却声称客户端完全一致。这是「透明性 vs 安全性」的取舍：放 Composite 是安全方案（客户端需类型判断，一致性被破坏），放 Component 是透明方案（叶子抛异常）。答题必须说明选了哪一边。
  • 把享元的外部状态也塞进享元对象。享元对象必须可共享 → 必须不可变。随场景变化的外部状态由客户端保存、调用时传参。把坐标存进棋子对象，所有黑子会共用同一坐标。
  • 认为单例只要「私有构造 + 静态实例」就无懈可击。完整答案要覆盖：并发（DCL 需 volatile）、反射（setAccessible 可破私有构造）、序列化（反序列化产生新实例）、多类加载器。枚举是唯一能同时防住反射与序列化的写法。
