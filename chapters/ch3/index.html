第 3 章 · 软件设计的模式

模式：把前人的设计经验变成可复用的语言

设计模式不是 23 段可以照抄的代码，而是一套描述「问题—方案—代价」的共同语言。 本章讲清模式的来历、四要素、描述模板与三型分类，并给出 GoF 23 种模式的完整速查表—— 在第 4 章逐个展开之前，先把这张地图建立起来。

考试重点 约 25 分钟 概念与分类 简答 + 选择高频
开始阅读 23 模式速查表 直接自测

学习目标

读完后应能做到以下几点。

  1. 能说出模式的定义与起源（Alexander 的建筑模式 → GoF 的 23 种设计模式），并解释「模式不是被发明的，而是被总结和命名的」。
  2. 能完整背出模式的四要素（名称、问题、解决方案、效果），并说明每一要素缺失会造成什么后果。
  3. 能把任意一个 GoF 模式正确归入创建型 / 结构型 / 行为型，并说清三型的划分依据。
  4. 能按 GoF 描述模板（名称、问题、解决方案、效果、适用性、相关模式）复述一个模式，并解释「效果」一栏为什么必须写代价。
  5. 能辨析模式、惯用法、框架、类库、架构模式五个概念的层次差异，并在给定场景中判断「该不该用模式」。

知识地图

把全章压缩成四列：为什么需要模式、模式给什么、一个模式写什么、用模式要付什么。

问题

  • 经验难口头传递
  • 同类坑反复踩
  • 团队缺共同词汇
  • 读代码不懂意图

方案

  • 给问题命名
  • 记录上下文
  • 形成设计词汇
  • 给出结构与协作

要素

  • 名称 / 别名
  • 问题
  • 解决方案
  • 效果（含代价）

代价

  • 抽象层增多
  • 运行性能下降
  • 架构复杂度上升
  • 过度设计风险

图 3-1　设计原则 → 设计模式 → 架构模式

读法：自下而上「原则定目标，模式定手法，架构定格局」；自上而下则是「质量属性反过来筛选可用的模式」。 注意箭头的粗细含义——原则与模式之间是约束关系，模式与架构之间是组成关系， 而架构对上的虚线表示反馈：同样的原则，在不同质量属性要求下会选到不同的模式。

02

核心概念

#

先把术语钉死。本章之后所有的讨论，都建立在这十个词的区分之上。

模式 Pattern

在特定上下文中，针对反复出现的设计问题，给出的经过验证的解决方案的核心。 它描述的是「元素、职责与协作关系」的抽象结构，而不是某段可以照抄的代码。

定义 可复用经验

模式四要素 Four Elements

名称（共同词汇）、问题（何时适用、有哪些力在冲突）、 解决方案（角色与协作）、效果（收益与代价）。四者缺一不可， 缺「效果」就会只见优点不见坑。

必背 简答题骨架

模式语言 Pattern Language

建筑学家 Christopher Alexander 在《模式语言》中提出的思想：把若干模式组织成一张 「大模式包含小模式」的网络，让非专家也能按图索骥地做出好设计。设计模式的源头就在这里。

起源 易考

GoF 23 种模式 Gang of Four

1994 年 Gamma、Helm、Johnson、Vlissides 四人在《设计模式》中归纳的 23 种面向对象设计模式： 创建型 5 + 结构型 7 + 行为型 11。注意：他们是总结与命名，不是发明。

23 种 1994

三型分类 Creational / Structural / Behavioral

按意图划分：创建型管「对象怎么来」，结构型管「对象怎么拼」， 行为型管「对象怎么协作与分配职责」。分类依据是目的，不是结构长相。

分类 选择题高频

惯用法 Idiom

与具体编程语言绑定的低层模式，如 C++ 的 Pimpl、Java 的双检锁。 抽象层次低于设计模式：换语言就失效，因此不属于 GoF 的 23 种。

层次辨析 语言相关

反模式 Anti-pattern

看起来合理、实践中却反复造成损害的常见解法，如上帝类、意大利面代码、 复制粘贴式复用。反模式不是「坏模式」，而是「被证伪的伪模式」。

反面 易错

框架 Framework

一组可运行的半成品代码，通过控制反转在合适的时机回调你写的类。 模式是知识，框架是产品；框架内部大量使用模式，但模式不等于框架。

易混淆 控制反转

微架构 Micro-architecture

课件对设计模式的定位：经过验证的适用原则。它决定「把子系统拆成哪些部分、 部分之间如何合作」，粒度比架构模式细、比惯用法粗。

定位 课件原话

委托原则 Delegation

「优先使用组合 / 委托，而不是继承」。把请求转交给另一个对象处理， 被委托者可以是聚合的部分对象，也可以是运行时注入的抽象——后者正是绝大多数模式实现可替换性的手段。

实现手法 组合优于继承

模板示例：一个模式被描述成什么样

下面用第 4 章会详讲的策略模式做示范。注意五行的顺序是固定的： 意图 → 适用场景 → 参与角色 → 主要代价 → 相关模式。 考试让你「描述一个模式」时，照这个骨架写就不会漏项。

策略模式

Strategy Pattern 行为型
意图
定义一系列算法，把它们分别封装起来并使其可以互相替换，让算法的变化独立于使用它的客户。
适用场景
同一问题有多种算法、且需要在运行时切换；
许多相关类仅在行为上不同；
算法中含有客户不该知道的复杂数据结构。
参与角色
Strategy（策略接口）、ConcreteStrategy（具体策略）、Context（持有策略并委托调用）
主要代价
客户必须了解各策略的差异才能选对；策略类数量增多；策略与上下文之间可能产生额外通信开销。
相关模式
状态模式（行为随内部状态自动切换，客户不选）、命令模式（把请求封装成对象）、模板方法（用继承固定骨架）
03

模式的定义与描述

#

这一节回答四个问题：模式从哪来、由哪四块组成、怎么把它写清楚、以及为什么「优先用委托」。

3.1　从建筑到软件：模式是怎么来的

模式的思想不是软件界发明的。建筑学家 Christopher Alexander 在《模式语言》中提出： 城市与建筑中反复出现的问题，可以用一套「模式」来描述——每个模式都写清问题、 解决方案的核心以及在什么上下文下适用；把模式串成网络，就成了一种 模式语言，让不精通建筑的人也能据此做出不坏的设计。

1987 年前后，Kent Beck 与 Ward Cunningham 把这套思路带进面向对象界； 1994 年，Gamma、Helm、Johnson、Vlissides（合称 GoF）在《设计模式：可复用面向对象软件的基础》 中整理出 23 种模式，并第一次用统一的模板把它们写清楚。

关键认识：模式不是被发明的 GoF 的贡献不是「发明了 23 种巧妙写法」，而是把优秀设计师早就在用的做法总结出来、起了名字、 并写清了上下文与代价。所以同一段结构，在不同语言、不同年代可能叫不同名字； 而同一个名字，在具体项目里的实现可以千差万别。 正因为是「总结」而非「发明」，模式才会不依赖平台、不限定编程语言—— 它描述的是职责与协作关系，不是某段代码。

这解释了模式的真正价值：它首先是一套共同词汇。说一句「这里用观察者模式」， 比画半小时类图更能让同事立刻明白你的意图、以及你将付出什么代价。 其次才是可复用的经验——让你不必从零试错。

3.2　模式四要素：一个模式必须说清的四件事

四要素是本章最硬的考点。它同时是「模式的定义」和「描述一个模式的骨架」， 考简答题时按这四点铺开即可。

要素回答什么问题缺失会导致
名称 Name 用一个词指代这套方案，含别名（如「策略」又称 Policy） 无法在设计讨论中引用，模式退化成一个私人技巧
问题 Problem 在什么上下文下、面对什么反复出现的问题，有哪些力在互相冲突 变成无脑套用，在不该用的地方硬套
解决方案 Solution 由哪些元素组成、各自职责是什么、彼此如何协作（抽象描述，不是代码） 退化为一段只能照抄的代码，无法迁移到别的场景
效果 Consequences 收益与代价：对灵活性、扩展性、可移植性的影响，以及时间空间的代价 只见优点不见坑，直接滑向过度设计

答题技巧 问「什么是设计模式」时，标准答法是定义 + 四要素： 「设计模式是在特定上下文中，对反复出现的设计问题所给出的经过验证的解决方案的核心， 它由名称、问题、解决方案、效果四个要素构成。」 最后补一句「模式描述的是元素、职责与协作关系，而不是具体代码或可复用的类库」，通常就能拿满。

3.3　描述模式的模板：GoF 的六段式

课件给出的模板共六项，比四要素更细，是写文档和做设计题时的实际格式。 注意第 3 项「解决方法」下面还有四个子项——这四项正是把「解决方案」落到实处的地方。

序号模板项写什么
1名称 / 别名模式名 + 业界别名，便于检索与交流
2问题适用上下文、要解决的问题、相关的设计力
3 解决方法 ① 参与者：有哪些类与对象、各自职责；
② 类图：类之间的静态结构关系（继承、关联、聚合、组合）；
③ 动态关系：一次请求/通知在对象间如何流转；
④ 程序举例：一段能说明结构的示例代码
4评价（优缺点）即四要素中的「效果」，必须同时写收益与代价
5适用范围什么时候该用、什么时候不该用
6类似的模式易混模式及其差异，帮助选型

课件用词说明 第 3 项下课件原文写作「类图（金台关系）」，指的是类图中体现的静态结构关系 （继承、关联、聚合、组合等），与第 ③ 小项的「动态关系」相对。 复习时按「静态结构 / 动态交互」这一对来记即可，不要被字面写法卡住。

3.4　委托原则：绝大多数模式的实现手法

课件在讲「模式的使用」时专门强调了一条原则：优先使用组合 / 委托。 所谓委托，就是把请求转交给另一个对象处理。被委托的对象有两种来源： 一是它本就是当前对象聚合进来的部分对象；二是它是一个运行时才确定的抽象 （接口或抽象类）实现。第二种正是模式能「可插拔」的根源。

为什么不用继承？因为继承是编译期绑定、白箱复用，父类的实现细节对子类暴露； 委托是运行期绑定、黑箱复用，只依赖被委托者的接口。下面这段对比说明了差别。

用法差别一目了然：new LoggingSink(new ConsoleSink()) 可以在运行时任意组合； 而 LoggingList 只能通过新增子类来变化，类数量会随需求组合爆炸。 观察者、策略、状态、命令、装饰器、代理、桥接——这些模式的骨架里都藏着一个 「持有抽象 + 转发调用」的委托字段。

3.5　模式的目标：提高架构属性，但要付三笔账

课件把模式的主要目标归为两条：再次使用已获得的经验， 以及提高架构的灵活性和可扩展性。落到具体属性上：

  • 可理解性：靠简易性达到——结构清晰、职责单一，并配有结构化的全面文档。 模式名本身就是一种文档：看到 XxxFactory 就知道对象的创建被集中管理了。
  • 可扩展性：有两条路。一是静态继承（编译期扩展，简单但僵化）； 二是使用聚合接口或抽象类，即针对接口 / 抽象编程（运行期扩展，模式主要走这条路）。

而这一切都不是免费的。课件明确列出模式的三项代价：

收益：扩展性提高

变化点被隔离到一个抽象之后，新增实现只需新增类，不必修改既有代码—— 这正是开闭原则在起作用。

代价一：性能下降

多一层间接（接口调用、动态分派、对象转发），调用链变长； 极端情况下还会增加对象数量与内存占用。

代价二：复杂度上升

类与接口数量增加，控制流不再线性；新人读代码需要先理解模式的约定， 调试时也要跨多个对象追调用。

代价三：过度设计风险

为「将来可能的变化」预留抽象，结果变化从未发生， 白白背上一层间接——这是模式最常见的失败方式。

3.6　反模式与模式误用

反模式（Anti-pattern）指那些初看合理、实践中反复造成损害的常见解法。 它有两个必要成分：一是「看起来像解决方案」，二是「有据可查的负面后果」。 所以反模式不是「写得丑的代码」，而是被证伪的伪模式。

反模式表现为什么会发生正确做法
上帝类 一个类几千行，什么都管 需求不断往里加，没人敢拆 按职责拆分为多个协作对象
意大利面代码 控制流四处跳转，无层次 缺少分层与统一抽象 先立分层，再谈模式
复制粘贴式复用 相似代码多份并存 改一处忘一处，越改越不敢动 提炼共同抽象，用委托复用
模式堆砌 简单 CRUD 也要工厂 + 策略 + 外观 把「用了模式」当成了目标本身 先确认变化点，再决定是否引入模式

判断自己是不是在误用模式，看三个信号：

  1. 说不出这个模式在隔离哪个变化点。如果答不上「将来什么会变」，这层抽象就是空的。
  2. 为了套模式而增加了类，却没减少任何条件分支。模式的收益应体现为「改动点收敛」。
  3. 只有一种实现，且明确知道不会有第二种。此时抽象的成本大于收益，直接写具体类更好。

3.7　如何选择模式：五步决策法

选模式的顺序不能颠倒：先有问题，再有模式；而不是先挑一个模式，再去找地方用。 下面五步可以直接当作设计题的作答框架。

01

描述问题，而不是描述方案

先写清「谁在什么场景下遇到了什么困难」，禁止在这一步提模式名。

02

定位变化点

问「将来最可能变的是什么」——算法？对象创建方式？对象结构？交互流程？ 变化点决定候选模式的类别。

03

按意图匹配候选

用 23 模式总表的「意图」列筛选：创建型对创建、结构型对组成、行为型对职责分配。

04

评估代价与替代方案

对比候选模式的「主要代价」，并问一句：不用模式能不能解决？ 简单重构、提取方法、引入参数往往就够了。

05

小步引入，重构而非重写

先用最小改动验证抽象是否站得住，再逐步扩展。 模式应当在重构中长出来，而不是一开始就设计进去。

3.8　模式与设计原则的关系

一句话概括：原则是目标，模式是手段。原则说「应该松耦合、应对扩展开放」， 但没有告诉你具体怎么写；模式给出了一套经过验证的具体写法。 所以每个模式背后都能找到它服务的原则：

设计原则由哪些模式具体化
开闭原则（对扩展开放、对修改关闭） 策略、装饰器、工厂方法、观察者——新增实现只加类、不改调用方
依赖倒置原则（依赖抽象，不依赖具体） 工厂方法、抽象工厂、桥接——把具体类的创建与使用分离
单一职责 / 明确的职责 外观（对外简化）、中介者（集中交互）、命令（把请求对象化）
接口隔离（客户端只依赖它需要的接口） 适配器、代理——为不同客户端提供窄接口
组合 / 委托优于继承 装饰器、策略、状态、桥接——用持有抽象替代继承层次

反向不成立 「用了模式」不等于「遵守了原则」。单例模式若被滥用为全局变量，会同时破坏单一职责 （既管创建又管业务）与可测试性；模式堆砌更是直接违背「简单优于复杂」。 判卷时看到「因为用了 XX 模式，所以符合开闭原则」这种无条件推断，是不给分的。

横向对比

#

本节是本页最该反复看的部分：23 种模式的总表，以及最容易混淆的几组概念。

4.1　GoF 23 种设计模式完整速查表

下表是本章最核心的资产。5 + 7 + 11 = 23，三型的数量分配本身就常被考。 背法是「先记类型、再记数量、最后记意图关键词」：创建型看「谁负责 new」， 结构型看「怎么拼装、怎么加职责」，行为型看「职责与算法怎么分配」。

# 模式名 / 英文 类型 意图（一句话） 一句话场景
1 单例
Singleton		 创建型 保证一个类仅有一个实例，并提供全局访问点。 配置管理器、连接池、日志器——全局只需一份。
2 工厂方法
Factory Method		 创建型 定义创建对象的接口，让子类决定实例化哪一个类。 同一套业务流程，按不同渠道创建不同订单对象。
3 抽象工厂
Abstract Factory		 创建型 提供一个创建一系列相关或相互依赖对象的接口，而无需指定具体类。 一套 UI 控件要整体切换主题（Windows 风格 / Mac 风格），不能混搭。
4 建造者
Builder		 创建型 将一个复杂对象的构建与它的表示分离，使同样的构建过程可创建不同表示。 组装一台配置项极多的电脑或一辆车，需要分步、可读地构建。
5 原型
Prototype		 创建型 用原型实例指定创建对象的种类，并通过复制这个原型来创建新对象。 对象创建成本高（要查库、算很久），直接克隆一份再改。
6 适配器
Adapter		 结构型 将一个类的接口转换成客户期望的另一个接口，使原本不兼容的类能一起工作。 接入第三方支付 SDK，把它的接口转成系统内部的统一接口。
7 桥接
Bridge		 结构型 将抽象部分与它的实现部分分离，使它们都可以独立地变化。 「形状 × 颜色」两个维度独立扩展，避免继承层次爆炸。
8 组合
Composite		 结构型 将对象组合成树形结构来表示「部分-整体」层次，使客户对单个对象和组合对象的使用具有一致性。 文件系统、组织架构、UI 容器——叶子与容器一视同仁地递归处理。
9 装饰器
Decorator		 结构型 动态地给一个对象添加一些额外的职责，比生成子类更灵活。 给数据流依次叠加压缩、加密、缓冲，任意组合且顺序可变。
10 外观
Facade		 结构型 为子系统中的一组接口提供一个一致的、更高层的界面，使子系统更易使用。 一个「一键下单」接口，内部封装库存、支付、物流多个子系统的调用。
11 享元
Flyweight		 结构型 运用共享技术有效地支持大量细粒度对象。 文本编辑器里几十万个字符共享同一份字形数据，只存位置与样式。
12 代理
Proxy		 结构型 为其他对象提供一种代理以控制对这个对象的访问。 远程代理、虚拟代理（大图懒加载）、保护代理（权限校验）。
13 责任链
Chain of Responsibility		 行为型 使多个对象都有机会处理请求，从而避免请求的发送者与接收者之间的耦合。 审批流、过滤器链、异常处理链——沿链传递直到有人处理。
14 命令
Command		 行为型 将一个请求封装为一个对象，从而使你可用不同的请求对客户进行参数化、支持撤销与排队。 编辑器的撤销/重做、任务队列、宏录制。
15 解释器
Interpreter		 行为型 给定一个语言，定义它的文法的一种表示，并定义一个解释器来解释该语言中的句子。 简单的表达式求值、规则引擎、SQL 子集解析。
16 迭代器
Iterator		 行为型 提供一种方法顺序访问一个聚合对象中的各个元素，而又不暴露其内部表示。 统一遍历数组、链表、树、图，客户只用一个 next()。
17 中介者
Mediator		 行为型 用一个中介对象来封装一系列对象的交互，使各对象不需要显式地相互引用。 聊天室、对话框里控件之间的联动——把网状依赖收敛为星形。
18 备忘录
Memento		 行为型 在不破坏封装性的前提下，捕获并保存一个对象的内部状态，以便日后恢复。 撤销操作、事务回滚、游戏存档。
19 观察者
Observer		 行为型 定义对象间一对多的依赖关系，当一个对象状态改变时，所有依赖者都得到通知并自动更新。 事件监听、MVC 中模型变化后多视图刷新、价格订阅推送。
20 状态
State		 行为型 允许一个对象在其内部状态改变时改变它的行为，看起来像是修改了它的类。 订单状态机、电梯、TCP 连接——不同状态下的同一操作行为不同。
21 策略
Strategy		 行为型 定义一系列算法，把它们封装起来并使它们可以互相替换，让算法独立于使用它的客户变化。 多种计价/排序/压缩算法，运行时按配置切换。
22 模板方法
Template Method		 行为型 定义一个操作中的算法骨架，而将一些步骤延迟到子类中，使子类可不改变算法结构就重定义某些步骤。 框架的钩子方法：流程固定，具体步骤由子类填空。
23 访问者
Visitor		 行为型 表示一个作用于某对象结构中的各元素的操作，使你可以在不改变各元素类的前提下定义作用于这些元素的新操作。 对 AST 或文档树做多种分析（求值、格式化、导出），操作易增、元素稳定。

23 模式的记忆口诀 创建型 5：单例、工厂方法、抽象工厂、建造者、原型——「单工抽建原」；
结构型 7：适配器、桥接、组合、装饰器、外观、享元、代理——「适桥组装外享代」；
行为型 11：责任链、命令、解释器、迭代器、中介者、备忘录、观察者、状态、策略、模板方法、访问者——「责命解迭中备观状策模访」。
数量校验：5 + 7 + 11 = 23。考试若让你「列举行为型模式」，至少写出 8 个才算稳。

4.2　三型分类的划分依据

分类不是按「代码长什么样」，而是按模式的意图——它想让系统的哪一部分获得灵活性。 判断一个模式属于哪型，只问一句：它在给什么东西留出变化空间？

维度 创建型（5） 结构型（7） 行为型（11）
关注点 对象的创建机制 类与对象的组成结构 对象间的职责分配与算法
留出的变化点 「创建什么、由谁创建、怎么创建」 「怎么拼装、怎么加职责」 「谁来做、怎么协作、流程怎么走」
典型手法 把 new 藏到接口之后 组合、委托、继承 委托、回调、多态分派
解决的痛点 硬编码具体类导致换实现要改代码 继承层次爆炸、接口不兼容 大量 if-else、调用方与被调方强耦合
数量 5 7 11
易错归属 原型（看着像结构，实为创建） 享元（重点是共享，不是性能优化技巧） 模板方法（用继承实现，容易被误当结构型）

分类只按「意图」，不按「实现技术」 模板方法用继承实现，状态用委托实现，但两者都是行为型——因为它们的意图都是分配职责与算法。 反过来，工厂方法既可能是创建型（GoF 的定义），也会被某些教材称为「多态工厂」； 判断时永远回到意图。这是选择题最爱设的陷阱。

4.3　模式 vs 惯用法 vs 架构模式：差别就是抽象程度

课件用一句话点明了三者的界限：「区别就是抽象的程度」。 架构模式关注系统架构，设计模式原则上不影响系统架构，惯用法则绑定具体编程语言。 再补上框架与类库，就构成了下面这张完整的层次表。

维度 惯用法 Idiom 设计模式 Design Pattern 架构模式 Architectural Pattern
抽象程度最低（语言级）中（类与对象级）最高（子系统 / 系统级）
粒度几行代码的写法若干类与接口的协作模块划分、通信机制、部署结构
是否依赖语言强依赖，换语言即失效不依赖，可用任意 OO 语言实现不依赖
对架构的影响无原则上不影响系统架构本身即定义架构
典型例子C++ Pimpl、Java 双检锁观察者、策略、工厂方法分层、MVC、管道-过滤器、微服务
课件定位特定程序语言中的模式经过验证的适用原则，微架构关注系统架构

课件特别强调了两条包含关系，考简答题时几乎必问：

  • 一个系统的架构可以包含多个架构模式——例如同时采用分层架构与 MVC。
  • 架构模式可以包含多个设计模式，但这不是必要条件——最经典的例子是 MVC 包含观察者模式、组合模式、策略模式：模型变化通知视图是观察者， 视图的嵌套结构是组合，控制器选择不同的视图/行为是策略。

课件还给了两句高度凝练的判断：设计模式描述的是细致的模式，架构模式是粗略的模式； 以及设计模式是「经过验证的适用原则」，属于微架构—— 其结构和机制决定「把子系统拆分成哪些部分、并确定相互间的合作」。

4.4　模式、框架、类库：三种不同性质的「复用」

这是最容易混为一谈的一组。核心差别不在「代码多少」，而在控制权在谁手里。

维度设计模式类库 Library框架 Framework
本质 知识 / 经验，是描述而非代码 可被调用的代码集合 可运行的半成品应用，含骨架与扩展点
控制权 无（不涉及调用关系） 你调用它（我方控制） 它调用你（控制反转 / 好莱坞原则）
复用单位 设计与结构 函数 / 类 架构骨架与生命周期
与模式的关系 —— 通常不含模式，只是工具 内部大量使用模式（如 Spring 用单例、工厂、代理、模板方法）
典型例子 观察者模式 JDK 集合类、Guava Spring、MyBatis、Vue
误用后果 过度设计，抽象层空转 无（选错就换） 被框架绑定，替换成本极高

一句话记住三者 模式是「怎么想」，类库是「拿来用」，框架是「照着填」。 用类库时程序的主控权在你手上；用框架时主控权交给了框架，你只填写扩展点—— 这个「控制反转」就是框架与类库的分水岭，也是「框架里必然有模式、但模式绝不是框架」的原因。

4.5　四组高频混淆的模式辨析

第 4 章会逐个展开，这里先记住「差在哪一个点上」，选择题基本够用。

对比关键差异判断口诀
策略 vs 状态 策略由客户显式选择，算法之间互不知道；状态的切换由对象内部驱动，状态之间知道彼此并会触发转移 「谁决定换」——客户选策略，对象自己变状态
装饰器 vs 代理 装饰器增强功能且可层层嵌套；代理控制访问，通常只包一层 「加功能还是管访问」
适配器 vs 桥接 适配器让已有的不兼容接口能协作（事后补救）；桥接是设计时就分离抽象与实现两个维度 「事后补救还是事前分层」
组合 vs 装饰器 结构几乎相同（都持有同类型引用）；组合表示部分-整体的树，装饰器表示功能叠加的链 「是树还是链，是包含还是增强」
工厂方法 vs 抽象工厂 工厂方法创建一个产品；抽象工厂创建一族相关产品 「一个还是一族」
外观 vs 中介者 外观是单向简化调用（客户→子系统）；中介者是双向协调（同事之间互相隔离） 「简化入口还是协调交互」
05

易错点

#

这些是批改时最常见的失分点，多来自「把 A 当成 B」。

  • 把「模式」当成「可复用的代码」。 模式描述的是元素、职责与协作关系，不是一段能直接粘进项目的代码。 同一模式在 Java、C#、Python 里的实现可以完全不同；把模式当代码库用， 就会出现「为了用模式而硬套结构」的典型错误。
  • 认为 GoF「发明」了 23 种模式。 GoF 做的是总结、分类与命名。模式来自大量优秀设计中反复出现的做法， 其思想源头是 Christopher Alexander 的建筑模式语言。答「模式是专家发明的巧妙技巧」 会直接失分。
  • 只写模式的「效果」里的优点，不写代价。 四要素中的「效果」必须包含代价：性能下降、复杂度上升、类数量增加。 课件明确列了这三条。简答题只夸好处，通常只能拿一半分。
  • 按「实现技术」判断模式属于哪一型。 模板方法用继承实现、状态用委托实现，但两者都是行为型； 原型通过复制对象创建实例，看着像结构型，实为创建型。 分类依据永远是意图，不是代码长相。
  • 把「模式」与「框架 / 类库」混为一谈。 模式是知识，类库是你调用它的代码，框架是它调用你的半成品（控制反转）。 「框架里用了很多模式」正确，但「框架就是一组模式的集合」错误—— 框架还包含基础设施、生命周期管理与约定。
  • 以为「用了模式」就等于「设计得好」。 模式有代价，误用即过度设计。判断标准是有没有隔离真实的变化点： 只有一种实现且明确不会再有第二种时，引入抽象层是负收益。 同样，单例被当全局变量滥用时会破坏单一职责与可测试性。
  • 把反模式理解为「写得很差的代码」。 反模式有两个必要成分：初看合理且有据可查地造成损害。 它是一类「被证伪的伪模式」，而不是随手写的烂代码。答题时要点出「反复出现」与「看似是解法」这两点。
  • 混淆设计模式与架构模式的层次。 课件原话：设计模式描述的是细致的模式，架构模式是粗略的模式； 设计模式原则上不影响系统架构，属于微架构。 另外「架构模式包含多个设计模式」成立，但「架构模式必须包含设计模式」不成立—— 这是课件特别标注的「不是必要条件」。
