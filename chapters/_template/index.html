第 4 章 · 面向对象设计模式

行为型模式：观察者模式

当对象之间是「一对多」依赖，且被依赖对象的状态变化需要自动通知所有依赖者时， 观察者模式把「谁变了」与「谁关心」解耦。本节以它为例，演示本站在章节页里提供的全部组件。

02

核心概念

#

先建立术语，再看结构与代码。

观察者模式 Observer

定义对象间的一种一对多的依赖关系，当一个对象（Subject）的状态发生改变时， 所有依赖它的对象（Observer）都得到通知并自动更新。

行为型 对象模式

主题 / 被观察者 Subject

持有观察者列表，提供 attach、detach 与 notify 三个操作， 自身不关心观察者具体是谁、会做什么。

角色

推模型 vs 拉模型 Push / Pull

推模型把变更细节随通知一起传给观察者；拉模型只发「我变了」的通知， 由观察者自己回查需要的数据。前者简单，后者更灵活、耦合更低。

易混淆

发布-订阅 Pub-Sub

观察者模式的解耦升级版：发布者与订阅者之间插入事件通道 / 消息代理， 彼此甚至不知道对方存在。观察者模式中两者通常仍然相识。

03

结构与实现

#

角色协作流程

观察者模式的结构非常轻：Subject 维护一个观察者容器，Observer 提供一个 update 回调。当 ConcreteSubject 的状态变化时，遍历容器逐个调用 update，就完成了「广播」。

  1. 观察者实例通过 attach(observer) 注册到主题；
  2. 主题内部状态改变，调用 notify()；
  3. notify() 遍历观察者列表，调用每个观察者的 update()；
  4. 观察者收到通知后，拉取或接收新数据并刷新自身；
  5. 不再需要通知时调用 detach(observer) 注销。

答题技巧 简答题问「观察者模式的优点」时，抓住「解耦」与「开闭原则」两点展开： 主题只依赖抽象的 Observer 接口，新增观察者无需修改主题代码。 再补一句「支持广播通信」，基本就能拿满分。

推模型与拉模型的写法差异

推模型把数据塞进回调参数；拉模型只传「发生了什么」，由观察者回查主题。

注意 notifyObservers() 中遍历的是观察者列表的副本。 如果直接遍历原列表，而某个观察者在 update() 里调用了 detach()，就会抛出 ConcurrentModificationException。

典型应用

GUI 事件监听

按钮（Subject）被点击时通知所有注册的监听器（Observer）， 界面逻辑与事件源分离。Java 的 ActionListener 就是这一结构。

MVC 的模型-视图

Model 状态变化通知多个 View 刷新，同一份数据可以有多套展示， 新增视图无需改动 Model。

横向对比

#

考试最爱在这里出选择题：意图相近的模式放在一起辨析。

观察者 vs 发布-订阅 vs 中介者

维度 观察者模式 发布-订阅 中介者模式
耦合方式 主题知道观察者接口 双方互不相识，经事件通道 同事对象只认识中介者
拓扑 一对多 多对多 星形（网状收敛为一点）
通知方向 单向广播 双向 集中转发
典型实现 addListener 消息队列、EventBus 聊天室、对话框协调器
层级 设计模式（对象级） 架构风格 / 集成模式 设计模式（对象级）

推模型 vs 拉模型

对比项推模型拉模型
通知内容携带完整变更数据仅事件类型
实现复杂度低中（需回查接口）
耦合度主题需了解观察者所需数据观察者依赖主题接口
效率一次通知即可用可能多次回查
适用数据结构简单、变化少数据结构复杂、观察者需求各异
05

易错点

#

这些是本知识点最容易失分的地方。

  • 把观察者模式等同于事件总线。 GoF 的观察者模式中 Subject 直接持有 Observer 引用；一旦引入中间的事件通道， 严格说已经演进为发布-订阅，属于架构层面的解耦。
  • 忘记注销导致内存泄漏。 长生命周期的 Subject 持有短生命周期 Observer 的强引用，对象无法被回收。 必须在销毁时 detach，或使用弱引用。
  • 在通知里直接修改观察者列表。 遍历过程中 attach/detach 会触发并发修改异常，应先复制列表再遍历。
  • 误认为通知是同步可靠的。 默认实现是同步顺序调用，一个观察者抛异常会影响后续观察者； 需要可靠性时应引入异步与重试机制。
