第 1 章 · 面向对象设计的原理

从抽象到 SOLID：把「好设计」变成可判定的标准

面向对象设计要回答的不是「怎么用继承」，而是「怎么让软件改得动」。 本章先给出四个「难维护」的症状，再逐个给出对应的设计原则， 最后用 UML 类图把这些意图画成别人看得懂的图。后面四章的每一个设计模式，都建立在这里。

学习目标

读完后应能做到以下几点，每一条都可以自我检验。

  1. 能用「症状 → 原则 → 手段 → 结果」四段式，说明六大设计原则各自治的是哪一类可维护性问题。
  2. 能说清抽象、封装、信息隐藏三者的分工，并指出缺少其中任一者时程序会付出什么代价。
  3. 能读懂并画出类图中的泛化、实现、依赖、关联四种关系，尤其能说清依赖箭头的方向为什么不能画反。
  4. 能在给定代码里指出它违反了哪条原则，并写出符合开闭原则的改法（如 Shape、Copy、正方形/矩形三个反例）。

02

核心概念

#

先把术语钉死。本章所有简答题的失分，一半来自术语混用。

抽象 Abstraction

抽出与当前问题相关的特征、忽略其余细节。方法的接口就是对象功能的抽象： 抽象只声明「能做什么」，由具体对象实现接口定义的方法。 抽象是开闭原则的关键——没有抽象，扩展就必须改调用方。

单类设计 OCP 前提

封装 Encapsulation

把方法与数据封装成一个对象，对外只保留接口，内部实现细节不可见。 封装是信息隐藏的实现机制，信息隐藏是封装的目标。

单类设计

信息隐藏 Information Hiding

封装内部属性，外部只能通过接口访问（外部属性），这就是保密原则。 好处是：内部实现可以独立更换，而不会波及使用它的代码。

易混淆

继承 Inheritance

子类复用父类的结构与行为，并可用多态覆盖父类方法。 继承是最强的耦合：子类连父类的实现细节一起继承， 所以「滥用继承」是里氏替换原则要治的第一大病。

单类设计 易滥用

多态 Polymorphism

同一条消息，不同对象给出不同响应：调用方只写 s.draw()， 运行时才决定执行哪个子类实现。多态程序的正确性由里氏替换原则保证—— 子类实现必须与客户对基类的期望一致。

正确性

接口与实现分离 Interface / Implementation

客户代码只依赖接口，具体实现可以在不改客户代码的前提下替换。 这是开闭原则、依赖倒置原则、接口隔离原则共同的落地手段， 也是后续所有设计模式的技术基础。

手段

职责 Responsibility

职责不是「方法有多少个」，而是引起这个类变化的原因。 单一职责的准确表述是：一组方法只能有一个变化轴线， 并且最好有一个概念统摄这组方法。

SRP 易错

内聚 Cohesion

子系统内部各成分相互合作、相互依赖的程度。内聚越高， 一个模块内部的改动越不容易外溢。目标是「高内聚」。

松耦合

耦合 Coupling

子系统之间互相影响的程度，也叫功能耦合。耦合越低， 替换或新增一个子系统时牵动的代码越少。目标是「低耦合」。

松耦合 易与内聚混淆

契约式设计 Design by Contract

把客户类与服务器类的关系写成形式化的契约，用断言表达： 前置条件约束调用者（被调用者的权益）、后置条件约束被调用者（调用者的权益）、 不变式是对所有操作都成立的类级断言。

正确性 LSP 的落地

胖接口与接口污染 Fat Interface

为了减少类的数目，往接口里塞不属于它的方法，接口就被污染、变胖。 后果是：复用这个接口的客户被迫实现并维护自己用不到的方法， 本来无关的客户之间产生了意外耦合。

ISP

软件腐化的四个症状 Rigidity / Fragility / Immobility / Viscosity

过于僵硬：难加入新功能；过于脆弱：一改就牵一发动全身； 复用率低：想复用的代码被一堆依赖缠住拆不出来； 黏度过高：保持原设计意图的改法总比权宜之计更难走。

问题域 Robert C. Martin
03

原则逐条拆解

#

六条原则不是并列的口号，而是「同一件事的六个切面」。下面按课件的顺序逐条拆， 每条都给出「它治什么病、靠什么手段、违反后长什么样」。

一、先有病，才有药：软件为什么会难维护

Robert C. Martin 把「软件难维护」归结为四个症状。它们不是四个独立的问题， 而是同一个病根的四种表现——变化无法被隔离。

症状英文典型表现对应的设计目标
过于僵硬Rigidity很难加入新性能，一加就要动老代码可扩展性
过于脆弱Fragility很难改动，牵一发动全身；与僵硬同时存在灵活性
复用率低Immobility类似的算法、函数、模块被一堆依赖缠住，拆不出来可复用性
黏度过高Viscosity保持原设计意图的改法总比权宜之计难走可插入性

注意「复用率低」这一条课件里说得很直白：最好的复用方法变成了 Ctrl-C / Ctrl-V。 这句话是反讽——当代码拆不出来时，复制粘贴就成了唯一可行的「复用」， 而它带来的是同一份逻辑的多处副本，日后每一处都要单独改。

「黏度过高」的定义值得单独记：一个改动通常有两种走法，a 是保持原始设计意图与原始框架， b 是权宜之计、牺牲中长期利益。如果系统里总是 b 更容易，这个系统的黏度就过高。 也就是说，黏度衡量的是「设计本身对正确做法的阻力」。

二、可读性、正确性、可扩展性：三条验收线

课件用三条线把原则分了组，这是最省力的记忆结构——考场上问「某原则解决什么问题」， 先想它挂在哪条线上。

质量目标由哪些原则支撑一句话理解
可读性 封装、抽象与信息隐藏；关注点分离与单一职责原则 别人（和三个月后的你）能不能看懂这段代码在干什么
正确性 里氏替换原则；契约式设计；多态程序的正确性 多态调用在运行时选中的实现，是否仍然满足调用方的假设
可扩展性 接口隔离原则；松耦合；里氏替换原则；开闭原则；依赖倒置原则 加功能时要不要改已有的、已经测过的代码

另一条更细的分组是按「几个类在合作」来分：单个类的设计原则是抽象、封装与信息隐藏、 关注点分离与单一职责、接口隔离；多个合作类的设计原则是松耦合、开闭、里氏替换、依赖倒置与契约式设计。 单类设计管「这个类自己别太胖」，多类设计管「类与类之间的线怎么连」。

三、抽象、封装与信息隐藏

这三个词经常被混着用，但课件把它们分得很清楚：

  • 封装是动作——把方法和数据封装成一个对象，实现「信息隐藏、接口对外」。
  • 抽象是取舍——方法的接口使对象功能抽象，具体对象负责实现接口定义的方法。
  • 信息隐藏是结果——封装内部属性，外部只能通过接口访问（也就是课件说的「外部属性」），这就是保密原则。

三者的关系是：封装提供了隐藏的机制，抽象提供了对外的契约， 信息隐藏是这套机制要达成的目标。缺了抽象，封装就只是把一堆细节锁进黑箱， 外面照样得知道黑箱里有什么；缺了封装，抽象就只是一纸声明，谁都能绕过接口直接改内部状态。

答题技巧 简答题问「封装与抽象的区别」，最稳的三段式是： ① 封装是实现层面的机制，隐藏内部数据与实现；② 抽象是认知层面的取舍，只暴露与问题相关的特征； ③ 二者共同服务于信息隐藏，最终目的是让变化被限制在类的内部。三句话，三个层次，不重叠。

四、开闭原则 OCP：本章的核心

开闭原则由 Bertrand Meyer 于 1988 年提出，课件直接称它为「面向对象设计中最重要、最核心的原则之一」。 定义原文是：

software entities (classes, modules, functions, etc.) should be open for extension, but closed for modification. 即软件实体（类、模块、函数等）应当对扩展开放，对修改关闭。 这里的「软件实体」可以是一个软件模块、一个由多个类组成的局部结构，也可以是一个独立的类。

它对应的三个设计目标，恰好是前面四个症状的反面：

  • 可扩展性（Extensibility）——与「过于僵硬」相反；
  • 灵活性（Flexibility）——与「过于脆弱」相反，允许代码修改平稳发生，不波及别的模块；
  • 可插入性（Pluggability）——「黏度过高」的反面。

五、里氏替换原则 LSP：继承什么时候是错的

里氏替换原则由 Barbara Liskov 与 Jeannette Wing 于 1994 年提出 （Liskov 是 2008 年图灵奖得主、美国第一位计算机科学女博士）。 课件反复强调它针对的是一个相当普遍的现象：滥用继承。 「以为会用继承、会用多态，便很 OO」——这是误解；知道 ISA 关系还不够， 还得知道 ISA 真正的含义。

定义只有一句：

Subtypes Must Be Substitutable For Their Base Types. 子类型必须能够替换掉它们的基类型。

Liskov 1988 年的原始表述是：

若对于每一个类型 S 的对象 o1，都存在一个类型 T 的对象 o2，使得在所有针对 T 编写的程序 P 中， 用 o1 替换 o2 后，程序 P 的行为功能不变，则 S 是 T 的子类型。

违背它的后果，课件讲得很清楚：如果某个函数使用了指向基类的指针或引用却违背 LSP， 那么这个函数必须了解该基类的所有派生类——而这显然又违背了 OCP。 两条原则在这里咬合：LSP 是 OCP 能够成立的前提。

六、依赖倒置原则 DIP：把箭头的方向掰过来

依赖倒置原则出自 Robert C. Martin 1996 年为《C++ Reporter》所写专栏 Engineering Notebook 的第三篇，后收入其 2002 年的《Agile Software Development》。 课件从一个只有三个模块的小程序讲起：把键盘输入的字符拷贝到打印机上。

「倒置」到底倒置了什么？课件说：很多传统软件开发方法（比如结构化分析与设计）总是倾向于创建 高层模块依赖低层模块、抽象依赖细节的结构；而一个设计良好的面向对象程序， 其依赖关系结构相对于传统过程式方法而言，就是被「倒置」了。 原来箭头从「策略」指向「机制」，现在两端都指向中间的抽象。

层次化：依赖是可传递的

Booch 说过：所有结构良好的面向对象架构都具有非常清晰的层次， 每一个层次通过一个被很好地定义和控制的接口向外提供一系列相互内聚的服务。 但如果只是简单地照这句话分层，会得到这样的结构： Policy Layer 调用 Mechanism Layer，Mechanism Layer 再调用 Utility Layer。 课件点出了其中隐伏的特性：Policy Layer 对其下层次一直到 Utility Layer 的改动都非常敏感， 因为依赖是可传递的。

更合适的模型是在层与层之间插入抽象接口：Policy 依赖 Mechanism Interface（抽象）， Mechanism 实现它；Mechanism 依赖 Utility Interface（抽象），Utility 实现它。 这样 Utility 的变化被 Utility Interface 挡住，传不到 Policy。 这正是课件第 44、45 页那两张对照图要表达的东西。

七、接口隔离原则 ISP：别把不用的方法塞给客户

ISP 处理的是「胖接口」。当接口不内聚时，说明这个类具有胖接口； 胖接口可以分解成多组方法，每一组服务于一组不同的客户程序—— 一些客户用这一组，另一些客户用另一组。

定义：不应该强迫客户依赖于它们不使用的方法。

换个说法：一个类对另一个类的依赖性应当建立在最小的接口上； 使用多个专门的接口比使用单一的总接口要好。

接口污染是怎么发生的

  • 接口污染就是为接口添加了不必要的职责；
  • 常见动机是「在接口中加一个新方法只是为了减少类的数目」；
  • 持续这样做，接口就被不断污染、变胖；
  • 课件明确指出：类的数目不是问题，接口污染才会带来维护与重用方面的问题；
  • 最常见的问题是——为了重用被污染的接口，被迫实现并维护不必要的方法。

课件的门与定时器

一个安防系统里有 Door 接口（Lock / Unlock / IsDoorOpen），还有一个 Timer，它通过 TimerClient 接口的 TimeOut() 回调通知超时。 TimedDoor 需要在门开太久时报警，于是最省事的做法是把 TimeOut() 直接加到 Door 上。课件列出四条反对理由：

  1. 并非所有种类的门都需要计时；
  2. 最初的 Door 抽象与计时没有任何关系；
  3. 与计时无关的 Door 派生类将被迫为 TimeOut 提供空实现（nil implementation）；
  4. 使用这些派生类的应用还必须 #include TimerClient 的定义，尽管它根本用不到。

课件给这种状态的定性是：Door 的接口被它并不需要的接口污染了。

三种分离手法

手法做法结构特点
继承法 让 Door 直接实现 TimerClient，TimedDoor 继承 Door 所有门都沾上了计时接口——只是把污染往上提了一层，并未消除
委托法
对象适配器		 写一个 DoorTimerAdapter : public TimerClient，内部持有 TimedDoor&，TimeOut() 里转调 itsTimedDoor.DoorTimeOut() 用组合把两个接口接起来，Door 保持干净
多继承
接口法 / 类适配器		 class TimedDoor : public Door, public TimerClient，只覆盖 TimeOut() 用多继承让需要计时的门同时具备两个身份

课件的结论把 ISP 与适配器模式连了起来：胖接口会导致本应彼此隔离的客户之间产生意外耦合； 借助 ADAPTER 模式——委托（对象形式）或多继承（类形式）——可以把胖接口拆成抽象基类， 切断客户之间不需要的耦合。这是本章与第 4 章之间的一条明线。

八、单一职责原则 SRP：最简也最难

课件对 SRP 的定义有四句话，每一句都在纠偏：

  • 一个类应该有且仅有一个职责；
  • 一个类的职责是指引起该类变化的原因；
  • 并非极端到一个类只设定一个方法，而是一组方法只能有一个变化轴线；
  • 最好有一个概念统摄该组方法。

所以 SRP 的判据不是「方法数量」，而是「变化的原因有几个」。一个类如果有两个不同的变化原因， 就相当于把两个职责耦合在一起：其中一个职责变化时，可能影响另一个职责的运作。 课件也给出了代价：一个类（或大到模块、小到方法）承担的职责越多，它被复用的可能性越小。

课件对 SRP 的评价很有意思——它是实现高内聚、低耦合的指导方针， 在很多代码重构手法中都能找到它的存在，它是最简单但又最难运用的原则。 难在「发现类的多重职责」这一步，这需要较强的分析设计能力与相关重构经验。

例 1：Rectangle 的两个方法

Rectangle 类有两个方法：一个把矩形画到屏幕上，另一个计算矩形面积。 看起来都是「矩形的事」，但客户不是同一批： Computational Geometry Application 只用 area()， Graphical Application 只用 draw()。而两个应用都要连到 GUI， 于是几何计算应用也被迫依赖了绘图代码。按职责拆开之后， Geometric Rectangle 只保留 area()， Rectangle 只保留 draw()，两条依赖线各走各的。

例 2：Modem 接口

四个方法里其实藏着两个职责：dial / hangup 是连接管理， send / recv 是数据通信。两者变化的原因不同 （换连接协议 vs 换编码方式），应当拆成两个接口。

例 3：Automobile 的七个方法

Automobile 上有 start()、stop()、 changeTires(Tire[])、drive()、wash()、 checkOil()、getOil(): int。用 SRP 分析一遍，会发现 「这七个方法真的都是 Automobile 的职责吗」——答案是否。 课件给出的迁移结果：

原方法迁到哪个类理由
drive()Driver → drive(Automobile)驾驶汽车是司机的责任，不是汽车本身的职责
wash()CarWash → wash(Automobile)CarWash 能处理汽车的清洗
changeTires()、checkOil()Mechanic → changeTires(Automobile, Tire[])、checkOil(Automobile)技工负责为汽车换轮胎并检查机油
start()、stop()、getOil()留在 Automobile现在 Automobile 只有单一的职责：处理它自己的基本功能

课件还给了一句很实用的自检：假如你所说的方法并不合理，那么这个方法就可能违反了 SRP。 换句话说，如果你没法为「这个方法为什么在这个类里」讲出一个单一的理由，它就放错了地方。

例 4：烦人的手机

手机把拍照、摄像、游戏、GPS 全塞进一个设备，结果是功能多、不专业： 拍摄不如照相机和摄像机，游戏不如 PSP，导航不如专业 GPS。 这个生活化的例子说明的道理是——职责堆叠不会让一个类变强，只会让它每一方面都变弱。

九、合成复用原则与迪米特法则

合成复用原则（组合优先原则，CRP）：在系统中应该尽量多使用组合和聚合关联关系， 尽量少使用甚至不使用继承关系。原因还是耦合：继承把子类和父类的实现绑死 （连 itsWidth / itsHeight 这种私有成员都继承过来了）， 而组合只依赖被组合对象的接口，替换实现不影响外层。

迪米特法则（最少知识原则，LoD）：一个软件实体对其他实体的引用越少越好； 或者说，如果两个类不必彼此直接通信，那么这两个类就不应当发生直接的相互作用， 而应通过引入一个第三者发生间接交互。它在课件里的重要性评级是三星（★★★☆☆）， 是六条里最低的，但「引入第三者」这个说法在后面中介者模式、外观模式里会反复出现。

松耦合与高内聚

课件用两个词把「好结构」量化了：

  • 功能耦合：子系统之间互相影响的程度；
  • 内聚性：内部互相依赖的程度，或子系统内部相互合作的程度。

目标就是一句话：设计松耦合的子系统，同时实现每个子系统高内聚。 松耦合能增加子系统之间连接的灵活性。注意这两个词的方向完全相反—— 一个量「之间」，一个量「之内」，考试里把它们用反是最常见的失分点。

十、契约式设计：把 LSP 写成可执行的断言

契约式设计（Design by Contract）描述的是客户类与服务器类之间的 C-S 关系， 要求具有形式上的一致性与精确的定义：在什么情况下执行哪种正确的程序流程。 落地手段是断言，分三类：

断言约束谁保护谁的权益含义
前置条件调用者被调用者调用前必须满足什么；对调用者提出要求
后置条件被调用者调用者返回时必须保证什么；是被调用者的责任
不变式类所有客户与类有关的断言，对所有操作都有效

把它和 LSP 接起来，就得到「覆写要遵守契约」这条规则， 也就是课件第 70、71 页那两张椭圆图（图 1-7、图 1-8）的结论：

  • 前置条件只能弱化，不能强化。子类方法可以接受比父类更宽松的输入， 这样原来能传父类的地方传子类也没问题；反过来就会拒掉合法的调用。
  • 后置条件只能强化，不能弱化。子类方法必须承诺至少和父类一样多， 这样调用者按父类契约写的后续逻辑才不会落空。

一句话记忆：子类要「要求更少、承诺更多」。这正是里氏替换原则在方法层面的可操作版本。

十一、UML 类图：六种关系的读法

课件里所有的结构图都是类图，用的是同一套 UML 记号：空心三角表示泛化（继承）， 带虚线箭头的表示依赖，«interface» 是接口构造型， 0..* 是多重性。读懂这六种关系，等于拿到了后续所有模式类图的钥匙。

六种关系按耦合强度从弱到强排列，考场上按这个顺序回忆最不容易漏：

  • 依赖（Dependency）：虚线 + 开口箭头，指向被依赖方。最弱，通常表现为「局部变量、方法参数、静态调用」。
  • 关联（Association）：实线（可带箭头），表示长期的结构性联系，可标多重性。
  • 聚合（Aggregation）：空心菱形在整体端，部分可脱离整体独立存在。
  • 组合（Composition）：实心菱形在整体端，部分的生命周期由整体决定，是最强的「整体—部分」。
  • 泛化（Generalization）：实线 + 空心三角，指向父类，即继承。
  • 实现（Realization）：虚线 + 空心三角，指向接口，即 implements。

十二、例题解析：6174 的面向对象走法

课件第 3 页给出的题目是：给定一个四位数（数字不完全相同），把这四个数字排成最大四位数与最小四位数， 求差；若不是 6174 则重复上述过程，最终会得到 6174，验证这个过程。 这道题本身是算法题，但它是最好的设计练习题——因为它一眼看去「没有对象」。

第一步：先看过程式写法长什么样

这段代码能跑，但用本章的尺子量，它同时踩了三条： 职责过多（main 里混了「拆数字、排序、求差、驱动循环、打印」五件事）； 对修改开放（想改成验证三位数的 495、或换成五位数，必须改 main）； 无法复用（求差逻辑被锁在 main 里，别的程序拿不到）。

第二步：按 SRP 拆职责

先用「变化的原因」这把刀切。四个变化原因，对应四个角色：

变化的原因职责落到哪个角色
数字怎么拆、怎么补零把数表示为固定位数的数字序列DigitNumber
排序规则变了（升/降、按位还是按数值）由数字序列求出最大数与最小数Extremes
变换规则变了（6174 之外还有别的常数）一次变换：给定数，产出下一个数KaprekarStep
终止条件与迭代策略变了驱动迭代直到收敛，并记录过程Convergence

拆完之后每个类的变化轴线只有一条：改位数只动 DigitNumber， 改常数只动 KaprekarStep，改输出方式完全不动前面任何一个。 这就是 SRP 带来的直接好处——课件说的「职责越多，被复用的可能性越小」反过来成立。

第三步：按 DIP 定依赖方向

驱动循环是高层策略（「一直迭代到稳定」），求差是低层机制。 按 DIP，高层不应依赖低层，二者都应依赖抽象。于是先抽出两个接口：

第四步：实现具体策略，验证 OCP

易错点

#

这些是阅卷时真正扣分的地方，不是知识点的重复。

  • 把「会用继承和多态」当成「很 OO」。 课件原话是「以为会用继承，会用多态，便很 OO」——这是被点名的误解。 知道 ISA 关系还不够，还要知道 ISA 的真正含义：ISA 是就行为功能而言的， 不是就现实世界的分类而言的。正方形在现实中是矩形，但 Square 对象不能替换 Rectangle 对象。
  • 把 OCP 理解成「代码永远不许改」。 课件明确说没有任何一个大程序能做到 100% 的封闭，因此要「选择性的封闭」—— 先判断这个模块应该对哪种变化封闭，再设计抽象。 写简答题时如果只说「不修改代码」，会显得没读过后半段。
  • 把「加 virtual」当成 LSP 的解药。 课件专门验证过这条思路：把 SetWidth / SetHeight 都改成虚函数之后， g() 的断言仍然失败。问题不在绑定方式，而在子类行为与基类契约不相容。 同样，加了 virtual 也不代表就满足了里氏替换。
  • 把依赖箭头的方向画反。 依赖箭头从使用者指向被依赖者；泛化 / 实现的空心三角从子类指向父类。 画反了，整张图的「谁依赖抽象」就完全说反，OCP / DIP 的论证也就跟着反了。
  • 把内聚和耦合用反。 内聚量的是「之内」，耦合量的是「之间」。常见错误是写「提高耦合度、降低内聚」—— 正好说反。正确表述永远是「高内聚、低耦合」。
  • 把 SRP 理解成「一个类只能有一个方法」。 课件特意否定了这个极端：并非为一个类只设定一个方法，而是一组方法只能有一个变化轴线， 最好还有一个概念统摄这组方法。Modem 拆分的依据是两个变化原因（连接管理 vs 数据通信）， 不是方法个数。
  • 把 ISP 和 SRP 混为一谈。 SRP 管的是类的职责（一个类一个变化轴线），ISP 管的是接口对客户的暴露面 （不强迫客户依赖它不用的方法）。Door 加 TimeOut 的例子里， 每个类自身职责并不乱，问题出在接口把不相关的能力捆给了所有客户。
  • 以为「减少类的数目」是好事。 课件原话：实际上，类的数目不是问题；接口污染才会带来维护和重用方面的问题。 为了少建一个类而把方法塞进现有接口，是用未来的维护成本换眼前的行数。
  • 把「合成复用」理解成「禁止继承」。 课件的表述是「尽量少使用甚至不使用继承关系」，是优先级排序而非禁令。 当子类能完全替换基类（满足 LSP）且确实是 is-a 行为关系时，继承仍然合理。
  • 忘了契约的方向。 子类覆写时应当「要求更少、承诺更多」——即前置条件弱化、后置条件强化。 写反成「前置条件强化、后置条件弱化」，正是 LSP 违规在方法层面的精确形态。

本章小结

#

把全章压缩成能背下来的话，再逐条自检。

一页纸小结

  • 面向对象设计的目标是可维护性 + 可复用性；复用能提高开发效率、提高质量、节约成本，恰当的复用还能改善可维护性。
  • 难维护的四个症状：过于僵硬、过于脆弱、复用率低、黏度过高；对应三个设计目标：可扩展性、灵活性、可插入性。
  • 封装给机制，抽象给契约，信息隐藏是目标；三者共同支撑可读性。
  • 单一职责：一个类只负责一个功能领域中的相应职责，判据是「变化的原因」而非方法个数。
  • 开闭：对扩展开放、对修改关闭，即在不修改源代码的基础上扩展行为；关键是抽象，且只能做到选择性的封闭。
  • 里氏替换：能用基类对象的地方一定能用子类对象；ISA 是就行为功能而言，不是就现实分类而言。
  • 依赖倒置：抽象不依赖细节，细节依赖抽象；针对接口编程，不要针对实现编程。
  • 接口隔离：客户端不应依赖它不用的接口，把大接口细化成小接口；胖接口要用适配器拆。
  • 合成复用：多用组合聚合、少用继承；迪米特：少引用、必要时引入第三者。
  • UML 六种关系按耦合从弱到强：依赖 → 关联 → 聚合 → 组合 → 泛化 / 实现。
  • 契约式设计把 LSP 变成断言：子类覆写只能弱化前置条件、强化后置条件。
